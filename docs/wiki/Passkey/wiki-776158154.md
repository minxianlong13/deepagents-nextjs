### Introduction

The Event Metadata Object (EMO) is a standardized, JSON-based contract designed to universally normalize incoming event-related data from external sources into a uniform internal representation.

By providing a consistent schema and format, the EMO simplifies integrations, reduces data transformation complexity, and ensures that data can be seamlessly passed through the Passkey ecosystem for:

-   event creation
-   registration linking
-   and inventory management.

### Purpose and Scope

#### **Purpose:**

-   Define a formal contract (schema) that represents all necessary event data (and related resources) to create and provision an event in the Passkey ecosystem.
-   Open the door to support multiple external input formats _**(CSV, XLS,** **PDF, etc.insially will rely on XLS only**_)  by normalizing them into a single, consistent JSON structure.
-   Facilitate transformations needed for public APIs, making it easier to integrate with third-party systems.

#### **Scope:**

-   The EMO will initially focus on room list-based event creation scenarios.
-   In future phases, the EMO can be extended to other request types _(e.g., GML requests, RFP, RFQ)._
-   The specification includes both a JSON schema and a corresponding GraphQL schema definition to ensure compatibility with Apollo/GraphQL-based services.

### Terminology

-   **EMO (Event Metadata Object):** A JSON object encapsulating all the data required to create and provision an event.
-   **RLM (Room List Mapping):** A service and data model that maps raw uploaded file data (e.g. XLS columns) to normalized EMO fields.
-   **DynamoDB Mappings Store:** A persistence layer for field mappings generated from raw input files.
-   **Raw Data Resource:** The original, customer-provided Excel file (e.g., XLS, CSV, XLSX), stored in S3 or via the Cvent File Upload service.
-   **Passkey-Reglink:** A service that can create events and associated resources. The EMO will be integrated into this workflow.

### High-Level Architecture

1.  **Raw Input File (EXCEL):** Customer uploads a room list or other data file.
2.  **RLM Service:** Automatically analyzes the file, identifies column-to-field mappings, and stores the resulting mapping metadata in DynamoDB.
3.  **EMO Generation:** Using the stored mappings and raw file data, the RLM service (or a dedicated EMO service) constructs a JSON-based EMO.
4.  **Integration with Passkey-Reglink:** The EMO is then passed to the passkey-reglink service, which consumes the EMO to create the event, attendee types, room blocks, and other necessary resources.

### Key Components of the EMO

-   **Event-Level Data:** Basic event properties (e.g., event name, start/end dates, venue details).
-   **Room Block Information:** Information about room types, inventory, and block allocations derived from the parsed input file.
-   **Attendee Data (Optional):** Potential attendee types or other event participants, if provided.
-   **Mappings & Normalizations:** Metadata about how raw fields map to normalized EMO fields.

**Example:**

-   `eventId`: The internal Passkey event identifier that will be assigned after the event is created.
-   `rawFileId`: The identifier of the source data file from S3 or the file upload service.
-   `mappings`: A structured list of fields mapping raw columns to EMO attributes.

### Integration with Passkey-Reglink

-   **Existing Endpoint Reuse:** The EMO schema is derived from an object form factor currently used by `passkey-reglink`.
-   **Direct Alignment:** The `RoomBlockRequest` interface (currently used by GML requests) will inform the structure of the EMO.
-   **Flow:**
    1.  User uploads file.
    2.  Mapping is generated and stored.
    3.  EMO is created from mappings.
    4.  EMO is sent to `passkey-reglink` via a compatible endpoint.
    5.  `passkey-reglink` creates the event and provisions resources based on the EMO.

### Infrastructure and Dependencies

-   **DynamoDB:** Stores column-to-field mappings and transient state.
-   **S3 (or Cvent File Upload Service):** Stores raw input files and possibly cached EMO documents.
-   **RLM Service:** Responsible for parsing raw data, generating mappings, and producing EMOs.
-   **Passkey-Event-Requests Service:** Will serve as the main interface for creating and managing Event Requests, including those that produce EMOs.
-   **Security & PCI Compliance:** Additional sanitization steps required for files and data, considering 2025 DITRA compliance.

### Security and PCI Considerations

-   Ensure that any sensitive data (e.g., PII or PCI data) is sanitized before producing the EMO.(  could we do integration with Amazon Macie?)
-   JSON schema should not contain raw credit card data or similarly sensitive fields.
-   Logging and storage must comply with relevant standards and ensure no sensitive data is exposed in logs.
