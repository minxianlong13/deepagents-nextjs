This page is the working requirements for Phase 1 messaging as the project restarts. Where it differs from the Project Phases page or the discovery page, this page wins.

## summarySummary

Phase 1 adds a Messages section to the event record in both Manage and Planner Portal. In it, the event organizer side (acting as one participant, even if multiple users all have access to the event) and each event-level planner hold one continuous thread per pair of participants per event. Planners can also message each other the same way. Items marked **Decision** link to the decisions table at the end.

**Biggest current risk:** one thread per pair means unrelated topics pile into one long thread.

**Biggest blocker:** the email service (ESS) drops a thread's email record after 30 days, which stops email alerts and reply by email on older threads. See Technical constraints.

**In scope for Phase 1**

-   New Messages section on the event, in Manage (under Communications) and in Planner Portal
-   Organizer to planner, planner to organizer, planner to planner, within one event
-   Organizer can message a planner the moment the planner's email is assigned to the event on the Planners tab, before the planner has an account or has logged in
-   Multi-select To line, including Select all planners: the organizer can select several planners in one new message. This is not a group message. The system creates a separate individual thread with the same message between the organizer and each selected planner.
-   Planners can only see the messages they are participating in
-   Reply in app; email notification to planners with reply link and reply by email
-   Messages section empty states, including the organizer view when no planner is assigned
-   Unread indicators and in-app alerts

**Out of scope for Phase 1**

-   Sub-block group (SBG) contacts as senders or recipients (**Decision 1**, decided)
-   Read and write permissions and the admin view (Phase 2)
-   Group threads with more than two participants (Phase 3)
-   Topic or subject-based threads, attachments, search, edit, delete, recall (Phase 4 or later)
-   Messaging across events
-   Migrating existing Bulletin Board messages

Rules

1.  Messaging is available only on an event with at least one event-level planner assigned, or the organizer sees the no-planner state (Screen states).
2.  A planner sees only participants on events they are assigned to. They never see planners on other events.
3.  Every message shows which person sent it, even when the organizer side sent it. For example: "Aspen Lee, DF Meetings".
4.  Planner recipients see the organizer as one recipient option, labeled with the event owner's account name. Any role text in parentheses is removed so it reads as a customer-friendly company name, for example "DF Meetings", not "DF Meetings (Organizer)" (**Decision 2**).
5.  A planner can be messaged the moment a Manage user assigns their email to the event on the Planners tab. They do not need a Planner Portal account or a past login. The message is delivered by email, and the thread is waiting in Planner Portal when they first log in with that email.

**Call center users** can open the event's Messages section and read every organizer thread, but cannot send, reply or mark unread. No event-level permission controls this: the code checks for the call center user type, the same way it applies their other restrictions.

-   New message, the reply box and Mark unread are hidden for them (not just disabled), and the no-planner state shows no Add a planner button.
-   Opening a thread does not change the organizer side's shared read state, so the users who need to reply keep their alerts.
-   Unread messages do not appear in their bell count or notifications panel.

**Participating hotels (Decision 3):** hotels participating in an event they do not own (CW and MP events) are excluded from messaging. Their users see no Messages section, no threads, no message alerts and no unread messages in their bell count, and are never offered as recipients. A hotel that owns the event (HD events) is the event organizer and keeps full messaging. This overrides the hotel rows in the permission matrices on the Project Phases page.

## thread-modelThread model

Each event has at most one thread per pair of participants. All messages between that pair on that event, on any topic and any day, go into that thread in time order.

Rules

1.  A thread has its own thread ID, an event ID, and exactly two participants. In Phase 1, the organizer side counts as one participant.
2.  Sending to a pair that already has a thread on the event appends to that thread. Otherwise the system creates the thread with the first message.
3.  Sending to several recipients at once is not a group message. It fans out: one copy of the message lands in each recipient's own pair thread with the sender. Recipients do not see each other, do not know who else received it, and never see each other's replies.
4.  A reply goes only to the other participant in that thread.
5.  Threads stay with the event: one planner on two events has two separate threads with that organizer.
6.  Threads are never merged. Changing the pair rule later (for example to topic threads) applies to new messages only.
7.  After a multi-recipient send there is no summary entry: each new or updated pair thread appears at the top of the sender's thread list (**Decision 4**).
8.  A planner participant is identified by the email assigned on the Planners tab, so a thread can exist before that planner has an account. When they create an account or log in with that email, the existing threads are theirs.

**Example:** the organizer selects Event Planner A and Event Planner B and sends "Block is up and running." Two separate threads now exist: Organizer-Planner A and Organizer-Planner B, each containing that message. Planner A and Planner B each get their own email. If Planner A replies, only the organizer sees it, in the Organizer-Planner A thread.

## endtoend-workflowsEnd-to-end workflows

Six workflows cover Phase 1. Each ends with the thread updated, the right people alerted, and nothing sent to anyone outside the pair.

### w1-organizer-sends-a-new-message-manageW1: Organizer sends a new message (Manage)

1.  Organizer opens the event and selects Messaging under Communications.
2.  Organizer selects New message and clicks into the To line. A list opens showing Select all planners at the top, then every event-level planner assigned to the event, including planners with no account yet, alphabetically by last name.
3.  Organizer selects one or more planners, or Select all. Each selection appears in the To line as a removable chip, and the list stays open for more selections.
4.  Organizer types the message and selects Send.
5.  System validates: at least one recipient, message not empty, within the length limit.
6.  System writes one copy into each Organizer-planner thread, creating individual threads where none exist. No group thread is created.
7.  System emails each recipient planner separately (Email section) and adds an unread alert in Planner Portal.
8.  Organizer lands on the thread list, where each recipient's thread appears at the top.

### w2-organizer-messages-a-planner-they-just-assigned-manageW2: Organizer messages a planner they just assigned (Manage)

1.  Manage user adds a planner's email on the event's Planners tab and assigns them to the event. The planner has no Planner Portal account and has never logged in.
2.  Manage user goes straight to Communications > Messaging on the same event, with no page refresh, new session or wait.
3.  The new planner is already in the To line list, shown by name if one was entered, otherwise by email.
4.  Manage user sends the message. The thread is created and the planner gets the notification email.
5.  If the planner replies from the email before having an account, the reply posts to the thread (W5).
6.  When the planner creates an account or first logs in with that email, the thread is in their Messages section with the message unread.

### w3-planner-sends-a-new-message-planner-portalW3: Planner sends a new message (Planner Portal)

1.  Planner opens the event and selects Messages.
2.  Planner selects New message and clicks into the To line. The list shows the organizer first, then other event-level planners on the event.
3.  Planner selects one or more recipients, types, and sends. The system validates as in W1, and each recipient gets an individual thread.
4.  For the organizer recipient: message lands in Organizer-planner, and an unread alert appears for organizer users in Manage. No email.
5.  For each planner recipient: message lands in that planner pair thread, an email goes out, and an unread alert appears in Planner Portal.

### w4-reply-in-app-either-sideW4: Reply in app (either side)

1.  User opens a thread from the thread list. Opening it marks its messages read (Unread section).
2.  User types a reply and selects Send.
3.  Reply appends to the thread; the other participant is alerted as in W1 or W3.

### w5-planner-replies-from-emailW5: Planner replies from email

1.  Planner receives the notification email and selects Reply in their email client.
2.  Planner writes and sends.
3.  System matches the reply to the thread by its reply-to address, checks the sender, removes quoted history and signature, and appends the text.
4.  The other participant is alerted. If the system cannot match or verify the reply, it sends the planner a short bounce notice with a link to Planner Portal, and the reply is not posted.

### w6-planner-opens-the-reply-link-in-the-emailW6: Planner opens the reply link in the email

1.  Planner selects the email's View and reply button.
2.  Logged in: Planner Portal opens the event's Messages section with that thread in focus.
3.  Logged out: the login screen opens, then after login the same thread opens.
4.  No account yet: the planner is taken through the existing Planner Portal account setup for that email, then lands on the same thread.
5.  No longer assigned to the event: an access message shows, and no event data is shown.

### compose-to-lineCompose To line

Who is listed in Manage

Who is listed in Planner Portal

The organizer first (Decision 2), then every other event-level planner on the event, alphabetically by last name. The planner viewing never sees themselves.

## email-notifications-and-reply-by-emailEmail notifications and reply by email

Only planners receive email, and only as the recipient: one email per new message in their thread, whether it came from the organizer or another planner. A planner who sends a message gets no email. Organizer users get in-app alerts only (**Decision 6**).

Rule

Requirement

Trigger

A new message lands in a thread where the planner is the recipient, including planners with no account yet. A planner never gets an email for their own message.

Multi-recipient sends

Each recipient gets their own email. No recipient's email shows or names the other recipients.

Frequency

One email per message, no batching in Phase 1. Revisit if planners report too many emails.

Content

The new message only, not the thread history; sender name and organization; event name; View and reply button

From name

Cvent Passkey Notifications

From and reply-to address

Production sends from msg.cvent-planner.com (staging: msg.cmanager.com), per Kelli Sippola in #passkey-messaging, May 2026. The reply-to address is unique to the thread. This replaces the [info@cvent.com](mailto:info@cvent.com) idea on the Project Phases page.

Subject

Event name plus sender, for example "New message from DF Meetings about Annual Sales Meeting 2027" (final wording with content team)

Template

New Cvent brand, localized, no HTML tables in the layout

Tracking

Delivered, opened, replied; pixel and click tracking switched off for accounts that disabled tracking

Reply by email

Posts to the matched thread after sender check; quoted history, signature and attachments removed; auto-replies and out-of-office messages are ignored

Reply that fails

Not posted; sender gets a bounce notice with a Planner Portal link

Bounce of the notification

Logged against the message for support; the message stays in the thread

CSN's message service ignores attachments on email replies and does not support rich text in email. Phase 1 matches that.

## unread-and-inapp-alertsUnread and in-app alerts

A planner's read state is their own. The organizer side shares one read state: once any organizer user opens a message, it is read for every organizer user on the account. Messages a user sends, from the app or by email reply, are never unread to them.

Rule

Requirement

What counts as unread

A message from another participant (another planner or the organizer side) that the reader's side has not opened

Own messages

Never unread to the sender, whether sent in the app or posted from an email reply

Planner side

Read state per planner. Messages sent before a planner has an account are unread when they first log in.

Organizer side

One shared read state across all organizer users on the event. When any organizer user opens the thread, its messages are read for all of them. Call center users do not change it.

Marked read

Opening the thread marks its messages read (for the planner, or for the whole organizer side) and clears the matching notifications

Mark unread

Makes the thread unread again for that side; sends no email and no alert

Above the event: Planner Portal

Green dot on the top-nav notifications icon when the planner has unread messages on any of their events. The fly-out Messages section lists each with event name, sender, date and time, and View message.

Above the event: Manage

The bell count is the sum of all unread notifications: unprocessed reservations, rooming lists, waitlist reservations and now unread messages. The notifications panel gets a new Messages section with its own unread message count, collapsed by default. Each entry is one thread with unread messages, showing event name, sender, and date and time of the latest unread message, plus "N unread messages" when the thread has more than one. Selecting an entry opens that thread in the event's Messages section, marks it read, removes the entry, and lowers both counts. While messages load, the section shows a spinner. If they fail to load, it shows "Notifications failed to load properly. Please try again." with a Try again action, matching the waitlist reservations section's pattern.

Inside an event: both apps

The Messages item in the event navigation shows an unread count for that event; unread threads in the list show a green dot plus a text label for screen readers

Counts

Above 99 show "99+"

Refresh

Counts and dots update without a full page reload. Engineering confirms the refresh method and interval.

**Decision 7 (decided):** shared read state on the organizer side. If one organizer user opens a reply meant for a colleague, the colleague gets no unread alert. Mark unread is the workaround in Phase 1.

## acceptance-criteriaAcceptance criteria

One story per heading, written to be lifted into Jira as is.

### ac1-messages-section-appears-on-the-eventAC1: Messages section appears on the event

-   Given a Manage user with access to an event, when they open the event, then Messaging appears under Communications in the event navigation.
-   Given an event-level planner, when they open an event they are assigned to in Planner Portal, then a Messages section is in the event navigation.
-   Given an SBG contact, when they open the event, then no Messages section shows.

### ac2-organizer-with-no-planner-assigned-s1AC2: Organizer with no planner assigned (S1)

-   Given an event with no event-level planner, when an organizer opens Messaging, then they see the value statement and an Add a planner button, and no compose box.
-   When they select Add a planner, then the add-planner flow opens for this event.
-   Given they add a planner and return to Messaging, then the S2 empty state shows with New message enabled, without a page refresh.
-   Given the user cannot add planners, then the button is replaced by text saying who can (Decision 5).

### ac3-empty-states-with-planners-s2-s3AC3: Empty states with planners (S2, S3)

-   Given planners exist but no threads, then the organizer sees S2 with New message as the main action.
-   Given a planner has no threads on the event, then they see S3 with New message as the main action.

### ac4-send-to-one-recipientAC4: Send to one recipient

-   Given no thread exists for the pair, when the sender sends, then a thread is created containing the message.
-   Given a thread exists for the pair, when the sender sends, then the message is appended to that thread and no new thread is created.
-   Then the thread appears at the top of the sender's thread list.

### ac5-multiselect-to-line-and-send-to-several-recipientsAC5: Multi-select To line and send to several recipients

-   Given an event has 2 event-level planners assigned, when an organizer selects New message and clicks into the To line, then Select all planners and both planners are listed, each planner with name and email, including a planner with no account yet.
-   When the organizer selects both, then both appear as chips in the To line, and the list stays open.
-   When the organizer selects Select all planners, then every planner on the event is selected and shown as a chip.
-   Given Select all is on, when the organizer unchecks one planner, then Select all unchecks and the other planners stay selected.
-   When the organizer selects x on a chip, then that planner is removed from the To line and unchecked in the list.
-   When the organizer types part of a name or email, then the list filters to matches and already-selected planners stay selected.
-   Given the organizer selects Planner A and Planner B and sends "Block is up and running.", then two separate individual threads exist, Organizer-Planner A and Organizer-Planner B, each with that message, and no group thread is created.
-   Then Planner A and Planner B each get their own notification email, and neither can see that the other received it.
-   Given Planner A replies, then the reply appears only in the Organizer-Planner A thread, and Planner B sees nothing.
-   Then both threads appear at the top of the sender's thread list, with no separate summary entry.
-   Given a planner in Planner Portal selects the organizer and 1 other planner, then one copy lands in each individual pair thread.
-   Given a keyboard-only user, then they can open the list, select and deselect recipients, use Select all, and remove chips without a mouse.

### ac6-compose-validationAC6: Compose validation

-   Given no recipient or an empty message, when Send is selected, then the send is blocked with a message naming the problem and typed text is kept.
-   Given the message exceeds the length limit, then the character count shows the excess and Send is blocked.
-   Given Send is selected twice quickly or a retry follows a timeout, then only one message is created per recipient.

### ac7-thread-list-and-thread-viewAC7: Thread list and thread view

-   Threads sort by latest message, newest first, with name, preview, date and time, and unread dot.
-   In the thread view, messages run oldest to newest, each with sender name, organization, date and time in the viewer's time zone.
-   Organizer users see messages sent by any organizer user on the event, each labeled with the person who sent it.

### ac8-email-to-plannerAC8: Email to planner

-   Given any message lands in a planner's thread from someone else, then one email is sent to that planner with only the new message, sender, event name and a View and reply button.
    -   Note this may be the first message that starts the thread as well
-   Given a planner sends a message, then that planner receives no email for it.
-   Given the account has tracking disabled, then the email carries no tracking pixel or tracked links.
-   Given an organizer user receives a message, then no email is sent to any organizer user.

### ac9-reply-linkAC9: Reply link

-   Given the planner is logged in, when they select View and reply, then the event's Messages section opens with that thread in focus.
-   Given they are logged out, then after login they land on that thread.
-   Given they have no account yet, then they go through the existing account setup for that email and then land on that thread.
-   Given they are no longer assigned to the event, then they see an access message and no event data.

### ac10-reply-by-emailAC10: Reply by email

-   Given a planner replies to the notification from the address it was sent to, then the reply text is appended to the thread with quoted history and signature removed, whether or not they have an account.
-   Given the reply is an auto-reply or out-of-office, then nothing is posted.
-   Given the reply contains attachments, then they are dropped and the text is posted.

### ac11-unread-and-mark-unreadAC11: Unread and mark unread

-   Given a new message from another participant, then the thread shows an unread dot with a text label for the recipient side.
-   Given a planner sends a message, in the app or by email reply, then it is not unread for that planner.
-   Given an organizer user sends a message, then it is not unread for any organizer user.
-   When a planner opens the thread, then its dot and matching notifications clear for that planner.
-   Given organizer user Megan opens an organizer thread, then it is read for every organizer user on the event, including Aspen.
-   When a user selects Mark unread, then the thread is unread again for their side, and no email or alert goes to anyone.

### ac12-topnav-alertsAC12: Top-nav alerts

-   Planner Portal, above the event: the notifications icon shows a green dot when the planner has unread messages on any of their events, and the fly-out lists each with event name, sender, date and time, and View message.
-   Manage bell: given a user has 4 unprocessed reservations, 1 rooming list, 2 waitlist reservations and 3 unread messages, then the bell shows 10.
-   Manage panel: the Messages section shows the unread message count in its header and is collapsed by default.
-   Manage panel: each entry is one thread with unread messages, showing event name, sender, and date and time of the latest unread message, plus "N unread messages" when the thread has more than one.
-   Manage panel: while messages load, the Messages section shows a spinner, and the other sections are not blocked.
-   Manage panel: given messages fail to load, then the section shows "Notifications failed to load properly. Please try again." with Try again, styled like the waitlist reservations error, and the bell count excludes messages until they load.
-   When a user selects a panel entry, then that thread opens in the event's Messages section with the latest unread message in focus, the thread is marked read for all organizer users, the entry disappears, and the section count and bell count drop by that thread's unread messages.
-   Inside an event, both apps: the Messages item in the event navigation shows that event's unread count, and it clears when no unread threads remain.
-   Counts over 99 show "99+".

### ac13-release-readiness-mobile-brand-accessibility-localizationAC13: Release readiness (mobile, brand, accessibility, localization)

-   Given a planner on a phone browser opens an event from its link or from the email, then they can view threads, compose, choose recipients, send and reply without horizontal scrolling or zooming.
-   Then every messaging screen and the notification email use the new Cvent brand.
-   Then every messaging screen passes a WCAG 2.1 AA check and works by keyboard alone.
-   Given the user's language is any of the 31 supported languages, then all messaging UI text, alerts and the email appear in that language, with dates and times in their locale.

### ac14-messages-are-obfuscated-with-the-eventAC14: Messages are obfuscated with the event

-   Given the customer's Passkey licensee flag has been unchecked for 90 days, when the obfuscation run processes it, then every message and thread on that customer's events is obfuscated in the same run.
-   Then message text, participant names and email addresses, reply-to addresses and email tracking data are no longer readable in Manage, Planner Portal, the message service or reports.
-   Given an email reply arrives for an obfuscated thread, then nothing is posted and the sender gets a bounce notice.
-   Given an event's messages fail to obfuscate, then the event's obfuscation status records the failure and the run retries it, following the existing pipeline's failure handling.

### ac15-call-center-usersAC15: Call center users

-   Given a call center user type opens an event, when they open Messages, then they see the thread list and threads, and no New message, reply box or Mark unread.
-   Given that user opens a thread with unread messages, then the messages stay unread for the other organizer users.
-   Then that user's bell count and notifications panel include no unread messages.
-   Given a call center user calls the send or reply API directly, then the request is rejected.

### ac16-participating-hotels-cannot-see-messagingAC16: Participating hotels cannot see messaging

-   Given a hotel user on a CW or MP event their hotel participates in but does not own, when they open the event in Manage, then no Messages section appears.
-   Then their bell count and notifications panel include no messages from that event.
-   Then they never appear in any recipient picker on that event.
-   Given they call the message APIs for that event directly, then the request is rejected and no message data is returned.
-   Given a hotel user on an HD event their hotel owns, then they have full organizer messaging.

### ac17-message-a-planner-as-soon-as-they-are-assignedAC17: Message a planner as soon as they are assigned

-   Given a Manage user assigns a planner's email to the event on the Planners tab, when they go straight to Communications > Messaging on that event, then that planner is in the To line list with no page refresh, new session or wait.
-   Given that planner has no Planner Portal account and has never logged in, when the Manage user sends a message, then the thread is created and the planner receives the notification email.
-   Given that planner replies from the email before creating an account, then the reply posts to the thread.
-   Given that planner later creates an account or logs in with the same email, then the thread is in their Messages section and messages they have not opened are unread.
-   Given the planner was assigned with an email only and no name, then the To line list, chip and thread show the email address.

## nonfunctional-requirementsNon-functional requirements

Targets marked (confirm) need Cvent standards or engineering input.

Category

Requirement

Brand

The Messages section, compose, thread views, both fly-outs and the notification email ship on the new Cvent brand at release. No messaging screen or email goes live on the old brand.

Mobile

The full workflow works on a phone browser: open an event from its links, view the thread list, open a thread, compose, choose recipients, send and reply. The same applies when arriving from the email's View and reply link. Layout reflows to a single column at Planner Portal's supported mobile widths, with no horizontal scrolling and touch targets of at least 44 px (confirm). The email renders in Outlook, Gmail and Apple Mail on desktop and mobile, including dark mode. Manage on mobile follows Manage's current mobile support (confirm).

Accessibility

WCAG 2.1 AA (confirm). Compose, the To line, thread list, thread view and both fly-outs work by keyboard alone, with focus moving into and back out of the fly-out. Unread state is never shown by colour alone. New messages and count changes are announced to screen readers. The email uses semantic markup and stays readable with images off.

Localization

All UI strings, notification and alert text, and the email template are translated into all 31 supported languages at release. Dates and times follow the viewer's locale and time zone. Layouts allow for longer translated text (confirm whether any supported language is right-to-left). Message text written by users is not translated. A missing translation falls back to English (confirm).

Security

Every read and write checks the user's access to the event and thread, so changing an ID in a request returns nothing. Every recipient in a send is checked against the event's current planners on the server. Message text is sanitized in the app and the email. Email replies are verified against the expected sender. Sending is rate limited (limit to confirm).

Privacy and obfuscation

Messages follow the same obfuscation policy and process as all other event data: they are obfuscated in the same run as the rest of the customer's event data, 90 days after the customer's Passkey licensee flag is unchecked. See [Event Level Requirements for Obfuscation for CDR Phase 2](https://wiki.cvent.com/spaces/PASKY/pages/1154127959/Event+Level+Requirements+for+Obfuscation+for+CDR+Phase+2), [Passkey CDR Architecture Design](https://wiki.cvent.com/spaces/PASKY/pages/1015739441/Passkey+CDR+Architecture+Design) and [Passkey Data Obfuscation and Retention Timeline - CDR Initiative](https://wiki.cvent.com/spaces/PASKY/pages/860128917/Passkey+Data+Obfuscation+and+Retention+Timeline+-+CDR+Initiative). In scope: message text, sender and recipient names and email addresses, thread reply-to addresses, and email tracking data. Messages are stored in the CSN message service, not Passkey's database, so the obfuscation pipeline must call that service; this is new work. Multi-recipient sends never expose one recipient's name or email to another. The rule for card numbers and personal data typed into messages is still open (Decision 8).

Performance

Thread list loads in under 2 s for an event with 100 threads; the To line list opens in under 1 s for an event with 100 planners; a Select all send to 100 planners creates every thread and queues every email within 1 minute; a sent message appears in the recipient's thread within 5 s; a newly assigned planner is in the To line as soon as the Planners tab save completes (all confirm).

Reliability

If the message service is down, compose shows an error and keeps the text and selected recipients; email sends retry on failure.

Analytics

Events for message sent (by side, app, device type and number of recipients), Select all used, thread created, email delivered, opened and replied, alert clicked, and S1 Add a planner clicked.

Rollout

Messaging sits behind a feature flag that can be switched on per account.
