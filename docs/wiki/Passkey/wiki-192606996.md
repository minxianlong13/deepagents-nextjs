The latest pass at a branching strategy for Passkey Development has an emphasis on simplicity.  We should be able to flexibly manoeuvre around anomalous or unorthodox merging/branching scenarios as they pop up, but these accommodations should not disrupt simplicity for the other 95% of use cases.  
  
Branching simplicity, though, is contingent on a systematic and disciplined workflow.  We must abide by certain rules when creating and merging branches or we will pay a heavy price when the tech debt gets called in.

This document intends to outline two branching strategies - one for our monolithic products, and another for our microarchitecture products.  The basic workflows for each are visualized and , but it is strongly encouraged that you read this document to understand the rules about what we ought and ought not do during feature development (as to branching).

## Concepts

### Why Two Branch Strategies?

This document describes two somewhat different branching strategies - one for our monolithic applications and another for our microservice applications.  
  
They are different primarily due to the impacts that form factor has on our release cycle.  Passkey is a very large application that is deployed all-at-once with many updates and code changes in a single release, and so necessarily requires a bit of additional branching complexity in order to compile production quality changes in a trusted, testable branch without blocking the regular development workflow for the entire application.  
  
Microservices are far smaller and do not carry the weight of massive changes from release to release. Periods of code stability for the purpose of producing testable branches are abundant, and release-related hang ups with a single microservice would not typically block development in other microservices.  For these reasons, the branching strategy can be simplified for general development, and adjusted on a case-by-case basis to accommodate anomalous release scenarios.

### Trusted Branches vs Untrusted Branches

A _trusted_ branch is just a branch that contains only certified features and bugfixes.  In the basic workflow, the _master_, _releaseitems_ and _release_ branches are trusted branches.  In the _epic_ workflow, we can add epic branches to that list.  
  
_Feature_ branches containing not-yet-certified code changes along with the _qai_ and _ci_ branches (of the Monolith Passkey and Microservice workflows, respectively) generally house uncertified and partially-developed code, so those branches are _untrusted_ branches.  
  
The key take-away concept here is that when creating code solutions for our product, it is important in our branching and release strategies to prevent untrusted code from infiltrating our trusted codebase. We accomplish this through the process of _certification_. 

### Certification

The process whereby untrusted code isolated in a particular feature branch becomes trusted through various reviews, as well as the disciplines of _unit_, _feature_ and _integration_ testing.  A feature branch - considered untrusted during development - officially becomes trusted when it has passed certification.  Certification occurs in the _qai_ branch for monolithic passkey projects, while for microservice-related projects, the _ci_ branch serves this purpose.

### Production Quality Features

A _production quality_ feature is the definition of a story or work item (JIRA ticket) whose implementation is a self-contained unit of tested, certifiable work that can be deployed as-is in the next release in its certified state.  ALL features should be production quality, whenever possible, _even_ when they represent only small piece of some larger unimplemented feature (See the Epic Workflow section below).

### Intermediary Release

This is an unofficial release that is sometimes used to satisfy internal dependencies and un-block development workflow.  Intermediary releases go through the same dev cycle as ordinary releases, but they are not release tested and they are not released to production. For example, an intermediary release can be useful for certifying and pre-publishing API interfaces in order to make them available to dependencies (e.g. another microservice) _before_ feature implementation is complete without imposing a release testing cycle.

# Passkey Monolithic Branch Workflow

## Highlights

The basic monolithic workflow begins in the master branch, the authoritative branch that always represents the most recent release-stabilized state of a project codebase.

-   All _feature_ branches must be based off of either the project's _master_ branch () or an _epic_ branch ().
-   Code reviews are completed during a pull request of the _feature_ branch to the _qai_ branch.
-   Upon certification, feature branches should be merged into RELEASEITEMS.

## Da Rules...

### ...as to creating _feature_ branches

-   DO create _feature_ branches based off of _master_ or another _epic_ branch.
-   DO NOT create _feature_ branches from _qai_, _releaseitems_, or any _release_ branch.

### ...as to feature _pull_ requests

-   DO create a pull request from your feature branch targeted to QAI so that it can be peer reviewed.
-   DO NOT directly merge your feature branch anywhere else until it has been certified (with the exception of reconciling dependencies - see below).
-   DO pull request the contents of your feature branch into the RELEASEITEMS branch following certification.

### ...as to reconciling dependencies with other DONE features

-   DO merge the _feature_ branch corresponding to the DONE feature into your working _feature_ branch.

### ...as to reconciling dependencies with other in progress features

-   DO communicate to the author of the opposing feature the nature of the dependency
-   Between the two of you, select the appropriate course of action:
    -   If the dependency between the two features is a shallow, interface-level dependency:
        -   DO isolate the work that represents the intersection of the two features (e.g. interface or object model) into a separate _feature_ branch/Jira ticket pair.
        -   DO submit the changes in the new branch as a PR to QAI as per normal.
        -   DO undergo an expedited certification process (that tests only the specification of the integration - NOT the implementation).
        -   Following certification, merge the certified feature from its branch into the two original _feature_ branches that required it.
    -   If the dependency runs deeper than in interface-level integration OR if time does not permit the above workflow:
        -   DO consider the two tickets a single story.
        -   DO merge the contents of the two branches into one or the other _feature_ branch
        -   DO delete the abandoned branch.
        -   DO co-author your respective features in the remaining _feature_ branch.

While inter-feature dependencies happen occasionally and cannot be entirely helped, these types of dependencies often happen because of improper sequencing or poorly defined feature boundaries.  Feature intersections need to be identified at sprint planning and implemented ahead of time.  If we find ourselves consistently reconciling dependencies with other feature branches, we may need to revisit our sprint planning and/or grooming habits.

### ...as to resolving conflicts with QAI

-   DO NOT merge your feature branch with QAI.  These branches have untested and/or obsolete code that must not be inadvertently released.
-   DO NOT create a _merge/GROUP-<XXXXX>_ branch _unless as a last resort_.  This will replicate the conflict at release time and create an error-prone, risky condition.
-   DO find the feature branch(es) that are determined to be the source of the conflict (Using Stash's \`blame\` feature in the QAI branch should tell you this).
-   DO treat the conflict as a dependency, using the appropriate 'reconciling dependencies' steps above to merge the offending feature into your branch and resolve the conflict _in situ_.

# Epic Workflow

## Highlights

The intent of the epic workflow is to produce a central hub for development of a particularly large feature that can be broken into smaller pieces and developed concurrently across multiple developers.  This is additional process overhead that actually brings about simplicity during the merging phase of these types of features - PROVIDED the epic workflow rules are followed.  
  
Epic workflows are supported by both the monolithic and microarchitecture branching strategies.  Epic branches are 'living' branches and **must** be managed and communicated regularly until the entire epic has been delivered.  _The simple, isolated act of creating an epic branch does not solve conflict problems on its own_.  Read the following rules below carefully, and make sure you manage your epic branches accordingly (or suffer the consequences of painful and complex file/file system conflicts).

Note that there is no strategy to completely remove conflicts from the picture.  What we CAN do is reduce their frequency and scope, as well as ensure that we do not duplicate conflict resolution effort (increasing opportunity for human error) as features move downstream.

## Da Rules...

### ...as to creating _epic_ branches

-   DO create e_pic_ branches (\`epic/GROUP<XXXXX>\`) based from m_aster_ OR from another _epic_ or _feature_ branch whose contents are already certified (trusted).
-   DO NOT create _epic_ branches based off of _ci_, _qai_, _releaseitems_ or _release_.

### ...as to creating epic _feature_ branches

-   DO create _feature_ branches (\`feature/GROUP-<XXXXX>\`) for new development related to the epic.  If the epic requires new code that does not have a related ticket, create the ticket and then create the _feature_ branch.
-   DO NOT develop or commit new code directly in an _epic_ branch.

### ...as to synchronizing _epic_ branches to master

-   DO keep your epic branch synchronized with the head of the _master_ branch via periodic, post-release \`git pull origin master\` commands from the _epic_ branch root.
-   DO resolve conflicts between _master_ and your epic directly in the epic branch. Conflict resolution is not 'new code', so conflict-related changes are acceptable.
-   DO notify your team when you have refreshed the _epic_ branch to the head of _master_.
-   DO NOT let your epic branch fall behind master.  Failure in this capacity will cause conflicts with unrelated newly-released items, and propagate those conflicts to all epic child feature branches.
-   DO NOT make changes to the _epic_ branch without notifying the affected team members. Communication of epic changes is paramount to conflict avoidance.

### ...as to synchronizing _epic_ branches to child features

-   DO keep e_pic_ branches synchronized with **certified** features from _feature_ branches that were spun off of it:
    -   Following feature certification, execute a \`git merge feature/GROUP-<XXXXX>\` command from the epic root (the merge destination), specifying the child feature branch containing the change (the merge target).
    -   EMAIL or SLACK your team to inform them of the change to the epic branch.
-   **DO NOT sync the _epic_ branch with un-certified changes**.  If a sibling _feature_ branch requires a change from your branch in order to proceed:
    -   Isolate the change that they require into a discrete pull request (and associated Jira work item).  Pull request should contain ONLY what is required (interface, type class, etc).
    -   Allow that item to proceed through regular testing (expedited, since it has been isolated). 
    -   Make note of the sequencing problem that resulted in this urgency/blockage so that it can be avoided in the future.
    -   Did I forget to mention: DO NOT check un-certified changes into epic branches?

### ...as to synchronizing child _feature_ branches with the _epic_ branch

-   DO keep _feature_ branches that were created from an epic branch synchronized with the epic branch. When a fellow epic developer merges their feature changes back to the epic (and subsequently notifies you), you must synchronize your branch to the head of the epic with \`git pull origin epic/GROUP-<XXXXX>\`.
-   DO NOT let feature branches fall out of sync with the head of the epic branch.

### ...as to merging epic and child feature contents to downstream branches

-   DO pull requests to ci and qai from feature branches ONLY.
-   DO NOT initiate pull requests from an _epic_ branch that contains uncertified changes
-   DO NOT initiate pull requests from an epic branch that is not synchronized with the head of _master_.

  

**Q: Why can't I push uncertified feature changes down to the epic branch?**  
A: Before answering this, it is important to note that the urgent situations in which we are tempted to push untested changes in our feature branches back down to their corresponding epic branch are symptoms of bad sprint work allocation.  Generally this problem manifests as either a sequencing issue, or because of overly-broad, poorly-decoupled tickets that lump interfacing and implementation into the same work item.  We can avoid these situations by being careful during sprint planning not to create co-dependencies (two tickets that need each other), and by making sure that units of work representing one-way dependencies are assigned _sequentially_ (NOT concurrently).  
  
The answer to the initial question is that uncertified changes committed directly to an epic spoils the epic for downstream merging purposes.  Epic branches that are synced with master and contain only **certified**, **reconciled** and **production**\-quality changes are especially useful during release creation as they contain tested conflict reconciliations that do not need to be re-engineered a second time for another downstream branch, AND because they offer natural feature correlation that reduces the amount of error-prone work that the release lead must do in order to compile release features.  
  
Epic branches that contain uncertified changes, are not synced with their own features or are not synced with master are useless for release prepping purposes.  While epic issues related to syncing can be dealt with case-by-case by release leads, issues related to untested code cannot, and so the branch is spoiled.

## Experimental Framework and Production Quality Features

Being able to count on our feature branches to always contain deliverable content is an important assumption when delivering epics.  Epics that do not merge into release branches and continue to accumulate changes over long periods of time cause conflict nightmares and incompatibilities that can affect an entire project across releases.  To prevent this, we need to make sure that the state of an epic is always deliverable such that when the time comes for a new release, the certified contents of an epic-in-progress can still be applied to the release _event though the feature is incomplete_.

Except in severe cases, the experimental framework allows us to protect incomplete features at run time from being used while in an incomplete or inappropriate state.  While these features may not be available by users, the released codebase still contains certified portions of new code that have endured successful feature, integration and release testing.  
  
By allowing epics to churn through the development workflow in partially-complete states, it allows them to reconcile with other ongoing changes to the codebase without creating huge gaps in file versions (read: conflicts!).  
  
Ergo, please plan accordingly, and attempt to provide individual story/feature solutions in a deliverable manner - even if they're just pieces of an epic.
