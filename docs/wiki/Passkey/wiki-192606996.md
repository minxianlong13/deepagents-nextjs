one for our monolithic applications and another for our microservice applications.<br /><br />They are different primarily due to the impacts that form factor has on our release cycle.  Passkey is a very large application that is deployed all-at-once with many updates and code changes in a single release, and so necessarily requires a bit of additional branching complexity in order to compile production quality changes in a trusted, testable branch without blocking the regular development workflow for the entire application.<br /><br />Microservices are far smaller and do not carry the weight of massive changes from release to release. Periods of code stability for the purpose of producing testable branches are abundant, and release-related hang ups with a single microservice would not typically block development in other microservices.  For these reasons, the branching strategy can be simplified for general development, and adjusted on a case-by-case basis to accommodate anomalous release scenarios.</p><h3>Trusted Branches vs Untrusted Branches</h3><p>A <em>trusted</em> branch is just a branch that contains only certified features and bugfixes.  In the basic workflow, the <em>master</em>, <em>releaseitems</em> and <em>release</em> branches are trusted branches.  In the <em>epic</em> workflow, we can add epic branches to that list.<br /><br /><em>Feature</em> branches containing not-yet-certified code changes along with the <em>qai</em> and <em>ci</em> branches (of the Monolith Passkey and Microservice workflows, respectively) generally house uncertified and partially-developed code, so those branches are <em>untrusted</em> branches.<br /><br />The key take-away concept here is that when creating code solutions for our product, it is important in our branching and release strategies to prevent untrusted code from infiltrating our trusted codebase. We accomplish this through the process of <em>certification</em>. </p><h3>Certification</h3><p>The process whereby untrusted code isolated in a particular feature branch becomes trusted through various reviews, as well as the disciplines of <em>unit</em>, <em>feature</em> and <em>integration</em> testing.  A feature branch - considered untrusted during development - officially becomes trusted when it has passed certification.  Certification occurs in the <em>qai</em> branch for monolithic passkey projects, while for microservice-related projects, the <em>ci</em> branch serves this purpose.</p><h3>Production Quality Features</h3><p>A <em>production quality</em> feature is the definition of a story or work item (JIRA ticket) whose implementation is a self-contained unit of tested, certifiable work that can be deployed as-is in the next release in its certified state.  ALL features should be production quality, whenever possible, <em>even</em> when they represent only small piece of some larger unimplemented feature (See the Epic Workflow section below).</p><h3>Intermediary Release</h3><p>This is an unofficial release that is sometimes used to satisfy internal dependencies and un-block development workflow.  Intermediary releases go through the same dev cycle as ordinary releases, but they are not release tested and they are not released to production. For example, an intermediary release can be useful for certifying and pre-publishing API interfaces in order to make them available to dependencies (e.g. another microservice) <em>before</em> feature implementation is complete without imposing a release testing cycle.</p><h1>Passkey Monolithic Branch Workflow</h1><h2>Highlights</h2><p>The basic monolithic workflow begins in the master branch, the Workflow</h1><h2>Highlights</h2><p>The intent of the epic workflow is to produce a central hub for development of a particularly large feature that can be broken into smaller pieces and developed concurrently across multiple developers.  This is additional process overhead that actually brings about simplicity during the merging phase of these types of features - PROVIDED the epic workflow rules are followed.<br /><br />Epic workflows are supported by both the monolithic and microarchitecture branching strategies.  Epic branches are 'living' branches and <strong>must</strong> be managed and communicated regularly until the entire epic has been delivered.  <em>The simple, isolated act of creating an epic branch does not solve conflict problems on its own</em>.  Read the following rules below carefully, and make sure you manage your epic branches accordingly (or suffer the consequences of painful and complex file/file system conflicts).</p><p>Note that there is no strategy to completely remove conflicts from the picture.  What we CAN do is reduce their frequency and scope, as well as ensure that we do not duplicate conflict resolution effort (increasing opportunity for human error) as features move downstream.</p><h2>Da Rules...</h2><h3>...as to creating <em>epic</em> branches</h3><ul><li>DO create e<em>pic</em> branches (`epic/GROUP&lt;XXXXX&gt;`) based from m<em>aster</em> OR from another <em>epic</em> or <em>feature</em> branch whose contents are already certified (trusted).</li><li>DO NOT create <em>epic</em> branches based off of <em>ci</em>, <em>qai</em>, <em>releaseitems</em> or <em>release</em>.</li></ul><h3>...as to creating epic <em>feature</em> branches</h3><ul><li>DO create <em>feature</em> branches (`feature/GROUP-&lt;XXXXX&gt;`) for new development related to the epic.  If the epic requires new code that does not have a related ticket, create the ticket and then create the <em>feature</em> branch.</li><li>DO NOT develop or commit new code directly in an <em>epic</em> branch.</li></ul><h3>...as to synchronizing <em>epic</em> branches to master</h3><ul><li>DO keep your epic branch synchronized with the head of the <em>master</em> branch via periodic, post-release `git pull origin master` commands from the <em>epic</em> branch root.</li><li>DO resolve conflicts between <em>master</em> and your epic directly in the epic branch. Conflict resolution is not 'new code', so conflict-related changes are acceptable.</li><li>DO notify your team when you have refreshed the <em>epic</em> branch to the head of <em>master</em>.</li><li>DO NOT let your epic branch fall behind master.  Failure in this capacity will cause conflicts with unrelated newly-released items, and propagate those conflicts to all epic child feature branches.</li><li>DO NOT make changes to the <em>epic</em> branch without notifying the affected team members. Communication of epic changes is paramount to conflict avoidance.</li></ul><h3>...as to synchronizing <em>epic</em> branches to child features</h3><ul><li>DO keep e<em>pic</em> branches synchronized with <u><strong>certified</strong></u> features from <em>feature</em> branches that were spun off of it:<ul><li>Following feature certification, execute a `git merge feature/GROUP-&lt;XXXXX&gt;` command from the epic root (the merge destination), specifying the child feature branch containing the change (the merge target).</li><li>EMAIL or SLACK your team to inform them of the change to the epic branch.</li></ul></li><li><strong>DO NOT sync the <em>epic</em> branch with un-certified changes</strong>.  If a sibling <em>feature</em> branch requires a change from your branch in order to proceed:<ul><li>Isolate the change that they require into a discrete pull request (and associated Jira work item).  Pull request should contain ONLY what is required (interface, type class, etc).</li><li>Allow that item to proceed through regular testing (expedited, since it has been isolated). </li><li>Make note of the sequencing problem that resulted in this urgency/blockage so that it can be avoided in the future.</li><li>Did I forget to mention: DO NOT check un-certified changes into epic branches?</li></ul></li></ul><h3>...as to synchronizing child <em>feature</em> branches with the <em>epic</em> branch</h3><ul><li>DO keep <em>feature</em> branches that were created from an epic branch synchronized with the epic branch. When a fellow epic developer merges their feature changes back to the epic (and subsequently notifies you), you must synchronize your branch to the head of the epic with `git pull origin epic/GROUP-&lt;XXXXX&gt;`.</li><li>DO NOT let feature branches fall out of sync with the head of the epic branch.</li></ul><h3>...as to merging epic and child feature contents to downstream branches</h3><ul><li>DO pull requests to ci and qai from feature branches ONLY.</li><li>DO NOT initiate pull requests from an <em>epic</em> branch that contains uncertified changes</li><li>DO NOT initiate pull requests from an epic branch that is not synchronized with the head of <em>master</em>.</li></ul><p><br /></p><p><strong>Q: Why can't I push uncertified feature changes down to the epic branch?</strong><br />A: Before answering this, it is important to note that the urgent situations in which we are tempted to push untested changes in our feature branches back down to their corresponding epic branch are symptoms of bad sprint work allocation.  Generally this problem manifests as either a sequencing issue, or because of overly-broad, poorly-decoupled tickets that lump interfacing and implementation into the same work item.  We can avoid these situations by being careful during sprint planning not to create co-dependencies (two tickets that need each other), and by making sure that units of work representing one-way dependencies are assigned <em>sequentially</em> (NOT concurrently).<br /><br />The answer to the initial question is that uncertified changes committed directly to an epic spoils the epic for downstream merging purposes.  Epic branches that are synced with master and contain only <strong>certified</strong>, <strong>reconciled</strong> and <strong>production</strong>-quality changes are especially useful during release creation as they contain tested conflict reconciliations that do not need to be re-engineered a second time for another downstream branch, AND because they offer natural feature correlation that reduces the amount of error-prone work that the release lead must do in order to compile release features.<br /><br />Epic branches that contain uncertified changes, are not synced with their own features or are not synced with master are useless for release prepping purposes.  While epic issues related to syncing can be dealt with case-by-case by release leads, issues related to untested code cannot, and so the branch is spoiled.</p><h2>Epic Workflow (Monolith &amp; Microservices)</h2><p><ac:image Production Quality Features</h2><p>Being able to count on our feature branches to always contain deliverable content is an important assumption when delivering epics.  Epics that do not merge into release branches and continue to accumulate changes over long periods of time cause conflict nightmares and incompatibilities that can affect an entire project across releases.  To prevent this, we need to make sure that the state of an epic is always deliverable such that when the time comes for a new release, the certified contents of an epic-in-progress can still be applied to the release <em>event though the feature is incomplete</em>.</p><p>Except in severe cases, the experimental framework allows us to protect incomplete features at run time from being used while in an incomplete or inappropriate state.  While these features may not be available by users, the released codebase still contains certified portions of new code that have endured successful feature, integration and release testing.<br /><br />By allowing epics to churn through the development workflow in partially-complete states, it allows them to reconcile with other ongoing changes to the codebase without creating huge gaps in file versions (read: conflicts!).<br /><br />Ergo, please plan accordingly, and attempt to provide individual story/feature solutions in a deliverable manner - even if they're just pieces of an epic.</p>
