<p><strong>Epic</strong> <ac:structured-macro ac:name="jira" ac:schema-version="1" ac:macro-id="b4ec5b2d-eabd-4a9b-929d-1951ccb9af54"><ac:parameter ac:name="server">Cvent JIRA</ac:parameter><ac:parameter ac:name="serverId">d1d78885-1a8e-3259-b68d-3df198ee3d46</ac:parameter><ac:parameter ac:name="key">GROUP-76220</ac:parameter></ac:structured-macro></p><p><ac:structured-macro ac:name="toc" ac:schema-version="1" ac:macro-id="9d1597f4-bebc-4bc9-b79e-6f08cae515d6" /></p><h2>Skeleton Loaders</h2><p>Skeleton loaders, also referred to as placeholder containers, are components that visually communicate to the user that content is loading without breaking the websites layout and architecture.</p><ul><li><strong>For users</strong>, skeleton loaders visually communicate to users that website content is loading, replacing the visually jarring experience of not having any loading indicators.</li><li><strong>For developers and businesses</strong>, skeleton loaders provide a modern look and flow to website loading.</li></ul><h2>Benefits</h2><ul><li>Wait times are almost always unavoidable, so rendering components that mimic the look and structure of loaded data will provide users with a better, less-jarring user experience</li><li>Allows content to load without breaking the structure of the website. </li><li>Users know what to expect once website content is loaded</li></ul><h2>Why not just use a spinner (or any other kind of loading visual cue)?</h2><p>Spinners are cool and are an important visual cue for UX. However, for our specific case, which is the Autoblock Requester site, I think loading skeletons would provide a better user experience. This is due to the fact that we are working with a website/product with a clear <strong>structure.</strong> One of the main benefits of loading skeletons is that they mimic the exact structure that will be present once data is loaded, so users have an idea of what to expect. Spinners are great for representing buffering in videos, images, or loading screens in video games. Essentially, they are great for unstructured UI's. But, <ac:inline-comment-marker ac:ref="657117c9-817b-4225-b13f-bafb51486293">for Autoblock-UI,</ac:inline-comment-marker> having a loading flow with a spinner would plunge the user straight into the website content once data is loaded, which can be a bit jarring.</p><h2>Which Components could benefit from Skeleton Loaders?</h2><h4>HotelItem.js</h4><p><ac:image ac:height="250"><ri:attachment ri:userkey="2c9562af5f041176015f73c154940087" /></ac:link>, we realized that in order to keep performance costs as low as possible, it might be best implement skeleton-loaders at the page level, not the individual component level. Meaning, we should create a component that will render about 5-8 &lt;HotelItemSkeletonLoader/&gt;, instead of rendering one &lt;HotelItemSkeletonLoader/&gt; per incoming HotelItem. Otherwise, we could bump into a situation where we decrease perfomance due to the amount of components we are rendering.</p><h3>Overhead</h3><p>In order to reduce developer overhead, we could create a &quot;Mother Skeleton Loader&quot;. This component would have a &quot;type&quot; property that would define what kind of skeleton card we need. For example, we already have an implementation for a HotelItem skeleton loader card. We could pass in the value &quot;HOTEL_ITEM&quot; to our Mother Skeleton Loader, and it would return a &lt;HotelItemSkeletonLoader/&gt;. Since we will only have about 3 or 4 components that will bene fit from skeleton loaders, then we could implement these 3 or 4 designs once and not have to implement them again.</p><h2>Design href="https://www.npmjs.com/package/react-loading-skeleton">https://www.npmjs.com/package/react-loading-skeleton</a></p><p><strong>Github</strong> <strong>repo</strong>: <a href="https://github.com/dvtng/react-loading-skeleton">https://github.com/dvtng/react-loading-skeleton</a></p><p><strong>Latest issue submitted</strong>: November 15, 2021</p><p>From my experience, this library was the most complete of the two I compared. Currently, support is very consistent, having recieved 58 issues, and closing all of them. Issues tend to receive a eply back the same day, and are fixed one or two days after the issue was submitted. There were lots of issues before October 21 2021. However, since the release of version 3.0.1. on the same day, there has <ac:inline-comment-marker ac:ref="c2ff77ac-fee7-4323-a052-065fadfac953">only been one issue, which was caused by a user's incorrect implementation of thelibrary rather than a bug in the library itself, and</ac:inline-comment-marker> seems to suggest that many issues were resolved in version 3.0.1. Overall, the library seems to be consistently well-taken care of and should be <ac:inline-comment-marker ac:ref="20854170-1c7f-4ffe-8af0-bbb9f168d4ac">a good option</ac:inline-comment-marker> to use for our purposes.</p><p><strong>Known possible roadbumps when implementing: </strong>Skeleton components do not have an innate width predetermined. This can cause issues when using skeletons that are wrapped in flex boxes. The are two workarounds for this which are outlined in the issue itself: </p><ol><li>Give the<span> </span><code>Skeleton</code><span> </span>a width using the<span> </span><code>width</code><span> </span>prop.</li><li>Set the<span> </span><code>containerClassName</code><span> </span>prop and then add the CSS rule<span> </span><code>flex-grow: 1</code><span> </span>to the container.</li></ol><p>Issue link: <a href="https://github.com/dvtng/react-loading-skeleton/issues/122">https://github.com/dvtng/react-loading-skeleton/issues/122</a></p><h3>react-placeholder</h3><p><strong>Docs</strong>: <a href="https://buildo.github.io/react-placeholder/#!/ReactPlaceholder">https://buildo.github.io/react-placeholder/#!/ReactPlaceholder</a></p><p><strong>Github</strong> <strong>repo</strong>: <a href="https://github.com/buildo/react-placeholder">https://github.com/buildo/react-placeholder</a> </p><p><strong>Latest issue submitted</strong>: February 5, 2021</p><p>This library has many useful features, like the delay prop, which can be used to define a set delay time between showing the skeleton-loaders and the loaded content, as well as the ability to pass in your own custom placeholder card. However, the library is not as consistently maintained as react-skeleton-loader. The last few opened issues were all submitted in 2020, and their latest release is almost a year old. For these reason, I think it would be more comfortable to use a library like react-skeleton-loader, since it has all the features we need to build custom skeleton loaders without much overhead.</p><h2>Implementation</h2><p>For our purposes, we can use the following implementation to create skeleton cards for our HotelItem cards.
