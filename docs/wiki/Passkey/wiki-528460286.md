re-use.</li></ul></li><li><a href="https://www.apollographql.com/docs/react/api/link/apollo-link-batch-http/">Apollo <strong>BatchHttpLink</strong></a> is very neat, but it does not solve performance Singleton?</ac:parameter><ac:rich-text-body><ul><li>In this context, A <em>singleton</em> is a collection of cache policies specified in your Apollo client init configuration: <a href="https://www.apollographql.com/docs/react/caching/cache-configuration/#initialization">https://www.apollographql.com/docs/react/caching/cache-configuration/#initialization</a></li><li>The <strong>Query</strong> singleton specifies query level cache settings<ul><li>Queries can be referenced by name in the Query singleton in order to provide query-specific cache settings.</li></ul></li><li>All other singletons represent a collection of policies for a specific Normalized object type (and its fields)<ul><li>The singleton name is equivalent to the value of the '_typename' field of the object.</li><li>Enumerated object fields can have their own cache policies.</li></ul></li><li>The Apollo Client cache is configured via a working set of Singleton type policies.</li></ul></ac:rich-text-body></ac:structured-macro><p><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="11ec9da9-22ff-40d4-8d48-3a73a09f21d1"><ac:parameter ac:name="title">Cache Concepts: Normalized vs Query</ac:parameter><ac:rich-text-body><ul><li>The <em>query cache</em> is configured by the <strong>Query</strong> singleton and contains string → string key/value pairs where:<ul><li>The key consists of the name of the invoked query along with the variable values that were provided to the invocation.</li><li>The value is the entire query response.</li><li>A cache hit on a query cache entry only occurs when that same operation is again executed <em>with the same parameter values</em>.</li></ul></li><li>The <em>normalized</em> cache is the 'smart' part of apollo client caching: <br /><ul><li>JSON objects in a query response that contain a '_typename' field along with an 'id' (or '_id') field are <em>independently cacheable</em> using their typename and id field values as a composite lookup key.</li><li>Objects in a response that can be normalized are added to the normalized object cache, and replaced in the cached query result with a reference to the normalized object.  If that object already existed in the cache, than a reference to that object is used instead.</li><li>In that way, 2 different query invocations that return <em>partially</em> the same data will 'share' their results in the same normalized map.<ul><li>Eliminates cache redundancy (one cached object instead of two)</li><li>Improves cache reusability (future queries can be redirected to the normalized cache to check for matches in there).</li></ul></li></ul></li></ul></ac:rich-text-body></ac:structured-macro><p><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="2dbf3639-f6a4-4339-8adb-03acf90c8694"><ac:parameter ac:name="title">Normalize your Apollo Client Cache.</ac:parameter><ac:rich-text-body><ul><li>Reduces the memory footprint of your application cache in the user's browser</li><li>Increases the re-usability and relevance of cached objects (cache 'hits').</li><li>See <ac:link ac:anchor="Normalization"><ri:page ri:space-key="PASKY" ri:content-title="On The Outside Looking In: An excogitative look at GraphQL-based UIs" that contain objects with a '_typename' field, as well as a field called &quot;id&quot; or &quot;_id&quot; will be cached automatically.</li><li>For all others, update your ApolloProvider's <a href="https://www.apollographql.com/docs/react/caching/cache-configuration/">cache key configuration</a> to map object types with a custom-enumerated unique field or field consider the following.</p><p><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="9be24909-0dbe-4e43-9dde-8b04cab3c4be"><ac:parameter ac:name="title">Your Application's new or proposed Apollo Server Integration should have specific and material design and/or roadmap objectives.</ac:parameter><ac:rich-text-body><ul><li>What will be the purpose of the integration?  During design, consider the functional role of Apollo in your system.</li><li>GraphQL's query flexibility and data unity are big wins - <em>if</em> your use-cases leverage them!<ul><li>Are your application's data needs rigid? Do your clients request the same data in the same form factor over and over again?</li><li>If you do not plan to organize or prepare your data to be used in multiple, flexible ways, then GraphQl will only ever be merely an extraneous, expensive proxy for you (and a nuisance).</li></ul></li><li>The point is, the justification for an Apollo integration is not a built-in slam-dunk.  You will justify the decision by tracing real value to it, and this will most likely come in the form of use cases that require flexible, multi-present and diverse schemas.  If you don't have actual winning use cases in your project that do that, you may be in for some difficult retrospectives should the integration project not go as smoothly as you hoped.</li><li>How can you maximize the value of an Apollo Deployment? <em>Make sure your schemas are available and present in as many different application contexts as you can</em> (this also segways to graph unity and federation, another topic for another day).</li></ul></ac:rich-text-body></ac:structured-macro><p><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="87a1a3d2-7085-4f7f-98c4-de837ceb2e55"><ac:parameter ac:name="title">Do Not Apply Cyclical/Circular References In Your Schema</ac:parameter><ac:rich-text-body><ul><li>Basically, a cyclical reference is when the same object appears more than once in the same traversal.  In design, circular references are created between object types when they reference one another (as data fields) in a closed loop (e.g. 'Account' object has an 'Invoice[]' field called 'invoices', while 'Invoice' objects have an 'Account' field called 'forAccount').  Self-referential types can also produce circular references.</li><li>What's wrong with circular references? They are security and performance risks:<ul><li>Cyclical query attack</li><li>Out-of-privilege graph traversals: Cyclical references enable 'bidirectional' traversals that can make it extremely difficult to properly limit a query's view of data.  Eliminating the bi-directional nature of cyclical references helps to trivialize the problem of securing data.</li></ul></li><li>Remove reference OR construct a connection/edge wrapper that externalizes and separates circular references into separate wrappers that are each only queryable separately.</li><li>See: <a href="https://wiki.cvent.com/display/PASKY/Wise+In+The+Ways+Of+Wisdom%3A+The+Philosopher%27s+Guide+To+Good+GraphQL+Design+Patterns#WiseInTheWaysOfWisdom:ThePhilosopher%27sGuideToGoodGraphQLDesignPatterns-ProverbVI:CyclicalReferencesAreBad">Cyclical References are Bad</a></li></ul></ac:rich-text-body></ac:structured-macro><p><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="5def23a4-479f-48f9-a22e-82475540e81d"><ac:parameter ac:name="title">Use Query Arguments In Your GQL Query Schema ONLY when you can't use field level arguments</ac:parameter><ac:rich-text-body><ul><li>Query level arguments are not visible to your field level resolvers...unless you're doing some things you shouldn't be doing.</li><li>Query level arguments often force your client to provide an arbitrary argument value even if it is not relevant to the data fields they are fetching.</li><li>See <a href="https://wiki.cvent.com/display/PASKY/Wise+In+The+Ways+Of+Wisdom%3A+The+Philosopher%27s+Guide+To+Good+GraphQL+Design+Patterns#WiseInTheWaysOfWisdom:ThePhilosopher%27sGuideToGoodGraphQLDesignPatterns-Usefield-levelargumentsratherthanquery-levelarguments">Field-level args vs Query-level args</a></li></ul></ac:rich-text-body></ac:structured-macro><p><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="ace89f52-7b0f-4bd6-a206-ec298427d990"><ac:parameter ac:name="title">Use The Field Resolver Pattern to maximize Graph Connectivity and Flexibility</ac:parameter><ac:rich-text-body><ul><li><p>This approach is build around the concept that each field in your schema has a <a href="https://www.apollographql.com/docs/apollo-server/data/resolvers/#default-resolvers">de-facto resolver</a> that can be customized in order to be independent and agnostic of the implementation of it's 'parent' resolver (in a resolver chain).</p><ul><li>Explanation: Anywhere a field does NOT utilize a custom field resolver, <a href="https://www.apollographql.com/docs/apollo-server/data/resolvers/#default-resolvers">a default resolver</a> is invoked in its place.<ul><li>The default resolver for any data field infers an <em>implicit dependency</em> on its parent query to supply that value</li><li>Ergo, any new query written to supply an object of some type that tacitly uses the default resolver will be required to provide that data.</li><li>Graphs alleviate themselves from dependency on the default resolver by writing field resolvers that create a singular and explicit source of data for each object field.</li><li>Such fields are referenceable from any context and from any query in such a way that they do not need to be actively managed by the query itself.</li></ul></li></ul></li></ul><ul><li>This pattern is intended to defer the lazy-loading of a particular data field until it is known that it is requested/required data.</li><li>This pattern maximizes the re-usability of cached data</li><li>This pattern maximizes the flexibility and cohesion of your schema and introduces the notion of<em> implicit resolver re-use</em></li><li>Backloading the resolution of fields to the field resolver makes it easier to reason about your query resolvers (which are otherwise more complicated)</li><li>It maximally reduces over-fetching of data from your data sources by <em>eliminating extraneous fetches of un-requested data</em>.</li><li>Not particularly well documented, but the field resolver approach is the only way to achieve truly arbitrary Graph traversals.  This would be how any organization would begin to approach graph unification.</li><li>At Paypal: <a href="https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55">https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55</a></li><li>At LogRocket: <a href="https://blog.logrocket.com/properly-designed-graphql-resolvers/">https://blog.logrocket.com/properly-designed-graphql-resolvers/</a></li></ul></ac:rich-text-body></ac:structured-macro><p><br
