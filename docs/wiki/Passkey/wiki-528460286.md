# Apollo Client

Consider the following design highlights when building your client-side queries.  Please consult the reference links included with each bullet point for an explanation.

  

Let your graphql queries be appropriately refined.

-   _Appropriately refined_ means neither too fine nor too coarse in the workflow in which it is being used.
-   Unrefined, greedy whole-page queries (_monolith queries_) will have a tendency to negatively impact user experience and eventually lead to over-fetching problems in your UI.
    -   Longer query times are further exacerbated by requests for data that a component does not need in order to render.
-   Over-refined, multiplicitous queries that fetch data too granularly within the same UX sequence (_micro-queries_) leads to load performance concerns on your Apollo server.
    -   In short, micro-queries circumnavigate memoized session objects that are intended for re-use.
-   [Apollo **BatchHttpLink**](https://www.apollographql.com/docs/react/api/link/apollo-link-batch-http/) is very neat, but it does not solve performance limitations that are implicit with hitting Apollo Server with too many queries associated with the same UX transaction, so do not use it as a license to bypass this best practice.

Cache Concepts: What's a Singleton?

-   In this context, A _singleton_ is a collection of cache policies specified in your Apollo client init configuration: [https://www.apollographql.com/docs/react/caching/cache-configuration/#initialization](https://www.apollographql.com/docs/react/caching/cache-configuration/#initialization)
-   The **Query** singleton specifies query level cache settings
    -   Queries can be referenced by name in the Query singleton in order to provide query-specific cache settings.
-   All other singletons represent a collection of policies for a specific Normalized object type (and its fields)
    -   The singleton name is equivalent to the value of the '\_typename' field of the object.
    -   Enumerated object fields can have their own cache policies.
-   The Apollo Client cache is configured via a working set of Singleton type policies.

  

Cache Concepts: Normalized vs Query

-   The _query cache_ is configured by the **Query** singleton and contains string → string key/value pairs where:
    -   The key consists of the name of the invoked query along with the variable values that were provided to the invocation.
    -   The value is the entire query response.
    -   A cache hit on a query cache entry only occurs when that same operation is again executed _with the same parameter values_.
-   The _normalized_ cache is the 'smart' part of apollo client caching:   
    -   JSON objects in a query response that contain a '\_typename' field along with an 'id' (or '\_id') field are _independently cacheable_ using their typename and id field values as a composite lookup key.
    -   Objects in a response that can be normalized are added to the normalized object cache, and replaced in the cached query result with a reference to the normalized object.  If that object already existed in the cache, than a reference to that object is used instead.
    -   In that way, 2 different query invocations that return _partially_ the same data will 'share' their results in the same normalized map.
        -   Eliminates cache redundancy (one cached object instead of two)
        -   Improves cache reusability (future queries can be redirected to the normalized cache to check for matches in there).

  

Normalize your Apollo Client Cache.

-   Reduces the memory footprint of your application cache in the user's browser
-   Increases the re-usability and relevance of cached objects (cache 'hits').

# Apollo Server

As you build your Apollo services and the models that go with them, please consider the following.

  

Your Application's new or proposed Apollo Server Integration should have specific and material design and/or roadmap objectives.

-   What will be the purpose of the integration?  During design, consider the functional role of Apollo in your system.
-   GraphQL's query flexibility and data unity are big wins - _if_ your use-cases leverage them!
    -   Are your application's data needs rigid? Do your clients request the same data in the same form factor over and over again?
    -   If you do not plan to organize or prepare your data to be used in multiple, flexible ways, then GraphQl will only ever be merely an extraneous, expensive proxy for you (and a nuisance).
-   The point is, the justification for an Apollo integration is not a built-in slam-dunk.  You will justify the decision by tracing real value to it, and this will most likely come in the form of use cases that require flexible, multi-present and diverse schemas.  If you don't have actual winning use cases in your project that do that, you may be in for some difficult retrospectives should the integration project not go as smoothly as you hoped.
-   How can you maximize the value of an Apollo Deployment? _Make sure your schemas are available and present in as many different application contexts as you can_ (this also segways to graph unity and federation, another topic for another day).

  

Do Not Apply Cyclical/Circular References In Your Schema

-   Basically, a cyclical reference is when the same object appears more than once in the same traversal.  In design, circular references are created between object types when they reference one another (as data fields) in a closed loop (e.g. 'Account' object has an 'Invoice\[\]' field called 'invoices', while 'Invoice' objects have an 'Account' field called 'forAccount').  Self-referential types can also produce circular references.
-   What's wrong with circular references? They are security and performance risks:
    -   Cyclical query attack
    -   Out-of-privilege graph traversals: Cyclical references enable 'bidirectional' traversals that can make it extremely difficult to properly limit a query's view of data.  Eliminating the bi-directional nature of cyclical references helps to trivialize the problem of securing data.
-   Remove reference OR construct a connection/edge wrapper that externalizes and separates circular references into separate wrappers that are each only queryable separately.
-   See: [Cyclical References are Bad](https://wiki.cvent.com/display/PASKY/Wise+In+The+Ways+Of+Wisdom%3A+The+Philosopher%27s+Guide+To+Good+GraphQL+Design+Patterns#WiseInTheWaysOfWisdom:ThePhilosopher%27sGuideToGoodGraphQLDesignPatterns-ProverbVI:CyclicalReferencesAreBad)

  

Use Query Arguments In Your GQL Query Schema ONLY when you can't use field level arguments

-   Query level arguments are not visible to your field level resolvers...unless you're doing some things you shouldn't be doing.
-   Query level arguments often force your client to provide an arbitrary argument value even if it is not relevant to the data fields they are fetching.
-   See [Field-level args vs Query-level args](https://wiki.cvent.com/display/PASKY/Wise+In+The+Ways+Of+Wisdom%3A+The+Philosopher%27s+Guide+To+Good+GraphQL+Design+Patterns#WiseInTheWaysOfWisdom:ThePhilosopher%27sGuideToGoodGraphQLDesignPatterns-Usefield-levelargumentsratherthanquery-levelarguments)

  

Use The Field Resolver Pattern to maximize Graph Connectivity and Flexibility

-   This approach is build around the concept that each field in your schema has a [de-facto resolver](https://www.apollographql.com/docs/apollo-server/data/resolvers/#default-resolvers) that can be customized in order to be independent and agnostic of the implementation of it's 'parent' resolver (in a resolver chain).
    
    -   Explanation: Anywhere a field does NOT utilize a custom field resolver, [a default resolver](https://www.apollographql.com/docs/apollo-server/data/resolvers/#default-resolvers) is invoked in its place.
        -   The default resolver for any data field infers an _implicit dependency_ on its parent query to supply that value
        -   Ergo, any new query written to supply an object of some type that tacitly uses the default resolver will be required to provide that data.
        -   Graphs alleviate themselves from dependency on the default resolver by writing field resolvers that create a singular and explicit source of data for each object field.
        -   Such fields are referenceable from any context and from any query in such a way that they do not need to be actively managed by the query itself.

-   This pattern is intended to defer the lazy-loading of a particular data field until it is known that it is requested/required data.
-   This pattern maximizes the re-usability of cached data
-   This pattern maximizes the flexibility and cohesion of your schema and introduces the notion of _implicit resolver re-use_
-   Backloading the resolution of fields to the field resolver makes it easier to reason about your query resolvers (which are otherwise more complicated)
-   It maximally reduces over-fetching of data from your data sources by _eliminating extraneous fetches of un-requested data_.
-   Not particularly well documented, but the field resolver approach is the only way to achieve truly arbitrary Graph traversals.  This would be how any organization would begin to approach graph unification.
-   At Paypal: [https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55](https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55)
-   At LogRocket: [https://blog.logrocket.com/properly-designed-graphql-resolvers/](https://blog.logrocket.com/properly-designed-graphql-resolvers/)

  

Use RESTDataSource for outbound calls to REST Microservices

Using built-in Apollo datasources to allow your resolvers to communicate with your backend has a few meaningful advantages:

-   It helps to provide a separation of concerns between the responsibilities of handling business use cases in your resolvers and the responsibility of fetching raw values from your backend.
-   Provides a structured and patterned way to access data that will improve API reference-ability and encourage re-use.
-   Built-in caching will help you debounce duplicate and expensive HTTP calls.
-   Built-in memoization will protect you from duplicitous serialization tasks.
-   Built-in memoization also reduces your memory footprint by managing objects that are re-referenceable between resolvers.
-   Reduces boilerplate code with provided fetch-based wrapper.
-   Data sources are automatically supplied to clients and can be accessed by any resolver via the context object.
-   NOTE: HTTPDataSource is an alternative to RESTDataSource that is mentioned in the official Apollo docs, but you should stay away from it.
    -   I see that as of the V4 documentation, [HTTPDataSource is considered a 'Legacy' datasource](https://www.apollographql.com/docs/apollo-server/data/fetching-data/#legacy-data-source-classes).

See: [Solve N + 1 issues with RESTDataSource](https://wiki.cvent.com/display/PASKY/Wise+In+The+Ways+Of+Wisdom%3A+The+Philosopher%27s+Guide+To+Good+GraphQL+Design+Patterns#WiseInTheWaysOfWisdom:ThePhilosopher%27sGuideToGoodGraphQLDesignPatterns-Solveduplication-of-requestproblemswithRESTDataSource)

  

Use DataLoader only where un-cacheable data can be fetched in bulk

-   DataLoaders are useful for reducing HTTP network overhead lag by generating 'bulk fetch' requests where such fetches are supported.
-   DataLoaders will also apply de-duping of requests.
-   DataLoader will generally make your response data un-shareable with other queries.
-   As such, DataLoader use should be reserved only for those times when you are required to bulk-load un-cacheable data payloads.
-   Per Apollo Docs: [Using DataLoader](https://www.apollographql.com/docs/apollo-server/data/fetching-rest#using-with-dataloader) should be reserved for uncacheable, non-REST circumstances.

See: [DataLoaders: Give yourself to the dark side](https://wiki.cvent.com/display/PASKY/Wise+In+The+Ways+Of+Wisdom%3A+The+Philosopher%27s+Guide+To+Good+GraphQL+Design+Patterns#WiseInTheWaysOfWisdom:ThePhilosopher%27sGuideToGoodGraphQLDesignPatterns-SolveyourN+1problemsII\(Or:TheotherN+1solutionsdon%27thelp.Ineedtogivemyselftothedarkside\))

  

Resolvers: Separate edge concerns from entity concerns

-   When constructing queries that return _lists_ of data, breaking up your search (edge) concerns and your response (entity) concerns will:
    -   Improve your ability to reason about complex resolver code
    -   Improve cache re-use across multiple queries
    -   Reduce over-fetching
-   It's important to use proper pagination when you use this approach (beware N+ 1)!
-   The general idea is to use your query-level resolver to fetch a list of sorted, filtered ids ONLY.
-   The list should be truncated to represent only those items returned for the current page of results.
-   Allow field level resolvers to use the key values supplied by the query resolver to fetch object details.
