# The First Word

The Passkey team is attempting to shift its new UI development efforts towards the use of GraphQL where such use is _useful_ and _appropriate_.  This is well underway, and one of the most easily-identified candidates for GQL to be introduced to (and receive maximum benefit) is any of our modern React-based UI/applications.

At the time of this writing, Passkey development has been creating UIs with React for over 4 years.  Over that time, we have developed an adherence to a set of particular UI development practices and patterns that are important to Cvent as a whole, _as well as_ some of our own ideas that we have found to work towards Passkey's own fairly-unique interests.

In our first few iterations of GraphQL development for React UIs, we can acknowledge through experience that the introduction of this technology in fact has a necessary impact on the way that a React component is built, and how that component will integrate into our application.  There are several ways a developer can attempt to deal with this impact, and the various paths one can take to address this impact can result in some very different consequences. Therefore, it is reasonable for the development team to understand this territory a bit better ahead of time and perhaps allow a somewhat-new way of thinking about React component development inform an updated set of design and implementation principles for integrating GraphQL into their React application.

That brings us to the contents of this document, which attempts to lay bare the landscape to show you what sort of changes to expect, how you can use these differences to your advantage, and how to avoid a few traps that are all too easy to step in.

# Planning your attack: GQL Query Configuration and Orientation

**LET GO OF LARGE, GREEDY MONOLITH QUERIES: FETCH MODULAR DATA MODULARLY**

This is one of the first ways GQL integrations can affect the way you look at UI development.

Modular UI approaches like React prepare the way for embracing higher-resolution data fetching methodologies (like GraphQL), which creates new opportunities for efficiency and optimization..._IF you use it right_.

In summary, there are a small handful of principles that should be considered as you begin to bring GQL queries into your application:

1.  Reduce the amount of data you require at any one time by design.
2.  Stick to fetching only data that is urgently required.
3.  Being too liberal with the number of queries required to complete a single user workflow (e.g. loading a page) can have unwanted impacts on your Apollo server's ability to handle high-load scenarios.
    1.  If you require more than 3-4 queries to load your page, you should at least have a second look at your design to see if all that data is urgently necessary.  Perhaps you can defer/manage some data operations with a flyover, or consolidate the queries of tightly-bound components.
4.  Minimize bulk fetch responses to an ordered keyset. (**Update**: Yes - but do this on the Apollo server side in the query resolver - don't propagate to the UI.  [See here](https://wiki.cvent.com/pages/viewpage.action?pageId=528457478).).
5.  Break up differently-sourced data into different operations.

  

Principle #1

**Data Reduction By Design**

Work with your product lead at design time to identify data-heterogeneous soft spots in the application workflow and figure out a way to break up these UIs into low-friction sub-workflows (example, instead of displaying everything at once, use flyovers, pop-in panels or chevron-controlled expanders to provide that data when a user interacts with the control.

  

Principle #2

**Fetch Only What Is Immediately Required**

Operation response payloads can be reduced in size, server impact, and complexity by only fetching those fields that are immediately required.  Avoid the temptation of over-fetching data in anticipation of upcoming and unpredictable user activity or application events, unless it can be done out-of-band or 'free of charge' (no workload impact on the current operation).  For example, the following example situations would probably not be representations of an immediate need:

1.  The last 450 items of a 500-item search response
2.  The billing details of a billing information popup that is hidden by a 'Show Billing Info' label
3.  The details of a new notification or alert that a user has not asked to see yet.
4.  Attendee contact info for Attendee #2 and Attendee #3 in a tabulated view of 3 attendees (where only tab #1 is currently shown).

  

**Fetch Everything That Is Immediately Required**

There will come another 'opposite' temptation to break your data up into _micro-queries_ that fetch _too_ granularly.  As it relates to peformance, understand the balance between a single user's experience and the apollo server's ability to perform/scale under heavy load.  TOO MANY QUERIES can incur additional overhead that brings your server to its knees as concurrent user visits to your app increases.

This is particularly important in list-like components such as grids or search result displays.  If you want to 'break out' expensive operations from list components, try to break them out of the page load operation as well (for instance, using a flyover or a clickable icon to fetch the data separately when it is requested).  That way, a heavy page load operation can render a useful grid for the user with just a small number of queries.

(Obsolete) Principle #3

**Reduce List Responses To A Key Set**

In cases where you have queries that return lists of data (for instance, search results), it may make sense to minimize bulk fetch operations to only those fields that can uniquely identify a row item and break out separate details queries for only those items currently in the display.  Why?  Because otherwise, re-use of the data in question (specifically, the cached data on both the client AND the server) will be limited to a narrow band of use cases that exactly re-use the same list query and provide an exactly-matching list of options such as sort order, filter criteria, page size and other list customizations (Premise: Query shape and params must match _exactly_  in order to produce a cache hit).  By breaking down a list into an N+1 setup, the amount of cache-unfriendly, list-like data is minimized, while the individual item details, now cached according to their native key, are _maximally_ reusable - not dependent on any particular use case and not dependent on any search criteria.

NOTE: This approach may not be practical in cases where results are unavoidably expected to be paginated in high viewable numbers at one time (e.g. 50 results per page).  In such cases, you should instead apply the Apollo client's pagination solution involving the _fetchMore()_ and the _cursor_ property.  Read more about it here:  [https://www.apollographql.com/blog/graphql/pagination/tutorial/](https://www.apollographql.com/blog/graphql/pagination/tutorial/)

**Update (Mar 3, 2023)**: Especially if you are applying the [field resolver pattern](https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55) with data sources in your Apollo server instance, you should use Apollo's built-in pagination (See above link) _all the time_, rather than using the list reduction method described above.  The concern regarding UI-side cache re-use that is mentioned in the paragraph above can be circumnavigated using an Apollo Client configuration feature called _[cache redirecting](https://www.apollographql.com/docs/react/caching/advanced-topics/#cache-redirects)_.

An example of the built-in pagination utilities in action can be found here: [Lighthouse project pagination](https://wiki.cvent.com/display/PASKY/Lighthouse+Pagination+Patterns#LighthousePaginationPatterns-ApolloServer&UIChanges\(Howdoespaginationaffectthequery?\))

  

Principle #4

**Break up Fetches For Latent Operations Into Different Interactive UX Sequences**

It _can be_ beneficial to break up differently-sourced data into separate operations, _even when that data is fetched for the same UI component_. It is perfectly okay for a React component to utilize multiple useQuery() hooks at once, and this approach helps to prevent any one schema data type (data source) from becoming a bottleneck to load a given component.  This is particularly important when one piece of data is substantially more expensive to get than another, or when a particular piece of data is more _important_ than another.  Rather than predicate the loading of the entirety of the component contents on the successful (and blocking!) retrieval of all data pieces at once, break up the fetch into logical units that could be fetched independently through user interaction, make the UI feel that much more responsive.

**Update (Mar 3, 2023)**: _Synthetic load tests that followed the creation of this document implicates page load sequences that utilize too many queries.  It is okay to break down differently-sourced data into different queries, but the reason for doing so should be to construct new interactive UX sequences that will fetch the data in a separate user-initiated workflow._

_That said, if you have pieces of differently-sourced data used inside the same component and one of them presents a UX experience bottleneck, you should consider the component's relationship with the data in one of the following ways:_

1.  _The bottleneck data is critical to the initial function of the component.  In this case, there is no point in otherwise rendering the component without this data, anyway.  Consolidate the data into a single query so that it is fetched all at once.  Use a spinner or a placeholder card in the meantime until all required data is retrieved._
2.  _The bottleneck data is not critical to the initial function of the component.  In this case, decouple the fetching of the bottleneck data from the loading of the component. Use a flyover or a clickable area to fetch the data on demand at the user's request, for instance.  Every situation is different, but the solution is often the same: create a new UX sequence that the user can engage in order to get data that is too expensive to implicitly attach elsewhere._

  

# UI Repository Setup

This section describes how you can apply a separation-of-concerns pattern in your repo structure for maximal manageability and maximal component reuse.

A GraphQL integration primarily consists of the following logical components:

-   An Apollo Client (for Apollo Provider)
-   Query Files (one per component)
    -   Query Definitions
    -   Variable Definition & Helper Functions
-   GQL Wrapper (one per integrated application component - this is where useQuery() will live)

Try not to overthink the idea of _sharing_ query definitions or query response definitions (where TypeScript is applicable) between components in your UI project.  This sort of contractual sharing and reuse is not an optimization in modular Apollo/React applications, but rather an _anti-pattern_ (Components should own their own contracts).  That said, a possible idea for a similar sort of sharing can be accomplished via GQL query fragments, a concept that is not covered in this document, but you can read about here: [https://www.apollographql.com/docs/react/data/fragments/](https://www.apollographql.com/docs/react/data/fragments/)

# How To Deal With 'Loading'-State Components

GraphQL integrations are delightfully asynchronous and do not prevent component rendering even when the query is not yet completed execution.  Instead, the useQuery() hook provides the component with a 'loading' boolean variable to indicate whether or not the query response has been fully loaded yet.  If not, 'loading' will return a value of true to your component, and your component code can decide how to proceed without a result in hand.

Hotel Name: {data.hotelInfo.name}

Hotel Description: {data.hotelInfo.description}

); }\]\]>

In the above case, we are simply going to return nothing if the query response is still incomplete.  When the network status of the query has changed (loading = false), the component will re-render and the value of the loading variable will be false, and the \`data\` payload will populated with the query response object(s).

In practice, though, returning a value of NULL during load is not ideal, as it results in a jarring disruption of the visual experience in the UI as a component suddenly appears without warning and displaces real estate of some other component in order to render itself.

We should find a better way to manage component loading state so that customers don't have to put up with jarring visuals and unexpected screen mutations (components 'making way' for new components post-render).

## Option 2: Yeh

{ const gqlVars = constructGQLVars(props.hotelId, props.localeId); const { \_, data } = useQuery(FETCH\_HOTEL\_INFO, { variables: gqlVars, notifyOnNetworkStatusChange: true, displayName: \`query-hotel-info-${props.hotelId}\` }); return (

Hotel Description: {data?.hotelInfo?.description || ''}

); }\]\]>

In this slightly modified case, we've improved the situation somewhat by unconditionally rendering the component, but _conditionally_  rendering the labels associated with query response data.  This at least prevents the jarring shift of UI components when the query response is finally received, and instead simply backfills the appropriate text into the appropriate space once the response text is available.

However, the end user still has no way of knowing the different between a query that is still running and a response that simply did not contain a name or description.  To solve this problem , we will have to be a bit more clever.

# Error Handling Recommendation: Build Unioned, Interfaced Errors Into Your Schema

Proper GraphQL error handling is likely a joint effort between your UI code, your GraphQL schema and your service-side Apollo resolver code.

-   Your GraphQL Schema must provide a medium for delivering errors from the server to the client in the first place
-   Your resolver code must intelligently populate schema elements with error information when errors occur
-   Your UI code must be able to interpret errors in client-side code and handle them elegantly and in their own particular way.

## The Top-Level Error Payload

Due to a general inability to gracefully filter and bubble Exceptions from the Apollo Provider, it is not recommended to use the Top Level Error object for delivering business-grade errors to GraphQL clients.  Colluding business errors with fatal (network/protocol/transport) errors at the top level of the error payload makes knowing what to do with any one error quite cumbersome.

Insofar that GraphQL is able to fulfill its own side of the bargain, it seems we should be avoiding the Top Level Error Object as an error mechanism, according to most online guidance on the matter

Unfortunately, that means that most of the error 'kinds' that we need to be able to provide special handling for are left without a home, and we are left to our own devices to accommodate business level error that are raised either by the resolver code in our Apollo Server OR by the microservices that are being accessed behind the scenes.

## Proposal: Unions Are The Best Fit

There is a comprehensive and recommended article here ([https://productionreadygraphql.com/2020-08-01-guide-to-graphql-errors](https://productionreadygraphql.com/2020-08-01-guide-to-graphql-errors)) that walks us through the various evolutions of error handling.  The Bottom line is that _there is no one error handling solution_ yet that seems to check all the boxes, and derivative solutions beyond the ones recommended in the article that attempt to cover all the bases appear verbose and unwieldy.

There are some fundamental things that we want our solution to cover (if not completely, at least partially):

-   Type-level or Field-level errors that can be contextually handled directly in affected components.
-   Strongly-typed error contracts that are easily discoverable by client-side GQL tooling.
-   A fallback Interface to allow public clients to handle errors that are new or that _don't_  require special handling
-   Ability to report multiple problems at once (particularly, when validating mutation input)

#### Things To Remember:

-   Remember that if you use a Union, your Apollo resolver set **MUST** supply a type resolver for your Union type. In the above example, see the '\_\_resolveType' function-type property in the resolver.ts file.
    -   This pattern is common in TypeScript and is known as a **user-defined type guard**.
    -   Specifically, this function is to allow GQL to apply the correct resolver chain on Union objects returned by parent resolvers.
        -   Remember, YOU created and determined the response objects in your resolver business code, and GQL cannot read your mind - you need to tell it what your intended pattern is.
    -   GQL will fail at run-time if you do not disambiguate Unionized responses to specific types.
    -   You _can_ use 'instanceof' in certain circumstances; specifically, when you utilize a class constructor to build your response objects.  However, we have not typically done this.  Remember that _compile_\-time typescript type instances are just ordinary javascript objects at _run_\-time, and TypeScript will complain if you attempt to use a Type rather than a Class on the right side of the instanceof operator.
    -   Apollo recommends testing field existence for determining Union subtypes using the **in** keyword (See the \_\_resolveType example above).
-   Your query now needs to specify multiple sets of response fields - one per union type.
    -   Use '...' (Spreader) syntax for this - see the '... on Hotel' example above. 
    -   Union subtypes can be ignored in your client queries, but if your query response contains an object of that subtype, you won't be able to see it.  

### Using Multiple/Nested Unions In Query and Mutation Responses

When you apply unions to query responses for error handling purposes, you generally want to **apply the unions in your schema where they correlate with a distinct data source API**.  The idea here is to not block sibling resolvers where you do not have to.

Let's expand our simple example Hotel schema type to include a few new fields:

jsMidnightHotel Schema Snippet

For the sake of this example, the important thing to know about these new fields is that they each require their own data source API function to fetch.  This means that the API function that fetches top-level hotel information might succeed, but the API call to fetch,say, the total available rooms (which utilizes an altogether different microservice) could possibly fail.

Now, if we continue to only handle errors at the **HotelResponse** union level, then we have much the same problem that we had when we used the top-level errors object to report problems - _ambiguity_ and _lack of context_.  Further, the presence of an errorCode at the hotelLevel when hotel-level data was successfully fetched is confusing, and the UI doesn't know which field to reconcile the error to.

Lastly, it may be important to know when several bad things have happened at one time.  For example, if both your room type data service and inventory service are offline for maintenance, your Hotel union does not have the capacity to report those separate failures in a single response.

# Caching Principles

Caching is an important topic in UI-side GraphQL development.  Most of the ideas in this section originate from the Apollo documentation: [https://www.apollographql.com/docs/react/caching/cache-configuration/](https://www.apollographql.com/docs/react/caching/cache-configuration/).  Client-side caching is very well documented by the Apollo team and I implore you to read it since it is a shame to simply duplicate their hard work here.

Note that there are two main cache components that I will discuss here:

1.  **The Normalized Object Cache**: This cache is configured to normalize all query response data into a cache keyed by each object's unique identifer(s).
2.  **The Query Result Cache**: This cache stores the results of a query operation (taking into account different query param values, sort orders and filters).  Rather than duplicitously store whole objects in the result cache, Apollo client replaces normalizable objects in the result with references to the corresponding Objects in the normalized cache.

## Normalization

The basis of client side caching is this idea of response normalization - the process whereby a query response is broken apart into entity layers, each layer component being cached according to its respective cache key.  Each schema type can be independently configured in the Apollo client bootstrap configuration.  **_There is typically a minimal amount of caching configuration that you need to provide_ in order to get caching to generally work.**

The idea is, Apollo client attempts to process your query results such that future queries that even merely partially overlap with previously collected data will fetch what it can from local storage.

## Cache Key Configuration

There are a couple of important notes you need to remember about cache normalization:

-   Your query results MUST supply Apollo Client with a **\_\_typename** field for each object you wish to store in the normalized cache.  This field is auto-populated in Apollo client's default configuration, but if you turn it off, you will have to supply type names manually, or live with a denormalized cache (response cache only).
    -   Apollo client uses the type name field to map a response object to a cache configuration, and also to partition cache results by type.
-   Your query results MUST supply an **id** (or **\_id**) field for each object you wish to normalize in your cache. If your schema types do not have id fields, you will have to supply Apollo client configuration with the name of the key fields ("keyFields") for each such type.  Otherwise, your cache is not going to function the way you want it to.
    -   FYI: Compound keys, as well as complex object-type keys are supported.
-   The normalized cache is a _flat map_.  That means that cache keys are _composites_ that consist of both the **\_\_typename** and the **id** of an object.

## Cache Merging

It is easy to confuse cache _merging_ with data _normalization_.  By default, the Apollo client cache reconciles incoming data to the cache in a way that is _cumulative_.  In other words, multiple queries that fetch different field sets for the same cached object will preserve all previously-fetched values for that object except for common crossover fields between the queries where the _new values are different_.  In those cases, the Apollo Client will simply replace the old values for the new values by default.

However, there might be cases in your application where you need to perform an intelligent reconciliation of cached field data and fresh incoming data.  For instance, you might have a cached object which contains a list property with local-only changes that you don't want to lose, but wish to _append_ fresh incoming list data to.

If that is the case, then you want to configure your cache with a fieldPolicy-level merge strategy.  As of Apollo Client v3, you can very quickly apply the built-in Apollo merge utility by specifying\`merge: true\` at the type level for the type in question in your typePolicy cache configuration.  If your application requires a more sophisticated field-level custom merge strategy, the merge property supports functions as well.

[https://www.apollographql.com/docs/react/caching/cache-field-behavior#the-merge-function](https://www.apollographql.com/docs/react/caching/cache-field-behavior#the-merge-function)

# Cache Management and Tuning

## Cache Timeouts/TTLs

The default InMemoryCache Apollo Client v4 implementation does not natively support cache timeouts.  HOWEVER, the Apollo Invalidation Policies cache ([https://www.npmjs.com/package/apollo-invalidation-policies](https://www.npmjs.com/package/apollo-invalidation-policies)) is a swap-in extension of the v3 cache that invalidates cache entries after a certain configurable period of time and forces an eviction and subsequent live query on the first request following expiration.

## Cache Busting

Caching is a fantastic tool, but sometimes it must be bypassed.  Perhaps you have timed updates that you need to be able to apply to cache objects, or perhaps you have a subset of data items that simply can't be cached. In any case, you need to figure out how to work around your cache to make sure you're getting the data you need.

## Cache Updates Following Mutation

As a best practice, Mutation operations should **always respond with the new, modified item** (including any new changes that were applied to it).  Mutations that are made in this way via the apollo client will update the locally cached with the results (merge function applies here as well). 

Note: ROOT\_QUERY caches will not be updated on mutation response (makes sense - how could it possibly know which responses to update?).  This is not a problem for all application contexts, but there are a couple of good options, here, when it is:

1.  The useMutation() function's _update_ callback can be used to manually update query responses in the cache with changed items.
2.  Cache busting: Following a mutation, invalidate the ROOT\_QUERY cache entries.
3.  Fetch Policies: Configure a 'cache-and-network' query fetch policy that provides cached results to your client immediately, while refreshing the cache under the covers (may cause follow-up renders)

# Testing Infrastructure

Once you get going with GraphQL, you will quickly notice that components become tightly coupled with their data sources, even after you apply the separation-of-concerns wrappers mentioned earlier in this document.

It is not avoidable (consider nested GQL objects and the necessary GQL dependencies created there), and we must figure out a way to integrate GQL query mocking into our test harnesses.

## MockedProvider

The utility we use in order to provide GQL connections in test environments is the Apollo-provided MockedProvider component:

jsMidnightGraphQLTest.ts { test('test basic render', async () => { let renderResp; await act(async () => { renderResp = render( ); /\* Wait for event tick - MockedProvider requirement \*/ await new Promise(resolve => setTimeout(resolve, WAIT\_FOR\_ASYNC\_HOOKS\_MS)); }); const { container } = renderResp; const renderedElement = getByCventId(container, 'expected-element-id'); expect(renderedElement).toHaveTextContent('Expected Text'); const content = pretty(renderResp.container.innerHTML); expect(content).toMatchSnapshot(); }); });\]\]>

Make note of the following:

-   Apollo MockedProvider only allows you to reference a mocked result ONE TIME.  If your test requires multiple renders, you will need to provide the same mock object multiple times.
    -   A cache-first fetch policy may address this, but cache policies currently break MockedProvider without giving it additional configuration.
-   Make sure your component is provided with mocked state data/properties that will match the expected variable values in your GQL mocks.  Otherwise, the mock will miss and your test will fail.
-   GraphQL useQuery, useMutation and useLazyQuery hooks are asynchronous 'fetch-while-rendering' react hooks.
    -   This means that if you do not wrap your mocked render in an asynchronous act() call and await() it's completion for the appropriate amount of time, your test will fail.
-   MockedProvider breaks the react-test-renderer's ability to test react DOM state directly.  You can no longer directly reference functional object methods with this utility!
    -   Recommendation: Stop testing DOM state changes and stick with testing-library to test component behaviour, NOT component state.
    -   testing-library produces element/HTML snapshots that are a suitable replacement for react-test-renderer when doing snapshot testing.
