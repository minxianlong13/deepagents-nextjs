<em>a retrofit of a modern <strong>backend-for-frontend microarchitecture</strong> overtop of an Oracle-based monolith datastore. </em></p><p>Product repository: <a class="" href="https://github.com/cvent-internal/passkey-rdk2">https://github.com/cvent-internal/passkey-rdk2</a></p><p>In Oct 2023, RDK2 was re-platformed as a<a href="https://wiki.cvent.com/display/KB/Cvent+Development+Framework"> CDF framework application</a>.  CDF is a custom Cvent platform for developing and deploying web applications and its supporting infrastructure. </p><p>RDK2 uses these key architectural components that are part of the CDF paved road, from the top down:</p><ol><li>React, running in a client browser.</li><li>NextJs/Apollo(GQL), running as a NodeJs service in AWS Fargate.</li><li>Dropwizard Microservices running in AWS ECS as containerized, clustered Java services.</li><li>Oracle Database and Legacy Procedures</li></ol><p>There are other architecture technologies used by RDK2 that deserve mention as well, including Cvent Auth (an authorization subsystem built by Cvent), Redis, STEP Functions front-end in production - the new home page (project is still called 'passkey-rdk2', but that will have to change).</li><li>New UI frontend projects will be created as we re-develop Resdesk Classic Navigation</h2><p>The RDK2 application and Resdesk Classic are <em>sister</em> deployments, simply meaning that they are independently deployed, but interconnected at run time in every user session. Service (NodeJS)</h1><h2>Integration with Resdesk Classic: How does auth work?</h2><p>We currently still use the old Resdesk Classic login sequence to log users into the system.  Once credentials are verified, we concurrently invoke 2 different auth systems:</p><ul style="list-style-type: square;"><li>Wildfly auth w/ custom session hydrating (used primarily by Resdesk Classic)<ul style="list-style-type: square;"><li>Cookie-supported</li><li>Session hydrating: Wildfly server is very stateful, tracking 'user journey' artifacts as the user browses from page to page</li><li>These artifacts can be loaded from the DB when not in memory</li><li>HTTP Sticky sessions provided by the Resdesk Classic Load Balancer keep users on the same Wildfly node for the duration of their user session (even when they are browsing RDK2).</li></ul></li><li>cvent-auth: Cvent's universal auth subsystem - uses API Keys and BEARER tokens for auth<ul style="list-style-type: square;"><li>This is also cookie supported.</li><li>This auth system is well frameworked to get basic functionality for free in microservices, CDK projects, and CDF/NX projects.</li></ul></li></ul><p>RDK2 and Resdesk Classic are deployed to the same sub-domain, so we combine both wildfly session id and cvent-auth token into the same cookie.  Insofar that other micro-frontends are deployed in the same sub-domain (and use cvent-auth), they can borrow the same cookie, allowing cross-navigation between apps to occur seamlessly.</p><p>See wiki: <ac:link><ri:page ri:content-title="Authentication Mechanism" /></ac:link></p><h2>Highlights</h2><ul style="list-style-type: square;"><li>NextJS is a web service for NodeJs that serves up typescript files as 'routable' UI content and (optionally) web APIs.<ul style="list-style-type: square;"><li>...including Apollo/GraphQL.</li></ul></li><li>NextJS serves up as much static UI content as possible, minimizing SSR live rendering.<ul style="list-style-type: square;"><li>Dynamic server-side rendering is expensive</li><li>Generally, for dynamic content, the preferred approach is to supply static UI bundles to the browser that include calls back to GraphQL for datasets the page requires to render.</li></ul></li><li>Deployed as auto-scalable Fargate svc.</li><li>Apollo formulates a data model using <a href="https://wiki.cvent.com/display/PASKY/Apollo+and+GQL+Best+Practices+Reference">the field resolver pattern and data sources</a>.<ul style="list-style-type: square;"><li>Caches/memoizes microservice endpoint calls that retrieve entity details all-at-once.</li><li>Field level calls ensure that data is not over-fetched by the browser</li></ul></li><li>Authorization:<ul style="list-style-type: square;"><li>Calls to fetch static UI content are generally not authorized</li><li>Calls back from frontend React components to Apollo/GraphQL are authorized via cvent-auth token.</li></ul></li><li>Apollo Data Caching:<ul style="list-style-type: square;"><li>Apollo Cache is a Redis cluster</li><li>We cache whatever we can, for as long as we can</li><li>Working on admin endpoints for cache invalidations (following data mutations)</li></ul></li></ul><h1>Microservices</h1><p>Note: Our microservices are not truly discrete.  This is because they all share the same Oracle RDBMS instance behind-the-scenes.  Oracle data is organized into 'areas of responsibility' and then assigned to one microservice or another.  There is often some crossover between services, which is not ideal but has suited our purposes.</p><h2>Highlights</h2><ul style="list-style-type: square;"><li>Java (JDK17) Microservices using Dropwizard</li><li>All microservices use cvent-auth for authorization</li><li>Microservices have these layers:<ul style="list-style-type: square;"><li>Resource: Resources are classes containing published endpoints.<ul style="list-style-type: square;"><li>Dropwizard annotations make this trivial.</li></ul></li><li>Service: Service classes contain business code and data manipulation/aggregation operations.</li><li>Data Access: DAOs contain functions to fetch/delete/add/edit data<ul style="list-style-type: square;"><li>Backed by an Oracle database cluster</li><li>Data operations are wrapped by XML-mapped Mybatis Persistence Framework calls.</li><li>Caches used:<ul style="list-style-type: square;"><li>Mybatis built-in cache</li><li>Google/Guava LoadingCache (for memoization)</li></ul></li></ul></li></ul></li><li>Principles:<ul style="list-style-type: square;"><li>The primary audience for microservices is internal Passkey components.<ul style="list-style-type: square;"><li>As such, use API_KEYs for auth, NOT BEARER tokens.</li></ul></li><li>Microservices are STUPID in that their endpoints perform very targeted operations.</li><li>Don't get distracted with validations and side-hustles in MS endpoints.</li><li>Multi-operation endpoints should be:<ul style="list-style-type: square;"><li>Broken down into multiple endpoints</li><li>Sequenced/orchestrated by a saga (we currently use AWS Step Functions for this)</li></ul></li></ul></li></ul>
