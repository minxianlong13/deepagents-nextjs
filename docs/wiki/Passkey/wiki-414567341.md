Note that <u><em>GQL does not support JOIN statements, or anything much like it</em></u>.</p><p><strong>Aggregations</strong>: If your UI requires a view of aggregate data, you need to consider the context of the request.  There are libraries available (e.g. dgraph) that will allow clients to request aggregate views over schema objects, but this approach would not be recommended with REST-backed datasources if the aggregation 'goes deep', or is simply attempting to aggregate a lot of data.  For those cases, we would consider actually modelling aggregation values into our schema and implementing an aggregation function in our underlying microservice so that aggregate values (rather than raw data) can be fetched by affected GraphQL field resolvers. This greatly reduces the HTTP transport overhead, serialization times and cache sizes.</p></ac:rich-text-body></ac:structured-macro><h2>Proverb VI: Cyclical References Are Bad</h2><p>In plain english, a cyclical reference is when an object field returned by a query is re-referenceable by traversing the graph further.</p><h3>Example:</h3><p>Suppose the following GQL schema:</p><ac:structured-macro ac:name="code" ac:schema-version="1" ac:macro-id="e9a8bf51-5c2b-42ac-a380-3c686ccf4fa4"><ac:plain-text-body><![CDATA[type FamilyMember {

  name: String
  age: Int 
}

# We can still allow this entity type to exist for controlled backend traversals as long as we do not return it in a query response.
type FamilyMemberBothDirs {
  familyMember: FamilyMemberInfo
  parents: [FamilyMemberBothDirs]
  children: [FamilyMemberBothDirs]
}

type FamilyMemberDescendantsConnector {
  familyMember: FamilyMemberInfo
  children: [FamilyMemberDescendantsConnector]
}

  familyMember: FamilyMemberInfo
  parents: [FamilyMemberAncestorsConnector]
}

  familyMember(name: String): FamilyMemberInfo
  familyMemberWithDescendents(name: String): FamilyMemberDescendantsConnector

VII: GraphQL is optimized to supply 'per-scalar' resolvers wherever possible.</h2><ac:structured-macro ac:name="info" ac:schema-version="1" ac:macro-id="5b0ee149-231c-4faa-8a16-5f8623049536"><ac:parameter ac:name="title">Summary</ac:parameter><ac:rich-text-body><ul><li><strong>Low-resolution data fetching should be avoided.</strong></li><li><strong>Avoid over-dependence on the default resolver.</strong></li><li><strong>Don't over-fetch in a resolver parent.</strong></li><li><strong>We should err on the side of resolver expressivity to avoid bad design during break-in period</strong></li></ul></ac:rich-text-body></ac:structured-macro><p class="auto-cursor-target"><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="264fc7e9-f547-4d08-9920-07cd94a2d382"><ac:parameter ac:name="title">Read more...</ac:parameter><ac:rich-text-body><p>This point is of particular importance to us (Passkey) precisely because we are layering GraphQL over <em>literally dozens</em> of HTTP REST microservices.</p><p>There is a mechanism in Apollo Server that any GraphQL query execution will fall back on when there is <em>NO explicit resolver function</em> defined for a particular schema field.  In such cases, GraphQL simply attempts to reconcile the schema field in question to the resolver's <strong>parent</strong> object (which is a special arg that is always passed in to all GraphQL resolver functions).</p><p>The mechanism which performs this implicit reconciliation is known as the <em>default resolver</em>.  In GraphQL, the approach where a parent object in a query resolver 'trickles' down the field data to its child fields via the default resolver is known as <em>type</em>-level resolution.</p><p>Aside from its use as a fallback for GraphQL to present data whenever it possibly can, the default resolver is often leveraged by developers as a shorthand way to auto-map schema fields to values that have already been retrieved by a parent resolver - no explicit mapping required.</p><p>This is an obvious call to convenience, here - after all, what developer doesn't want to avoid boilerplate code - but the many experts who are posting their GraphQL examples and solutions on the interwebs <em>already know</em> about the importance of 'bottom-up' resolver design at the field level.  There is a difference between understanding <em>how</em> and <em>where</em> type-level resolution does not hurt you in your specific model, and deciding not to declare field resolvers because nobody else seems to be doing it and you just want to make your code smaller.</p><p>As it turns out, indiscriminate use of the default resolver in any large graph is quite evil, and it will impose itself on our resolver design in very bad, un-performant, and/or un-scaleable ways when you do not understand the implications of model-induced over-fetching.  Low resolution fetching will typically result in fetching more data at one time, which is where the 'get-only-what-you-need' approach goes to die.  The remedy, then, is high-resolution fetching at the field level.</p><p>For this reason, I recommended that the whole Passkey dev team declaratively express their field-level resolvers for the time being, and <strong>do NOT fall back on the default resolver</strong> where at all possible.  In my opinion, this 'training' approach is how we will get developers to understand why field-level resolution is what makes this engine powerful, and why they should <em>want</em>  to do it.  Insofar that our devs do <em>NOT</em> understand this principle and lean on type-level resolution in the resolver parent anyway, we will be that much more Your GraphQL model should not merely be a perfect reflection of your low-level data sources, OR as a one-stop shop that must be equally capable of doing <em>everything</em>.  A well-built graph model will be <em>dynamic</em> and <em>asymmetric</em> - differently-shaped in its various surface areas because fundamental requirements of your application have dictated the profile of the model.  For graph-based applications, it is an advisable trade-off to specialize parts of your graph to be good at one important thing at the expense of some other less important function.  Start by asking some basic questions in the design phase of your project to gain contextual insight into the various parts of your graph:</p><ol><li><strong>Is the graph model I've constructed for my product appropriate?</strong>  In other words, are my queries simple or complicated (hint: avoid complicated GraphQL resolvers)? Ideally in any graph, you want to minimize the number of edges that must be traversed in order to produce the desired output for your particular use case(s).  For instance, let's say your application Graph model as currently designed is made up of raw user profile data.  Your UI use case appears to call for mostly aggregate user data based on profile categories.  Is there any way to simplify/reduce this part of your model so that aggregate views and values are more accessible, more easily cached, and more quickly retrieved?</li><li><strong>Are use case expectations appropriate?</strong>  UI designs often lend themselves to bad assumptions about how users will actually engage the data.  Don't assume or implicitly agree to requirements that impose immediate performance/scalability concerns when the use case has not yet been reasoned to be useful and/or purposeful.  For instance, a common anti-pattern that used to plague older web UIs was a bias for the premature presentation of list data.  It was assumed by some search-oriented interfaces that users should be presented with data immediately, and then supply filter values to hone in on what they wanted to see.  However, this presented a very expensive and data-heavy operation at the onset of the user experience.  Was it really necessary to do the work of fetching and organizing the entire firehose of data for all users, for every visit?  Is such a view even useful?  These are questions that we should have been asking at the time, yet only a few were doing it.  We can't change the past, but perhaps you can avoid the work of having to performance-optimize GraphQL queries that users shouldn't even be using. </li><li><strong>Is my resolver design appropriate?</strong> If you are abiding by best practices, this is the last question to ask, not the first (read the sections below to find out how to have the best of both worlds inside the boundaries of proper, supported GraphQL integration and good resolver design).  Attempts to compensate for performance problems by pre-emptively de-constructing your resolver model in favour of custom low-resolution batch/bulk fetching is very likely to hurt your UI's ability to scale up to large datasets without issues (HTTP timeout problems and cache ineffectiveness, to name two).</li></ol></ac:rich-text-body></ac:structured-macro><h2>Proverb IX: Do not desecrate the Context object, for it is sacred</h2><ac:structured-macro ac:name="info" ac:schema-version="1" ac:macro-id="782ace5b-0205-44b6-a6c0-9854ec53cd9c"><ac:parameter ac:name="title">Summary</ac:parameter><ac:rich-text-body><ul><li><strong>The GraphQL <em>context</em> object, while visible to all your resolvers, should <u>not</u> be modified.</strong></li></ul></ac:rich-text-body></ac:structured-macro><p class="auto-cursor-target"><br /></p><ac:structured-macro ac:name="expand" ac:schema-version="1" ac:macro-id="84dc5c83-8bca-40fd-8ddc-bf1f0a02c81b"><ac:parameter ac:name="title">Read more...</ac:parameter><ac:rich-text-body><p>Common to every query execution is the GraphQL <strong>context</strong> object that gets passed down through the entire resolver chain.  As the same instance of the context persists for the entire duration of query and is visible to all query frames, the temptation to use it as a means to supply custom data back and forth between resolvers can be quite strong.  Avoid this - context mutation produces implicit dependencies on state that make your resolvers harder to understand and harder to re-use.</p><p>The context object is for <em>request</em> context that is calculated at the start of a request.  It is NOT for accumulating session information <em>during</em> traversal, or for sending signals from one resolver to another in order to get them to do something special.  <em>You've been warned: You can look, but you can't touch.  if you write context-mutating resolvers, you will eventually wreck your application</em>.</p><p>In cases where you need data to 'trickle down' from one resolver to another, remember that the output object(s) of a parent resolver becomes the parent object for all immediate child resolvers.  This means you can share data from a parent resolver to a child resolver by incorporating the value into the parent object.  Use this to your advantage.  </p><p>Something else that can help here is <em>field-level arguments</em>.  If you have two resolvers in a resolver chain that are dependent on the same user-provided data, you should consider updating your model so that <em>both</em> fields/resolvers will inherit the argument value via field-level args.</p></ac:rich-text-body></ac:structured-macro><h2>Proverb X: GraphQL != REST</h2><p><br /></p><ac:structured-macro ac:name="info" ac:schema-version="1" ac:macro-id="5e1192fe-5605-41de-baa3-637fc3f3fc73"><ac:parameter ac:name="title">Summary</ac:parameter><ac:rich-text-body><ul><li><strong>Modelling dissimilarities between REST and GraphQL have been discussed in the first section of this document.</strong></li><li><strong>The rigid contract-based REST principles are loosened in GraphQL, particularly when the client is a UI front end.</strong><ul><li><strong>Not every error is a blocking error! ac:macro-id="d0fab7cb-2267-4ad9-9cf4-ee915ae8cacf"><ac:parameter ac:name="title">Read more...</ac:parameter><ac:rich-text-body><p>It is important to know that aside from the modelling principles identified above, there are specific semantical constraints that apply to REST endpoints that should not be propagated into your GraphQL queries.  GraphQL has its own unique error and edge case handling features that should not be bypassed for the sake of propagating REST errors to the client.</p><p>Simply put, coming to GraphQL from the area of Microservice development, we might incur unconscious bias towards treating our GraphQL response like REST endpoint responses.  But the point of your GraphQL response in the context of a UI is to <em>elevate the UI experience</em> and make things as comfortable as possible - not to interrupt users with interfering popups and their error codes that users can't do anything about, anyway.</p><p>The best practice in GraphQL is to absorb the error into the workflow as best as possible.  Don't make blocking problems out of non-blocking problems.  If there's something that needs to be communicated to the user, integrate your error into your response data so that the UI doesn't need a lot of error handling code to handle user-feedback error cases.  More on this in the <em>Proverbs that are not proverbs</em> section below.</p><p>For example, let's say a UI has requested info cards for ten doctors.  The data for nine of those cards were retrieved without issue, while one of them suffered a <em>not found</em> HTTP error during one of the supplemental catalog data lookups that occurred on a backend microservice.  By convention in REST, we do not return a 200 (OK) response unless we have satisfied the directives of the request, so we typically respond in such cases with a 404 not found HTTP code, or perhaps a 500 ISE, depending on our error propagation policy.</p><p>But once that error has propagated to your GraphQL service, you might (and often should) handle the situation in a different way.  This becomes a large conversation, but here's a couple of basic principles:</p><ol><li>Don't block the entire response with an error code if the error itself is not implicitly blocking in nature.</li><li>Don't place non-blocking errors in the 'errors' payload of the GQL result.  This forces the UI to 'stop the world' - conditionlessly block, parse and handle all 'errors' content since the UI can not tell whether or not they are important or urgent without doing that.</li><li>Global errors and/or user-blocking errors that have no data context (Permission Denied, for instance) <u>can</u> be added to the 'errors' GQL response object so that the UI code can take appropriate action.</li><li>In many - even most - cases, data-specific errors <u>can</u> be integrated into your 'data' response object so that errors show up as placeholders in your response where the expected data would have otherwise been.  In this case, the particular component(s) that handle the erroneous data element can decide what they want to do with it.<ol><li>Boris has excellent documentation about how to do that here: <ac:link element) can be found here: <a /></p><p>If an error raised in your resolver can be encountered during orthodox, reasonable use of your application, you should consider absorbing the impact of the error somewhere in your workflow in a way that reduces the impact to the user experience in whatever reasonable ways.  Here, it's important to note that <em>non-existent data is not necessarily an error condition in GraphQL</em>.  If you Apollo server attempt to fetch some data that could not be found by a microservice (HTTP 404), consider whether or not the user can press on in a normal fashion without it.  If they can, you would be well advised to handle these errors strictly on the server side (logging, alerting auditing, etc) and let the UI resume business as usual.</p><p>Remember to focus your graceful, 'white glove' error handling at UI end-users who are playing by the rules.  Errors that are produced by exploitative or unsupported use of your application do not require the extra effort of elegance and can be a more primitive experience.  Whatever the case, just be sure to handle it in a way that <em>protects the system</em> and <em>does not reward malicious caching</strong></p><p>A UI or another GraphQL client is likely to re-use some of the same queried response data to facilitate application data needs across multiple pages and/or multiple visits.  Drive down traffic between your Apollo server and your clients by implementing the @cacheControl directive on cacheable scalar fields that are resolved by REST microservices.  GraphQL says that the cacheControl maxAge attribute can roughly correlate with the interval in which the cached data is generally updated - obviously, this leaves the choice up to you.</p><p>Boris describes our target by GraphQL out of box.</p><p>Data sources apply server-side, or <em>microservice-facing</em>, caching of data that has been retrieved from microservice endpoints so that MS endpoints do not need to be redundantly queried for the same data over and over again merely because multiple clients are accessing it.  Caches are configurable, and you can tune your data source's cache on a case-by-case basis to correlate with expectations regarding the frequency of changes (in short, the longer the expected timeframe between updates to the data in question, the longer the data itself can be cached).</p><p>On the data source side, cache entries are keyed according to the complete URL (including query params) by default.  This is typically adequate, although it can be overridden with a RESTDataSource-provided hook called <strong>cacheKeyFor()</strong>.  For instance, if you are leveraging a HTTP POST endpoint to perform a search using a provided request payload, you will likely want to override the default cache key to incorporate request payload values.</p><ac:structured-macro ac:name="info" ac:schema-version="1" ac:macro-id="3dd8a0ac-6121-414a-8106-05cf5ec7584f"><ac:parameter ac:name="title">For your reference:</ac:parameter><ac:rich-text-body><p><em>Re: HTTP POST endpoints: If your target REST endpoints fetch data via HTTP post, you will want to override RESTDataSource's default cache key generator.</em></p><p><em>I recommend <strong>sorting</strong> the request body prior to sending the request (to remove out-of-order misses and maximize cache hits), and then using the <strong><a href="https://github.com/puleos/object-hash">object-hash</a></strong> library to create a unique SHA1 or MD5 cache key for your request object.</em></p></ac:rich-text-body></ac:structured-macro><p><strong>Object Creation Reduction</strong></p><p>Be aware of Node object creation behaviour in your frequently-accessed code!  Note that library-level methods (including Data Source APIs!) that get invoked over and over again should avoid creating new objects - implicitly or explicitly.  Object creation under high load scenarios will have a significant impact on your Apollo server's ability to respond to requests in a timely manner (single-threaded NodeJS can't respond to <em>anything</em> while its GC is running).</p><h3>Solve your N+1 problems II (Or: The other N+1 solutions don't help.  I need to give myself to the dark side)</h3><p>So, we've made use of the recommended <strong>RESTDataSource</strong> implementation that Apollo provides, which allows us to cache incoming data payloads from your underlying set of microservices.  Further, we've made sure that our UI use cases are operating on a 'get-only-what-I-need-right-now' basis so that they do not try to load/present too many document records at any one time.  </p><p>But...what about when, despite our best efforts to constrain use cases and utilize caching, we still cannot avoid the query that returns a (potentially large) collection of un-cacheable data? For instance, what if we were trying to present a report of live inventory data from our inventory system to our users? Or perhaps showing a list of oft-mutating data like alerts or notifications?  There are several cases like these in the Passkey universe that may require a second thought when it comes to caching as the answer for N+1.</p><p>So, what then? Shall we just concede the N+1 problem for these cases?  Or do we bypass our resolver-per-field pattern altogether?</p><p>Well, thankfully Apollo recommends another Data Source-friendly utility called <em><a href="https://github.com/graphql/dataloader">DataLoader</a></em>.  DataLoader can be used to accumulate a batch HTTP request (by a batch request, I don't mean 'a batch of many HTTP requests'.  I mean <em>one</em> HTTP request that is capable of providing a large, list-like responses based on a <em>set</em> of incoming request parameters).  This utility integrates nicely into the above proposed resolver pattern.</p><p><strong>Okay.  So then why are you calling this the dark side? Sounds like a Jedi mind trick to me.</strong></p><p>In short, DataLoader is a <em><u>final</u> - NOT first - consideration</em> in regards to performance sanity.  One <em>might</em> consider using bulk data loads in GraphQL to handle outstanding performance edge cases AFTER good use case management and RESTDataSource data source <em>have already been applied</em>.  But Bulk data loading as a standalone solution to performance improvement is going to introduce different types of potential performance problems, the solutions to which will have a profound impact on your GraphQL design (e.g. Rate limiting, HTTP request timeout issues, asynchronous responses, etc) as you scale your system to incorporate more data or longer datasets.</p><p>Further, the Apollo team itself does not recommend using a DataLoader where the requested data is <em>cacheable</em>, since the goal of caching is <em>re-use</em> and our cached values via a bulk load are only hit when another request with the exact same set of parameters (in the exact same order) is made.  Further, most of our REST APIs don't support batching, anyway, so unless you plan on writing your own batch endpoint, you're not going to be able to use DataLoader effectively.</p><p>If your data is cacheable, consider NOT using DataLoader and instead warming your cache immediately following startup so that your initial UI users do not have to absorb that impact in their experience.</p><p><strong>Last note on all of that</strong>: Keep in mind that the internet <em>sucks</em> at optimizing HTTP POST request performance. Before you make a decision to bypass normal RESTDataSource caching in favour of DataLoader, understand that this is more often than not going to be the wrong decision.  So, unless your use cases involve the handling of large quantities of live data at once, your use case is probably not that special.  You should really be using a cacheable, orthodox <em>RESTDataSources</em>-based data source instead of DataLoader, and finding other ways to improve performance.</p><ac:structured-macro ac:name="warning" ac:schema-version="1" ac:macro-id="38c32e39-35cc-4f90-a2da-6731c42caa20"><ac:rich-text-body><p>Consider DataLoader only in circumstances where your data is not cacheable, and where your UI is well-designed enough to address potential scalability concerns introduced by a bulk load.</p><p>In order to leverage a DataLoader in your use case, your underlying REST microservice API endpoints needs to support batching.  Most of our REST APIs DO NOT in fact support batching and so DataLoader will very useful in those cases.  If not integrated properly, DataLoader can introduce a new set of performance and scalability problems as you grow your system.  Always apply GraphQL best-practice approaches to query, schema, and resolver design, and don't use DataLoader where you do not need it.</p></ac:rich-text-body></ac:structured-macro><p><br /></p><ac:structured-macro ac:name="info" ac:schema-version="1" REST-based datasource involves a few mindset changes at the UI level<ul style="list-style-type: square;"><li>There is an <em>intentionally</em> high degree of coupling between data sources and UI components (less abstraction)</li><li>Creating re-usable components requires some extra consideration (e.g. GQL Fragment files)<ul style="list-style-type: square;"><li>Re-usability may not be practical where GQL is not used.</li><li>Abstracting GQL-awareness away from components that use data is NOT recommended!</li></ul></li></ul></li><li>How to optimize your UI:<ul style="list-style-type: square;"><li>Avoid bulk loads ('everything at once' queries)</li><li>Leverage concurrency (known as 'fetch-while-rendering' in React)</li><li>Break down traditional list results into multiple queries:<ul style="list-style-type: square;"><li>A query that returns a list of result identifiers (sorted, filtered)</li><li>Per-list-item queries that return data for a single result</li><li>Remember: High-resolution queries result in high cache reuse<ul style="list-style-type: square;"><li>Per list item caches means new searches with different filters will still leverage your cache.</li><li>Remember to keep list results paginated and size-managed in order to prevent overfetching</li></ul></li></ul></li></ul></li><li>Unblock your renders by decoupling high-impedance data from low-impedance data into separate non-blocking queries.<br /><ul style="list-style-type: square;"><li>Page renders are constrained only by the fastest-executing queries</li><li>Slower query executions can simply 'backfill' element contents on your already-rendered page (spinners/skeleton loaders are handy, here).</li><li>Avoid large list-driven queries that traverse multiple expensive portions of your graph at one time</li></ul></li></ul><p><strong>Tech Stack:</strong></p><ul style="list-style-type: square;"><li>It is possible to issue GQL queries via HTTP post (using your favorite fetch utility), but using the official apollo client <em>instead</em> is highly recommended for several reasons:<ul style="list-style-type: square;"><li>dev tool integration</li><li>built in cache</li><li>built-in provider &amp; utility integration</li></ul></li><li>Add the `@apollo/client` and `graphql` javascript libraries to your UI project dependency list.</li><li>Wrap your application with a provider for apollo-client called `&lt;ApolloProvider&gt;`.  This allows provider-compatible utilities to reference apollo clients implicitly from within your application components <em>without</em> having to add explicit client references to application state or your component properties.<ul style="list-style-type: square;"><li>NX typically provides new projects with the above configurations 'for free'.</li></ul></li><li>Fetch data that your components need using the 'useQuery() and useLazyQuery()' react hooks:<ul style="list-style-type: square;"><li><a href="https://www.apollographql.com/docs/react/data/queries/">https://www.apollographql.com/docs/react/data/queries/</a></li><li><a href="https://www.apollographql.com/docs/react/data/queries/#manual-execution-with-uselazyquery">https://www.apollographql.com/docs/react/data/queries/#manual-execution-with-uselazyquery</a></li></ul></li><li>Note: <strong>Avoid</strong> using HOC and component-driven apollo client utilities like (`&lt;Query&gt;` or `graphql()`).  These are deprecated in favor of React hook-based utilities.<ul style="list-style-type: square;"><li>If your project still utilizes out-moded class-based React components, you will be relegated to using one of the deprecated solutions above.  Strongly consider upgrading said components before attempting a GraphQL integration.</li></ul></li><li>Be mindful of the impact of asynchronous loading states and network status of your GQL queries on your component renders.<ul style="list-style-type: square;"><li>DON'T create render methods that simply assume that the data is already there!</li><li>Handle scenarios where expected data is not present gracefully. </li></ul></li></ul><p><strong>Configuration / Project Setup:</strong></p><ul style="list-style-type: square;"><li>Apollo client auth:<ul style="list-style-type: square;"><li>Typically, our production apollo services require clients to be authenticated with a valid auth token or API key. </li><li>Apollo clients should use ApolloLink infrastructure to automatically add an auth link to all subsequent queries invoked by that client<ul style="list-style-type: square;"><li>Docs: <a href="https://www.apollographql.com/docs/react/api/link/introduction">https://www.apollographql.com/docs/react/api/link/introduction</a></li><li>NOTE: Order matters.  Apollo Link is a linked list, so the auth link must be placed <em>before</em>  the http link<ul style="list-style-type: square;"><li>E.g.: `link<span style="letter-spacing: 0.0px;">: </span><span style="color: rgb(152,118,170);">from</span><span style="letter-spacing: 0.0px;">([errorLink</span><span style="color: rgb(204,120,50);">, </span><span style="letter-spacing: 0.0px;">authLink</span><span style="color: rgb(204,120,50);">, </span><span style="letter-spacing: 0.0px;">httpLink])`</span></li></ul></li></ul></li></ul></li><li>When creating the apollo client for your provider:<ul style="list-style-type: square;"><li>Configure cache merge algorithms to prevent cache overwrites.</li><li>Remember to enable `connectToDevTools` when in non-prod envs<ul style="list-style-type: square;"><li>NOTE: Getting apollo dev tools to show up in your browser can be a pain in non-local envs. See: <a href="https://github.com/apollographql/apollo-client-devtools/issues/213">https://github.com/apollographql/apollo-client-devtools/issues/213</a></li></ul></li></ul></li><li>Create helper files for storing queries and fragments<ul style="list-style-type: square;"><li>Create helper functions to produce variables objects for each query.</li></ul></li></ul><p><strong>Testing:</strong></p><ul style="list-style-type: square;"><li>For testing, use `&lt;MockedProvider&gt;` to wrap your tested GQL-enabled components.<ul style="list-style-type: square;"><li><a href="https://www.apollographql.com/docs/react/development-testing/testing/">https://www.apollographql.com/docs/react/development-testing/testing/</a></li><li>There are a few gotchas with this utility:</li><li>Bad setup/configuration of the mocked provider is a very easy situation to encounter, and feedback from the provider is often very poor at run time.  Please note the following:<ul style="list-style-type: square;"><li>In order to 'hit' a mocked response, the configured expected request and the actual request MUST MATCH EXACTLY.  The query must be the same, and the variables must be the same.  Variables may even need to be in the same <em>order</em> , depending on the version of the provider you are using.</li><li>Once the mocked provider uses a mock response to respond to a request, it cannot be used.  That bears repeating: MOCK RESPONSES CANNOT BE USED MORE THAN ONCE to respond to subsequent GQL queries, even if both queries exactly match the expected request.  To work around this limitation, you must add the same mock multiple times to your mock list for as many calls you intend to make for that data in your test.  <em>This means knowing the number of calls you need to make beforehand</em>.</li></ul></li></ul></li></ul><p><br /></p><h1>Part Three: Examples</h1><p>This section is for examples demonstrating the above best practices so that people can see how
