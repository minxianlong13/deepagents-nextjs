# Introduction and Disclaimer

STOP! This is not an intro course for GraphQL.  This document assumes beginner-level familiarity of GraphQL and some knowledge of GraphQL components.

The GraphQL Apollo server and corresponding GQL data access language is increasing in popularity across Cvent. Passkey products are no exception - it is an important enough piece of technology that our Techs Leads (including our architect) felt that we should create a knowledge base of best practices and general guidelines regarding GraphQL development.

As such, this document is a growing collection of idioms and tidbits that represent our fundamental understanding of the GraphQL approach to date.  These are not intended to be rules laid out in such a way that they cannot ever be broken, but they ARE precepts that should be well understood before making an _informed_ decision to stray away from them.

That said, we implore you to keep in mind that we (including the leads) are all still learning as we go and are yet discovering new, better ways to solve common problems.  Please consider this document to be a _starting place_ for understanding how to construct a well-designed GraphQL data layer.  The hope is that as better solutions to problems stated below are discovered, we can update this document to reflect new technologies and/or methodologies that we can apply in order to have the best-designed backend solution we can reasonably build.

# Part One: For Leads (Infrastructure and Modelling)

## Proverb I: O feckless vanity, why dost thou merely replicate thy REST services?

Summary

-   **GraphQL graphs are not simply propagated REST objects.**
-   **Don't use your Apollo server to relay data from your REST services 'as-is'.**
-   **Use data from your REST microservices to construct a graph that meets your application needs**

  

Read more...

This is heavy _meaning-of-life_ stuff to the GraphQL developer, and a good place to start.

GraphQL is not an arbitrary second layer of jam in your UI/Microservice/Database sandwich.  The purpose of GraphQL in any of our application stacks is to _provide application workflows with custom data views tuned for their specific use cases_.

As inexperienced GraphQL developers are still getting their sea legs, it can be very easy to misunderstand GraphQL early on as a glorified relay or proxy, configuring it to merely gatekeep the data supplied by your underlying REST data sources.  Such implementations merely proxy the flow of raw, siloed data to the client and are missing out on the most powerful querying features built into GraphQL.

[https://graphql.org/learn/thinking-in-graphs/#working-with-legacy-data](https://graphql.org/learn/thinking-in-graphs/#working-with-legacy-data)

If this describes you and your GraphQL implementation, then what you need to do is take the time to define a better _graph_.  Short of getting into a graphing tutorial here, A Passkey application graph model is typically going to be a **single graph** that _models relationships and unifies the output of its various microservices in the particular ways that the application in question wants to access the data (Side Note: Facebook actually utilizes a secondary graph - and a secondary endpoint - for admin fetches and mutations.  This seems like a good idea to me)._

With the model firmly in place, you can now formulate a diverse ecosystem of queries that leverage GraphQL's resolver mappings to provide the data (and data aggregates) that correspond to the selected fields.

## Proverb II: Let your graph embrace unity...but don't get _too_ unity

Summary

-   **Create graphs sparingly; Work towards graph unity, not graph disparity.**
-   **Attempting to federate all our data into a utopian single graph is not imminently realistic.**
-   **Apply the BFF (backend-for-frontend) pattern as a compromise.**

  

Read more...

The GraphQL team and their expert community have long promoted a 'unified graph' paradigm, encouraging all development teams within a single company to consolidate around a single graph model.  This is certainly a reasonable approach - particularly for _big data_ companies (who tend to utilize a more vertical data model at the core of their product lines, and narrow, horizontally-scalable infrastructure to service it) - but not all companies get to enjoy that same slim-jim model in the enterprise.  In Passkey, we have anything _but_ a vertical data model - dozens of Oracle schemas housing 100's of tables between them, and 40+ microservices to serve it all up...combine that with our other relevant data sources like DynamoDB and S3, and Passkey shows itself to be a very bottom-heavy architecture.  Attempting to implement a single graph across the passkey product line would require large-scale education, as well as integration, coordination and architectural pre-planning...that, or it would simply wind up being a sprawling, disorganized management nightmare.

So while it is unlikely we will approach the concept of a single, federated Passkey graph anytime soon, we should nonetheless be working towards single-graph models as best we can in the context of _any one application_.  On an application-by-application basis, this means, at the very least, unifying microservice data model requirements into a single application schema for that application.  This approach - know as the Backend-for-frontend (BFF) pattern - is a good fit for companies like ours having a very complex and service-rich backend architecture.

## Proverb III: Rome was not built in a day

Summary

-   **Architecture over-emphasis in your initial graph backend effort has been identified as a _known productivity impediment_.**
-   **Pick a couple of basic patterns and focus on those:**
    -   **Pre-consolidation: Build your Graph Model intact and un-fractured into a referential type hierarchy (like OOP HAS-A pattern).**
    -   **Separation-of-concerns: Partition the schema (separate model type definitions into files and directories).**
-   **Initial efforts should bias _adoption_ and _integration_ over regulatory adherence.**

  

Read more...

All I mean by this is: Don't let yourself become overwhelmed with DAL backend over-engineering at the expense of actual product integration:  One graph per application.  Model your schema like a OOP type hierarchy. Make meaningful relationships between microservice output objects.  That's it.

You can jump out on the interwebs and do a week's worth of blog reading about the best way to build a GraphQL backend.  Usually, these articles tend to introduce the designs that the author started out with but eventually outgrew, always crescendoing, it seems, to the pattern of _consolidation_.  Graph consolidation is the holy grail of GraphQL backend architecture.  Long story short, this pattern unifies the entire company into the single graph model, but partitions the schema types out as sub-graphs which can be managed by separate GraphQL servers and, in turn, separate development teams. The platform and specification that GraphQL provides the public to perform this evolution is called **Apollo Federation** ([https://www.apollographql.com/docs/federation/](https://www.apollographql.com/docs/federation/)).

But you may find it interesting that I'm not going to say a whole lot more about Apollo Federation or graph consolidation in this document.  So how d'ya like _them_ apples?

As it turns out, the Apollo team observes the most success amongst GraphQL adopters when they begin with something _other than_ graph consolidation.

For your reference:

**_At a fundamental level, a conversation about consolidation can begin as soon as it seems logical for multiple teams to manage different parts of the graph. While each company may have unique considerations in answering the question of when and how to consolidate, Apollo has recognized patterns of success and failure when making this shift._**

**_Historically at Apollo, we have seen that federation usually isn't a starting point for most enterprises in the early stages of adopting GraphQL._** \- [https://www.apollographql.com/docs/federation/enterprise-guide/graphql-consolidation/](https://www.apollographql.com/docs/federation/enterprise-guide/graphql-consolidation/)

The _patterns of success_ alluded to above are what that the Apollo Federation team refers to as _pre-consolidation_ patterns.  As luck would have it, the BFF pattern I discussed above falls into this group of patterns and fits very nicely with the way we have currently partitioned our Passkey products.  The BFF pattern is the way we should move forward with all current GraphQL implementations to ensure our success with it, following after the best advice out there given by the experts for GraphQL newcomers.

Putting it plainly, our _best_ GraphQL model will probably not be achievable until we are well past our initial attempts at GraphQL integrations.  Trying to circumvent the laws of evolution on a wing and a prayer is demonstrable folly.  Rather than focus on what we cannot yet do - it would be _really_ nice if we could instead focus on some of the other semantics described in this document that will help us in other practical ways to achieve actual integration.

## Proverb V: Queries shape your data, Schema shapes your relationships

Summary

-   **GQL has special data-shaping features you can use to profile query response data**
-   **GraphQL data relationships are always defined in the schema**
-   **GQL does _not_ support dynamic JOINs like SQL.**

  

Read more...

When it comes to your UI getting exactly what data it wants from GraphQL, think of client-side GQL queries like SQL queries without GROUP BY and JOIN: Using fragments, variables and directives, there is still a lot of data shaping power in GQL, and you should leverage those query features wherever practical.

One fundamental difference between GQL and SQL is that GQL relationships are always _declarative_, not _dynamic_.  This means that you design the relationships ('edges' in graph theory) between graph nodes in your _schema_, as opposed to dynamic linking in the query, a la SQL. Note that _GQL does not support JOIN statements, or anything much like it_.

**Aggregations**: If your UI requires a view of aggregate data, you need to consider the context of the request.  There are libraries available (e.g. dgraph) that will allow clients to request aggregate views over schema objects, but this approach would not be recommended with REST-backed datasources if the aggregation 'goes deep', or is simply attempting to aggregate a lot of data.  For those cases, we would consider actually modelling aggregation values into our schema and implementing an aggregation function in our underlying microservice so that aggregate values (rather than raw data) can be fetched by affected GraphQL field resolvers. This greatly reduces the HTTP transport overhead, serialization times and cache sizes.

This ability to recursively walk over a graph seems cool at first glance, but it can introduce some serious concerns around security and server performance, as well as some serious complexity to try and avoid them.

The take-home principle is: _our graph designs should not allow the same object to be referenced more than once in a single graph traversal_.

### How Do You Break the Cycle?

**Support only uni-directional graph traversals for any given query.**

1.  Is bidirectionality in your graph a product requirement?
    1.  If the ability to traverse the query in two different directions is not required, then you will simplify your graph (and its resolvers!) by excluding the unnecessary relationship.
2.  Break out cyclical references into separate wrappers that are independently queryable.  From the above example, we could break down the relational edges into new FamilyMembers 'connector' types that can be used by queries to enforce directionality.

With the above solution:

-   Your graph is still connected and integrated
-   The same data you otherwise wanted to be able to offer via the Bob object is still available; and
-   Clients are unable to indiscriminately traverse your graph.

  

**Use Apollo Server configurations to hard-limit your queries to some non-arbitrary maximum depth.**

Alternatively, if your graph use cases actually require the ability for clients to walk the graph simultaneously in both directions, then you can consider limiting the depth into which any one query can descend into your graph.  This is accomplished by using a Apollo server plugin.

-   The most oft-referenced query depth limiting plugin I've found on the interwebs is **graphql-query-depth**, but it appears to be abandoned.
-   Some newer docs instead point to a library of GQL security plugins called **graphql-armor**.  The query depth plugin is found here: [https://github.com/Escape-Technologies/graphql-armor#depth-limit](https://github.com/Escape-Technologies/graphql-armor#depth-limit)

  

  

  

## Proverb VII: GraphQL is optimized to supply 'per-scalar' resolvers wherever possible.

Summary

-   **Low-resolution data fetching should be avoided.**
-   **Avoid over-dependence on the default resolver.**
-   **Don't over-fetch in a resolver parent.**
-   **We should err on the side of resolver expressivity to avoid bad design during break-in period**

  

Read more...

This point is of particular importance to us (Passkey) precisely because we are layering GraphQL over _literally dozens_ of HTTP REST microservices.

There is a mechanism in Apollo Server that any GraphQL query execution will fall back on when there is _NO explicit resolver function_ defined for a particular schema field.  In such cases, GraphQL simply attempts to reconcile the schema field in question to the resolver's **parent** object (which is a special arg that is always passed in to all GraphQL resolver functions).

The mechanism which performs this implicit reconciliation is known as the _default resolver_.  In GraphQL, the approach where a parent object in a query resolver 'trickles' down the field data to its child fields via the default resolver is known as _type_\-level resolution.

Aside from its use as a fallback for GraphQL to present data whenever it possibly can, the default resolver is often leveraged by developers as a shorthand way to auto-map schema fields to values that have already been retrieved by a parent resolver - no explicit mapping required.

This is an obvious call to convenience, here - after all, what developer doesn't want to avoid boilerplate code - but the many experts who are posting their GraphQL examples and solutions on the interwebs _already know_ about the importance of 'bottom-up' resolver design at the field level.  There is a difference between understanding _how_ and _where_ type-level resolution does not hurt you in your specific model, and deciding not to declare field resolvers because nobody else seems to be doing it and you just want to make your code smaller.

As it turns out, indiscriminate use of the default resolver in any large graph is quite evil, and it will impose itself on our resolver design in very bad, un-performant, and/or un-scaleable ways when you do not understand the implications of model-induced over-fetching.  Low resolution fetching will typically result in fetching more data at one time, which is where the 'get-only-what-you-need' approach goes to die.  The remedy, then, is high-resolution fetching at the field level.

For this reason, I recommended that the whole Passkey dev team declaratively express their field-level resolvers for the time being, and **do NOT fall back on the default resolver** where at all possible.  In my opinion, this 'training' approach is how we will get developers to understand why field-level resolution is what makes this engine powerful, and why they should _want_  to do it.  Insofar that our devs do _NOT_ understand this principle and lean on type-level resolution in the resolver parent anyway, we will be that much more likely to incur over-fetching issues early on.

It is a lot easier to clean up an expressive resolver model than it is to refactor a bad design built on implicit _over-fetching_.  Once the team is up to speed on expectations around resolvers, we can rethink this approach and loosen our grip a bit.

As you move forward in field-level resolver design in Passkey's REST microservice-rich backend, you will very quickly take notice of some obvious performance-related considerations that, on their face, would appear to be 'show-stoppers' for an approach like this.  I encourage you to continue reading to understand how Apollo server provides the tools to allow us to get over various low-hanging performance talking points and stick with the intended program.

## Proverb IIX: Contextualization is key

Summary

-   **Optimize pain points in your graph in isolation (it's okay for your Graph to be asymmetric or 'funny-shaped').**
-   **Don't presume performance problems to necessarily be the fault of the backend.**
-   **Double-check requirements for unrefined or purpose-less use cases that carry performance expectations.**
-   **Don't pre-emptively sell out scalability and conformity for cheap performance gains.**

  

Read more...

For any given use case of your application, your solution requirements will bring with them a specific set of needs in regards to the feature set.  These requirements will inform your GraphQL query and schema design in very obvious and elementary ways that we needn't talk about here.

At the same time, there are GraphQL query considerations - such as load management, scalability and performance - that must likewise be acknowledged and reflected in any target GraphQL client.   Do not build all aspects of your application's graph model to be the same. Your GraphQL model should not merely be a perfect reflection of your low-level data sources, OR as a one-stop shop that must be equally capable of doing _everything_.  A well-built graph model will be _dynamic_ and _asymmetric_ - differently-shaped in its various surface areas because fundamental requirements of your application have dictated the profile of the model.  For graph-based applications, it is an advisable trade-off to specialize parts of your graph to be good at one important thing at the expense of some other less important function.  Start by asking some basic questions in the design phase of your project to gain contextual insight into the various parts of your graph:

1.  **Is the graph model I've constructed for my product appropriate?**  In other words, are my queries simple or complicated (hint: avoid complicated GraphQL resolvers)? Ideally in any graph, you want to minimize the number of edges that must be traversed in order to produce the desired output for your particular use case(s).  For instance, let's say your application Graph model as currently designed is made up of raw user profile data.  Your UI use case appears to call for mostly aggregate user data based on profile categories.  Is there any way to simplify/reduce this part of your model so that aggregate views and values are more accessible, more easily cached, and more quickly retrieved?
2.  **Are use case expectations appropriate?**  UI designs often lend themselves to bad assumptions about how users will actually engage the data.  Don't assume or implicitly agree to requirements that impose immediate performance/scalability concerns when the use case has not yet been reasoned to be useful and/or purposeful.  For instance, a common anti-pattern that used to plague older web UIs was a bias for the premature presentation of list data.  It was assumed by some search-oriented interfaces that users should be presented with data immediately, and then supply filter values to hone in on what they wanted to see.  However, this presented a very expensive and data-heavy operation at the onset of the user experience.  Was it really necessary to do the work of fetching and organizing the entire firehose of data for all users, for every visit?  Is such a view even useful?  These are questions that we should have been asking at the time, yet only a few were doing it.  We can't change the past, but perhaps you can avoid the work of having to performance-optimize GraphQL queries that users shouldn't even be using. 
3.  **Is my resolver design appropriate?** If you are abiding by best practices, this is the last question to ask, not the first (read the sections below to find out how to have the best of both worlds inside the boundaries of proper, supported GraphQL integration and good resolver design).  Attempts to compensate for performance problems by pre-emptively de-constructing your resolver model in favour of custom low-resolution batch/bulk fetching is very likely to hurt your UI's ability to scale up to large datasets without issues (HTTP timeout problems and cache ineffectiveness, to name two).

## Proverb IX: Do not desecrate the Context object, for it is sacred

Summary

-   **The GraphQL _context_ object, while visible to all your resolvers, should not be modified.**

  

Read more...

Common to every query execution is the GraphQL **context** object that gets passed down through the entire resolver chain.  As the same instance of the context persists for the entire duration of query and is visible to all query frames, the temptation to use it as a means to supply custom data back and forth between resolvers can be quite strong.  Avoid this - context mutation produces implicit dependencies on state that make your resolvers harder to understand and harder to re-use.

The context object is for _request_ context that is calculated at the start of a request.  It is NOT for accumulating session information _during_ traversal, or for sending signals from one resolver to another in order to get them to do something special.  _You've been warned: You can look, but you can't touch.  if you write context-mutating resolvers, you will eventually wreck your application_.

In cases where you need data to 'trickle down' from one resolver to another, remember that the output object(s) of a parent resolver becomes the parent object for all immediate child resolvers.  This means you can share data from a parent resolver to a child resolver by incorporating the value into the parent object.  Use this to your advantage.  

Something else that can help here is _field-level arguments_.  If you have two resolvers in a resolver chain that are dependent on the same user-provided data, you should consider updating your model so that _both_ fields/resolvers will inherit the argument value via field-level args.

## Proverb X: GraphQL != REST

  

Summary

-   **Modelling dissimilarities between REST and GraphQL have been discussed in the first section of this document.**
-   **The rigid contract-based REST principles are loosened in GraphQL, particularly when the client is a UI front end.**
    -   **Not every error is a blocking error! Know when to absorb UI impact of an unimportant error.**
    -   **Contextualize errors by embedding them in appropriate places in your response (rather than report them separately)**

  

Read more...

It is important to know that aside from the modelling principles identified above, there are specific semantical constraints that apply to REST endpoints that should not be propagated into your GraphQL queries.  GraphQL has its own unique error and edge case handling features that should not be bypassed for the sake of propagating REST errors to the client.

Simply put, coming to GraphQL from the area of Microservice development, we might incur unconscious bias towards treating our GraphQL response like REST endpoint responses.  But the point of your GraphQL response in the context of a UI is to _elevate the UI experience_ and make things as comfortable as possible - not to interrupt users with interfering popups and their error codes that users can't do anything about, anyway.

The best practice in GraphQL is to absorb the error into the workflow as best as possible.  Don't make blocking problems out of non-blocking problems.  If there's something that needs to be communicated to the user, integrate your error into your response data so that the UI doesn't need a lot of error handling code to handle user-feedback error cases.  More on this in the _Proverbs that are not proverbs_ section below.

For example, let's say a UI has requested info cards for ten doctors.  The data for nine of those cards were retrieved without issue, while one of them suffered a _not found_ HTTP error during one of the supplemental catalog data lookups that occurred on a backend microservice.  By convention in REST, we do not return a 200 (OK) response unless we have satisfied the directives of the request, so we typically respond in such cases with a 404 not found HTTP code, or perhaps a 500 ISE, depending on our error propagation policy.

But once that error has propagated to your GraphQL service, you might (and often should) handle the situation in a different way.  This becomes a large conversation, but here's a couple of basic principles:

1.  Don't block the entire response with an error code if the error itself is not implicitly blocking in nature.
2.  Don't place non-blocking errors in the 'errors' payload of the GQL result.  This forces the UI to 'stop the world' - conditionlessly block, parse and handle all 'errors' content since the UI can not tell whether or not they are important or urgent without doing that.
3.  Global errors and/or user-blocking errors that have no data context (Permission Denied, for instance) can be added to the 'errors' GQL response object so that the UI code can take appropriate action.
4.  In many - even most - cases, data-specific errors can be integrated into your 'data' response object so that errors show up as placeholders in your response where the expected data would have otherwise been.  In this case, the particular component(s) that handle the erroneous data element can decide what they want to do with it.
    1.  Boris has excellent documentation about how to do that here: 
    2.  The evolution of this solution (and why it is superior to using the 'errors' element) can be found here: [https://blog.logrocket.com/handling-graphql-errors-like-a-champ-with-unions-and-interfaces/](https://blog.logrocket.com/handling-graphql-errors-like-a-champ-with-unions-and-interfaces/)

  

If an error raised in your resolver can be encountered during orthodox, reasonable use of your application, you should consider absorbing the impact of the error somewhere in your workflow in a way that reduces the impact to the user experience in whatever reasonable ways.  Here, it's important to note that _non-existent data is not necessarily an error condition in GraphQL_.  If you Apollo server attempt to fetch some data that could not be found by a microservice (HTTP 404), consider whether or not the user can press on in a normal fashion without it.  If they can, you would be well advised to handle these errors strictly on the server side (logging, alerting auditing, etc) and let the UI resume business as usual.

Remember to focus your graceful, 'white glove' error handling at UI end-users who are playing by the rules.  Errors that are produced by exploitative or unsupported use of your application do not require the extra effort of elegance and can be a more primitive experience.  Whatever the case, just be sure to handle it in a way that _protects the system_ and _does not reward malicious users_.

## Proverb XI: Proverbs That Are Not Proverbs

In order to not diverge away from best-practice expectations, it is highly recommended that you apply the solutions specified below.

### What is the Field Resolver Pattern?

The idea that each field in your schema has a de-facto resolver that can and should be customized in order to be independent and agnostic of the resolver above it in the resolver chain.

-   This pattern is intended to defer the lazy-loading of cacheable data until the last moment we know it is required: the field level.
-   It maximizes the re-usability of cached data
-   It maximizes the flexibility and cohesion of your schema and introduces patterned resolver re-use
-   Makes it easier to reason about your query resolvers (which are otherwise more complicated)
-   It maximally reduces over-fetching of data from your data sources
-   Anywhere a field does NOT utilize a custom field resolver, [a default resolver](https://www.apollographql.com/docs/apollo-server/data/resolvers/#default-resolvers) is invoked in its place.  Ergo,
    -   Anywhere a field does NOT utilize a custom field resolver, that field has an implicit dependency on its parent query to supply that value
    -   Any new query written to supply an object of any type must therefore supply any field value of that type that is dependent on the default resolver.
-   Not particularly well documented, but the field resolver approach is the only way to achieve truly arbitrary Graph traversals.
-   At Paypal: [https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55](https://medium.com/paypal-tech/graphql-resolvers-best-practices-cd36fdbcef55)
-   At LogRocket: [https://blog.logrocket.com/properly-designed-graphql-resolvers/](https://blog.logrocket.com/properly-designed-graphql-resolvers/)

### Solve duplication-of-request problems with RESTDataSource

Passkey's microservice-rich backend requires some special consideration when constructing a GraphQL layer for our applications.

The inherent problem with out-of-the-box microservice integrations into your GraphQL resolvers is the problem of _duplicity_.  If you've read the sections above, you know that we have already evangelized the importance of _field-level_ - rather than type-level - resolvers.  By convention, resolver stacks for your queries should have the highest resolution possible so that they are not making extra round-trips to your microservices for data that was not actually requested - over-fetching.

But - and now let's address the elephant in the room - if I have field level resolvers that are each making their own microservice request to fetch field data...isn't that just as bad or worse as over-fetching?  Why should I create three resolvers (for instance) that make three identical requests to fetch three fields on the same object that I can easily fetch in a single request if I just move the request to the parent?

And the answer is: because of an important API that GraphQL has built called _Data Sources_.

Data Sources are sub-resolver components (resolvers use data sources, not the other way around) that provide a layer of **memoization** and **de-duplication** between GraphQL resolvers and our microservice-based DAL.  Utilizing a data source allows developers to not compromise on performance, request duplicity and scalability concerns while maintaining best-practice, per-field resolver patterns.

Of particular note, we will focus here on a specific DataSource implementation called **RESTDataSource**, as this is the abstract data source that GraphQL provides for microservice integrations.  [https://github.com/apollographql/apollo-server/blob/main/packages/apollo-datasource-rest/src/RESTDataSource.ts](https://github.com/apollographql/apollo-server/blob/main/packages/apollo-datasource-rest/src/RESTDataSource.ts)

#### What is memoization?

**Memoization** in GraphQL Data Sources is the ability to temporarily store a result (or the _Promise_ of the result) of some previously executed operation so that subsequent operations invoked by the same request requiring the same result will share the original result, rather than invoke their own additional operations.

What this means for us is that a request's data source instance (which are unique per request) will track the invocations of its API methods from the moment they are invoked until the moment the request is fulfilled.  Within that time, any additional API calls for the same data (in this case, additional calls to MyObjectAPI.getMyObject() with the same arg values) will _use the result returned by the first API call_, OR, if the call is not yet completed, will wait for the fulfilled Promise on that same call.

So, we can call ctx.dataSources.myObjectApi.getMyObject() in the same request - even in the same _frame_  - dozens of times, but the outbound request will only ever be made once.  This prevention of multiple, concurrent outbound calls is called _de-duplication_.

#### Which Datasource should I use?

There are two Datasource implementations mentioned in Apollo docs for microservice-sourced graphs: **RESTDataSource** and **HTTPDataSource**.  We used RESTDataSource already in our examples above, but what about HTTPDataSource?

In short, _don't use it_.

-   RESTDataSource has a properly-implemented memoization solution, whereas HTTPDataSource is considerably lacking in this department.
-   RESTDataSource is receiving regular maintenance updates.
-   Node object creation can quickly become a performance issue in HTTPDataSource implementations (which initiates duplicitous object reconstruction each time an API method is called in a resolver chain).
-   As of Feb 2023, HTTPDataSource Github has not merged a new PR in about 7 months (the last non-maintenance PRs occurred around the time of the original writing of this doc).  I wouldn't call this library abandoned yet, but it is not very active and is not well supported lately.
-   HTTPDataSource has no support for the new Apollo V4 package management yet, which is increasingly imminent in our NX upgrade path.

**Data source caching**

You are highly encouraged to design your GraphQL resolvers around the use of Data Sources - specifically of note for us, the **RESTDataSource** library is offered by GraphQL out of box.

Data sources apply server-side, or _microservice-facing_, caching of data that has been retrieved from microservice endpoints so that MS endpoints do not need to be redundantly queried for the same data over and over again merely because multiple clients are accessing it.  Caches are configurable, and you can tune your data source's cache on a case-by-case basis to correlate with expectations regarding the frequency of changes (in short, the longer the expected timeframe between updates to the data in question, the longer the data itself can be cached).

On the data source side, cache entries are keyed according to the complete URL (including query params) by default.  This is typically adequate, although it can be overridden with a RESTDataSource-provided hook called **cacheKeyFor()**.  For instance, if you are leveraging a HTTP POST endpoint to perform a search using a provided request payload, you will likely want to override the default cache key to incorporate request payload values.

_I recommend **sorting** the request body prior to sending the request (to remove out-of-order misses and maximize cache hits), and then using the **[object-hash](https://github.com/puleos/object-hash)** library to create a unique SHA1 or MD5 cache key for your request object._

**Object Creation Reduction**

Be aware of Node object creation behaviour in your frequently-accessed code!  Note that library-level methods (including Data Source APIs!) that get invoked over and over again should avoid creating new objects - implicitly or explicitly.  Object creation under high load scenarios will have a significant impact on your Apollo server's ability to respond to requests in a timely manner (single-threaded NodeJS can't respond to _anything_ while its GC is running).

### Solve your N+1 problems II (Or: The other N+1 solutions don't help.  I need to give myself to the dark side)

So, we've made use of the recommended **RESTDataSource** implementation that Apollo provides, which allows us to cache incoming data payloads from your underlying set of microservices.  Further, we've made sure that our UI use cases are operating on a 'get-only-what-I-need-right-now' basis so that they do not try to load/present too many document records at any one time.  

But...what about when, despite our best efforts to constrain use cases and utilize caching, we still cannot avoid the query that returns a (potentially large) collection of un-cacheable data? For instance, what if we were trying to present a report of live inventory data from our inventory system to our users? Or perhaps showing a list of oft-mutating data like alerts or notifications?  There are several cases like these in the Passkey universe that may require a second thought when it comes to caching as the answer for N+1.

So, what then? Shall we just concede the N+1 problem for these cases?  Or do we bypass our resolver-per-field pattern altogether?

Well, thankfully Apollo recommends another Data Source-friendly utility called _[DataLoader](https://github.com/graphql/dataloader)_.  DataLoader can be used to accumulate a batch HTTP request (by a batch request, I don't mean 'a batch of many HTTP requests'.  I mean _one_ HTTP request that is capable of providing a large, list-like responses based on a _set_ of incoming request parameters).  This utility integrates nicely into the above proposed resolver pattern.

**Okay.  So then why are you calling this the dark side? Sounds like a Jedi mind trick to me.**

In short, DataLoader is a _final - NOT first - consideration_ in regards to performance sanity.  One _might_ consider using bulk data loads in GraphQL to handle outstanding performance edge cases AFTER good use case management and RESTDataSource data source _have already been applied_.  But Bulk data loading as a standalone solution to performance improvement is going to introduce different types of potential performance problems, the solutions to which will have a profound impact on your GraphQL design (e.g. Rate limiting, HTTP request timeout issues, asynchronous responses, etc) as you scale your system to incorporate more data or longer datasets.

Further, the Apollo team itself does not recommend using a DataLoader where the requested data is _cacheable_, since the goal of caching is _re-use_ and our cached values via a bulk load are only hit when another request with the exact same set of parameters (in the exact same order) is made.  Further, most of our REST APIs don't support batching, anyway, so unless you plan on writing your own batch endpoint, you're not going to be able to use DataLoader effectively.

If your data is cacheable, consider NOT using DataLoader and instead warming your cache immediately following startup so that your initial UI users do not have to absorb that impact in their experience.

**Last note on all of that**: Keep in mind that the internet _sucks_ at optimizing HTTP POST request performance. Before you make a decision to bypass normal RESTDataSource caching in favour of DataLoader, understand that this is more often than not going to be the wrong decision.  So, unless your use cases involve the handling of large quantities of live data at once, your use case is probably not that special.  You should really be using a cacheable, orthodox _RESTDataSources_\-based data source instead of DataLoader, and finding other ways to improve performance.

Consider DataLoader only in circumstances where your data is not cacheable, and where your UI is well-designed enough to address potential scalability concerns introduced by a bulk load.

In order to leverage a DataLoader in your use case, your underlying REST microservice API endpoints needs to support batching.  Most of our REST APIs DO NOT in fact support batching and so DataLoader will very useful in those cases.  If not integrated properly, DataLoader can introduce a new set of performance and scalability problems as you grow your system.  Always apply GraphQL best-practice approaches to query, schema, and resolver design, and don't use DataLoader where you do not need it.

### Using the GraphQL Apollo Client Appropriately: How can I set up my project to use Apollo for component data?

This question breaks down into a few topics.  We'll try to tackle them briefly here.

**Mindset and design:**

-   Migrating to GraphQL from traditional REST-based datasource involves a few mindset changes at the UI level
    -   There is an _intentionally_ high degree of coupling between data sources and UI components (less abstraction)
    -   Creating re-usable components requires some extra consideration (e.g. GQL Fragment files)
        -   Re-usability may not be practical where GQL is not used.
        -   Abstracting GQL-awareness away from components that use data is NOT recommended!
-   How to optimize your UI:
    -   Avoid bulk loads ('everything at once' queries)
    -   Leverage concurrency (known as 'fetch-while-rendering' in React)
    -   Break down traditional list results into multiple queries:
        -   A query that returns a list of result identifiers (sorted, filtered)
        -   Per-list-item queries that return data for a single result
        -   Remember: High-resolution queries result in high cache reuse
            -   Per list item caches means new searches with different filters will still leverage your cache.
            -   Remember to keep list results paginated and size-managed in order to prevent overfetching
-   Unblock your renders by decoupling high-impedance data from low-impedance data into separate non-blocking queries.  
    -   Page renders are constrained only by the fastest-executing queries
    -   Slower query executions can simply 'backfill' element contents on your already-rendered page (spinners/skeleton loaders are handy, here).
    -   Avoid large list-driven queries that traverse multiple expensive portions of your graph at one time

**Tech Stack:**

-   It is possible to issue GQL queries via HTTP post (using your favorite fetch utility), but using the official apollo client _instead_ is highly recommended for several reasons:
    -   dev tool integration
    -   built in cache
    -   built-in provider & utility integration
-   Add the \`@apollo/client\` and \`graphql\` javascript libraries to your UI project dependency list.
-   Wrap your application with a provider for apollo-client called \`<ApolloProvider>\`.  This allows provider-compatible utilities to reference apollo clients implicitly from within your application components _without_ having to add explicit client references to application state or your component properties.
    -   NX typically provides new projects with the above configurations 'for free'.
-   Fetch data that your components need using the 'useQuery() and useLazyQuery()' react hooks:
    -   [https://www.apollographql.com/docs/react/data/queries/](https://www.apollographql.com/docs/react/data/queries/)
    -   [https://www.apollographql.com/docs/react/data/queries/#manual-execution-with-uselazyquery](https://www.apollographql.com/docs/react/data/queries/#manual-execution-with-uselazyquery)
-   Note: **Avoid** using HOC and component-driven apollo client utilities like (\`<Query>\` or \`graphql()\`).  These are deprecated in favor of React hook-based utilities.
    -   If your project still utilizes out-moded class-based React components, you will be relegated to using one of the deprecated solutions above.  Strongly consider upgrading said components before attempting a GraphQL integration.
-   Be mindful of the impact of asynchronous loading states and network status of your GQL queries on your component renders.
    -   DON'T create render methods that simply assume that the data is already there!
    -   Handle scenarios where expected data is not present gracefully. 

**Configuration / Project Setup:**

-   Apollo client auth:
    -   Typically, our production apollo services require clients to be authenticated with a valid auth token or API key. 
    -   Apollo clients should use ApolloLink infrastructure to automatically add an auth link to all subsequent queries invoked by that client
        -   Docs: [https://www.apollographql.com/docs/react/api/link/introduction](https://www.apollographql.com/docs/react/api/link/introduction)
        -   NOTE: Order matters.  Apollo Link is a linked list, so the auth link must be placed _before_  the http link
            -   E.g.: \`link: from(\[errorLink, authLink, httpLink\])\`
-   When creating the apollo client for your provider:
    -   Configure cache merge algorithms to prevent cache overwrites.
    -   Remember to enable \`connectToDevTools\` when in non-prod envs
        -   NOTE: Getting apollo dev tools to show up in your browser can be a pain in non-local envs. See: [https://github.com/apollographql/apollo-client-devtools/issues/213](https://github.com/apollographql/apollo-client-devtools/issues/213)
-   Create helper files for storing queries and fragments
    -   Create helper functions to produce variables objects for each query.

**Testing:**

-   For testing, use \`<MockedProvider>\` to wrap your tested GQL-enabled components.
    -   [https://www.apollographql.com/docs/react/development-testing/testing/](https://www.apollographql.com/docs/react/development-testing/testing/)
    -   There are a few gotchas with this utility:
    -   Bad setup/configuration of the mocked provider is a very easy situation to encounter, and feedback from the provider is often very poor at run time.  Please note the following:
        -   In order to 'hit' a mocked response, the configured expected request and the actual request MUST MATCH EXACTLY.  The query must be the same, and the variables must be the same.  Variables may even need to be in the same _order_ , depending on the version of the provider you are using.
        -   Once the mocked provider uses a mock response to respond to a request, it cannot be used.  That bears repeating: MOCK RESPONSES CANNOT BE USED MORE THAN ONCE to respond to subsequent GQL queries, even if both queries exactly match the expected request.  To work around this limitation, you must add the same mock multiple times to your mock list for as many calls you intend to make for that data in your test.  _This means knowing the number of calls you need to make beforehand_.
