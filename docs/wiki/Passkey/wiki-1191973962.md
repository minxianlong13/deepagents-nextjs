# 1\. Purpose

Create a Room Blocks neighborhood destination in Cvent Planner Portal. Authorized Core Event users can view the room-block state, link an eligible organization-owned Passkey room block, see unprivileged room-block insights, and navigate to Passkey.

This document is intentionally architectural. Endpoint names, payloads, concrete service ownership, persistence location, and authorization contracts remain LLD decisions.

# 2\. Product constraints that drive the design

-   Epic 1 is limited to Core accounts confirmed as Passkey license holders through account mapping. ([GROUP-127468](https://jira.cvent.com/browse/GROUP-127468), [requirements](https://wiki.cvent.com/spaces/PASKY/pages/1177698549/Passkey+Bridge+Page+for+Passkey+License+Holders))
-   A Core user with [View or Create Event permission](https://wiki.cvent.com/spaces/PASKY/pages/1177698549/Passkey+Bridge+Page+for+Passkey+License+Holders) can view the page and link an organization-owned room block. The user does not need to be a Passkey user or a MyCvent-linked user to do those account-scoped actions.
-   The page must reflect a linkage made from Travel, and Travel must reflect a linkage made from the bridge page. ([requirements](https://wiki.cvent.com/spaces/PASKY/pages/1177698549/Passkey+Bridge+Page+for+Passkey+License+Holders))
-   Post-linkage insights must be real-time and unprivileged. No reservation-level data or PII is displayed. ([requirements](https://wiki.cvent.com/spaces/PASKY/pages/1177698549/Passkey+Bridge+Page+for+Passkey+License+Holders))
-   Optional Registration integration enables Passkey RegLink and configures Cvent Travel only when account, event, and user permissions allow it. ([requirements](https://wiki.cvent.com/spaces/PASKY/pages/1177698549/Passkey+Bridge+Page+for+Passkey+License+Holders))
-   Epic 2 must support hotel/TPP-owned blocks, Planner Portal assignment by user email, and connection-code-based authorization without redesigning the page or mapping model. ([requirements](https://wiki.cvent.com/spaces/PASKY/pages/1177698549/Passkey+Bridge+Page+for+Passkey+License+Holders), [phase scope](https://wiki.cvent.com/spaces/PASKY/pages/1106609325/Neighborhoods+-+Passkey+Room+Block+Bridge+Page))

The requirements describe Account Mapping ID as the link between a Core account and a Passkey participant. A Passkey participant is an organization or hotel entity, not a user. [Neighborhoods requirements](https://wiki.cvent.com/spaces/PASKY/pages/1106609325/Neighborhoods+-+Passkey+Room+Block+Bridge+Page)

# 3\. Proposed Architecture

Build a new CDF planner web application, referred to here as `passkey-room-blocks-bridge`, deployed in the Cvent Planner Portal domain and registered as the Room Blocks neighborhood destination.

The app contains:

-   Browser UI: renders the bridge states and calls only its same-origin BFF/GraphQL facade.
-   Server-side BFF: validates the Core session, gets trusted event/account/permission context, orchestrates Cvent and Passkey calls, and applies policy.
-   Optional GraphQL facade: a good transport choice inside the app because it composes view-specific data. It is not the architectural boundary. The BFF/service layer remains the cross-product boundary.

This follows the core security property in the Jifflenow bridge-page pattern: a CDF planner application acts as the BFF. Cross-product credentials do not reach the browser. [Jifflenow technical design](https://wiki.cvent.com/spaces/Eng2/pages/1169371521/Technical+Design+Jifflenow+Bridge+Page+Integration)

### Record A: Cvent event-data integration record

Record A is the authoritative Cvent record for the Cvent Event ↔ external-resource relationship. Its current schema is confirmed by the event-data create, patch, and read-model definitions.

Field

Record A definition

`integrationId`

System-generated UUID. Read-only unique record ID; store it as Record B's foreign key. This will be the PK and SK.

`eventId`

Read-only UUID for the current Core event; supplied by the event URL path.

`accountId`

Read-only UUID for the Core account that owns the event.

`product`

Required at creation. Use `passkey`; it is the first immutable routing-key segment.

`id`

Required at creation. Use the Passkey event or room-block identifier; it is the second immutable routing-key segment.

`type`

Optional resource classification, such as `ROOM_BLOCK`. Mutable; pass `null` in a patch request to clear it.

`metadata`

Optional lightweight UI-assisting context: arbitrary product-defined string-to-string pairs. event-data does not interpret it. A patch replaces the whole object; `null` clears it. Never store credentials or PII.

Read-only Cvent planner user ID that created the record.

`configuredAt`

Read-only creation timestamp.

`updatedAt`

Read-only timestamp of the most recent update.

The `product` and `id` routing-key fields are immutable after creation. `type` and `metadata` are the only fields supported by the current patch contract. Record A does not define `linkStatus` or `source`; unlink is represented by deleting the integration record rather than changing an in-record lifecycle status.

The decorator service exposes idempotent create, read by `integrationId`, state update by `integrationId`, and hard delete operations. Record B is hard-deleted for rollback, unlink, and lazy orphan cleanup.

### Creation sequence

The BFF owns a sequenced, compensating saga—not a distributed transaction:

1.  Validate Core event eligibility and IMS account mapping.
2.  Create Record A through the authorized Cvent integration-write path.
3.  Create Record B in `passkey-event-sb` using Record A's returned `integrationId`.
4.  Return linked state only after both writes succeed.

The operation is idempotent; duplicate or concurrent requests must not create a second link. If Record B creation fails, delete Record A as compensating rollback. If Record A is unavailable, return a meaningful error without creating an orphan.

### Unlink and orphan handling

The BFF validates the requested `integrationId`, deletes Record A through the authorized Cvent integration-write path, then hard-deletes Record B. If Record A is already absent, the BFF treats Record B as an orphan and hard-deletes it during the unlink flow. If Record A deletion succeeds but Record B deletion fails, log the failure for observability. Periodic reconciliation remains deferred.

### Deletion of Passkey Records

We need to determine which of the two flows we want to use for setting the TTL of our DynamoDB records.

1.  Set a TTL during record creation that is X amount of time after the close date of the Cvent or Passkey event. Discuss with the product team during implementation.
2.  Hook into the delete flow of the Cvent event-data service to cleanup passkey related records.

# 7\. Key sequences

## Sequence A: open the bridge page and load state

\>UI: Open Room Blocks neighborhood for coreEventId UI->>BFF: GET bridge-state(coreEventId) BFF->>Core: Validate Core session and Event View/Create permission Core-->>BFF: platformUserId, coreAccountId, event context, permissions BFF->>Store: Read existing Passkey link for coreEventId Store-->>BFF: Link or no link alt No link BFF->>IMS: Resolve Core account mapping IMS-->>BFF: mapped PASSKEY\_ORG participant(s) or none BFF-->>UI: Unlinked state + eligibility + allowed actions else Link exists BFF->>PK: Get unprivileged room-block summary and insights(linked passkeyEventId) PK-->>BFF: Name, dates, location, metrics, booking URL, allowed actions BFF-->>UI: Linked state + insights + navigation actions end \]\]>

Notes:

-   The unlinked page can render educational content before eligibility is confirmed. But the link CTA should be policy-gated according to the product decision.
-   Do not use a Passkey user session to authorize unprivileged insights. The Core event permission plus an existing link is the authorization path. A service-to-service token fetches the insights (no MyCvent linkage required).
-   The BFF should return explicit, non-sensitive state codes: `NOT_ELIGIBLE`, `NO_MAPPING`, `NO_LINK`, `LINKED`, `RESTRICTED`, `DEPENDENCY_UNAVAILABLE`.

## Sequence B: discover, select and link an organization-owned room block

\>UI: Select existing room block to link UI->>BFF: Search candidates for coreEventId BFF->>Core: Revalidate event permissions and load dates/name/account Core-->>BFF: Authorized event context BFF->>IMS: Resolve mapped PASSKEY\_ORG participant IMS-->>BFF: participantIds BFF->>PK: Search Pre-Open or Open events by participantIds and dates PK-->>BFF: Candidate room blocks with ownership metadata BFF-->>UI: Suggested/search results U->>UI: Select candidate and choose optional Reg integration UI->>BFF: Create link for candidateId BFF->>Core: Validate linkability and Travel prerequisites alt Reg integration requested and allowed BFF->>RL: Enable/validate RegLink for Passkey event RL-->>BFF: Ready BFF->>Core: Enable/configure Travel two-way Passkey integration Core-->>BFF: Configured else Reg integration unavailable or not requested Note over BFF,Core: Persist only room-block linkage end BFF->>Store: Create Cvent link record Store-->>BFF: cventLinkId BFF->>PK: Create Passkey decorator with cventLinkId and regIntegrationState PK-->>BFF: Decorator persisted Note over BFF,PK: On failure - rollback Cvent link. Decorator is orphan-safe. BFF-->>UI: Linked state \]\]>

Failure semantics to settle in LLD:

-   Treat the optional RegLink/Travel setup as an explicit workflow with compensating behavior. The exact transactional boundary is not yet known.
-   Prefer persist-link-last when the business rule requires a fully connected Registration integration. Otherwise persist the room-block link with a truthful `regIntegrationState` such as `NOT_REQUESTED`, `UNAVAILABLE`, `FAILED`, or `CONNECTED`.
-   Use idempotency keys and an integration-record version to prevent double linking from retries or concurrent Travel actions.

## Sequence C: Travel-originated change and Passkey deep link

\>Travel: Link, change or unlink Passkey event Travel->>Core: Apply Travel workflow Core->>Store: Create/update/delete canonical link Store-->>Core: Current version/state U->>UI: Refresh/open Room Blocks page UI->>BFF: GET bridge-state(coreEventId) BFF->>Store: Read canonical link Store-->>BFF: Current Travel-originated state BFF-->>UI: Render same linked/unlinked state U->>UI: Open in Passkey / Planner Portal UI->>BFF: Request deep link(linked passkeyEventId, target) BFF->>SSO: Establish/verify user-level MyCvent/Passkey SSO alt User authorized for linked event SSO-->>BFF: Scoped deep-link URL BFF-->>UI: One-time navigation URL UI->>PK: Open new tab else User lacks user-level Passkey access SSO-->>BFF: Fallback or authentication-required outcome BFF-->>UI: Explain and offer permitted destination end \]\]>

The deep link is intentionally a separate, user-level authorization path. An account-authorized Core user can see unprivileged metrics and link an owned room block. But they may still lack the personal Passkey identity or role needed to open the same event in Manage or Planner Portal.

## Security controls

-   Validate the Core session and event permission on every BFF request. Never accept event/account/participant IDs from the browser as authority. Also re-validate the Events cookie on every request (not just on initial auth handshake) to detect logout or token revocation before forwarding to Passkey.
-   Keep API keys, service credentials, token-exchange responses and Passkey scoped tokens server-side.
-   Query the smallest Passkey projection needed. Do not proxy broad Planner Portal APIs or reservation data.
-   Log correlation IDs, event IDs, participant IDs and outcome codes. Redact authorization headers, tokens, booking/customer PII and deep-link URLs.
-   Use a server-side entitlement/feature flag keyed by the Core account (and rollout cohort) for Epic 1.
-   Threat-model cross-account access, stale IMS mappings, a changed link while displayed, and privilege differences between Core and Passkey.

## DD-3: Cross-realm auth design (3–4 days) [GROUP-130372](https://jira.cvent.com/browse/GROUP-130372)

The most uncertain area. Also consult [matthew-hostetler](https://wiki.cvent.com/matthew-hostetler) for the MyCvent/platform-user-ID side.

**Primary inputs**: Read these first:

-   [bridge-page-authentication](https://wiki.cvent.com/bridge-page-authentication) — the auth decision doc; fully specifies Approach 2 (BFF-orchestrated). Most of this design is already settled.
-   [jifflenow-bridge-page-td](https://wiki.cvent.com/jifflenow-bridge-page-td) — reference implementation of the same pattern

**Auth design is substantially resolved.** Approach 2 (BFF-orchestrated with encrypted-token-as-cookie) applies to Passkey. Full flow:

1.  BFF validates Events cookie with Cvent Auth → extracts Core `platformUserId` from token metadata
2.  BFF calls `getCventWidgetAccounts` GraphQL → resolves linked Passkey `platformUserId`. **Confirm API name with MyCvent team** — the auth doc flags this as uncertain ("is there a different API to use?"). The platform guide names `getParentUser`/`linkAccount` instead.
    -   If zero linked accounts: show MyCvent account linkage modal (once only — persists thereafter)
3.  BFF calls new Passkey auth server endpoint `getAuthenticatedUserToken` (service-to-service bearer, locked to bridge BFF only) → Passkey internally looks up local user → calls Cvent Auth to mint Passkey-scoped token → returns token to BFF
4.  BFF encrypts token with BFF secret key → stores as encrypted cookie
5.  Subsequent requests: BFF decrypts cookie → calls Passkey GraphQL (Odyssey/RDK2) with Passkey-scoped token
6.  BFF **also re-validates Events cookie on every request** (not just initial auth) to detect logout/revocation before forwarding

**Auth is lazy**: page load (Sequence A) validates Core session + checks event-data-service link status only. Auth handshake (steps 1–4) fires on the first privileged action (linking, viewing dashboard). Unprivileged page load has no Passkey auth.

**Only new Passkey backend artifact required**: the `getAuthenticatedUserToken` endpoint on Passkey's auth server. Everything else reuses existing Cvent Auth infrastructure. **Allain Turgeon owns this.**

**Unprivileged insights — resolved**: Post-link insights (pickup metrics, inventory) do not require user identity and are fetched with a service-to-service account-level token — no MyCvent linkage and no user-scoped token required. This preserves the Phase 1 "view insights without a Passkey user" guarantee. DD-3 confirms the exact token/credential and the precise set of GraphQL operations it covers. Privileged actions (linking, deep link) still require the user-scoped handshake.

**Acceptance criteria:**

1.  **Unprivileged path confirmed**: Post-link insights are fetched via a service-to-service (non-user-scoped) token without MyCvent linkage (decided). Document the exact token/credential mechanism and list the GraphQL operations it covers. Confirm none of them require a user-scoped token.
2.  **`getAuthenticatedUserToken` contract specified**: Document the new Passkey auth server endpoint — service-to-service bearer input, request parameters (Events `platformUserId`), response (Passkey-scoped Cvent Auth token), token lifetime, and which Passkey auth server service owns it. This is Allain's deliverable. The DD output is the agreed contract.
3.  **MyCvent API name confirmed**: Confirm with the MyCvent/Universal Login team whether the account-linkage GraphQL call is `getCventWidgetAccounts`, `getParentUser`, or another current API. Document the confirmed operation name, request/response shape, and how to handle zero vs multiple linked Passkey accounts.
4.  **Cookie lifecycle documented**: Specify what is encrypted into the cookie (Passkey-scoped token) and the BFF secret key management approach. Document how the `~15 min` token lifetime is handled (silent re-handshake vs re-auth prompt). Document how Events cookie re-validation on every request is implemented.
5.  **Failure modes documented**: Specify BFF behavior for: (a) Events session valid but `getAuthenticatedUserToken` fails; (b) Passkey token expires mid-session; (c) user has no MyCvent linkage on a privileged action; (d) Events cookie revoked mid-session (detected on re-validation). Privileged and unprivileged paths must have different failure responses.
6.  **Implementation tickets created** covering: `getAuthenticatedUserToken` on Passkey auth server (Allain), BFF auth middleware + Events cookie re-validation, encrypted cookie lifecycle, MyCvent linkage modal trigger, auth failure handling per path.

# 15\. Record of Decisions

## Validated decisions (2026-08-10, Josh Lartz + Boris Bronstein)

-   **BFF pattern confirmed**: Next.js CDF planner app. The BFF comes from Next.js at no extra cost. No separate internal GraphQL layer is needed in the bridge app.
-   **Reuse Passkey GraphQL confirmed**: The BFF proxies to existing Passkey GraphQL APIs (Odyssey \[new Planner Portal\] / RDK2) with minimal transformation. Do not call microservices directly from the BFF.
-   **Link store is a real Cvent service**: A separate Cvent team is building the event data service (link store). The spec was due ~2026-08-10, with implementation soon after. Passkey must: (1) register links with this service, AND (2) store the Cvent event ID on Passkey's own side. Josh will share spec/links when available.
-   **Auth confirmed**: Cookie-based bearer token (~15 min). No session state store. Same approach as JiffleNow bridge page.
-   **Phase 1 user identity unblocked**: Passkey stores platform user IDs in a direct 1:1 mapping table. APIs support bidirectional lookup (need to 100% confirm with  
-   **Phase 2 user identity is an open risk**: Non-licensed users without Cvent accounts are unsolved. Do not use generic Salesforce account workarounds (Social Tables cautionary tale). Keep out of scope or require proper Cvent account enrollment.
-   **Unprivileged insights auth confirmed**: Post-link insights use a service-to-service account-level token — no MyCvent user linkage required. Only privileged actions (linking, Manage/Planner Portal deep link) need the user-scoped token handshake. This preserves the Phase 1 "insights without a Passkey user" guarantee.
