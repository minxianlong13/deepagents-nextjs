href="https://blocks.passkey.com/guestside">https://blocks.passkey.com/guestside</a> is responsible for loading the UI app into the user's browser.  The behavior of this endpoint is dependent on the method in which the user has arrived at the site:</p><ul style="list-style-type: square;"><li>If the user has clicked on a public link, the reference endpoint will contain a 'block request uuid' query parameter, and will not contain any user-related token params.  This state causes the email validation pop in to appear (<em>See <strong>fig. 1a</strong> above</em>).</li><li>If the user has arrived by clicking on the emailed link to the site - that link will contain a user <em>token</em> (By Invitation) or a <em>userUUID</em> (By public link verification) query parameter to authenticate the user.</li></ul><p>The guestside service fetches the UI Application via the traditional <strong>NucleusView</strong> approach - the reference endpoint services HTTP requests by supplying an App Loader payload (NucleusView) to the requesting browser, giving it the Javascript instructions that will find and launch the public Autoblock UI asset webpack bundles stored in S3.</p><p>The NucleusView You should imagine this workflow going on while the Review &amp; Submit Screen: Submitting the Request activity (See above section) is <em>still going on</em>.</p><p>The block request submission, which is an HTTP POST, returns immediately with a task Id in its response payload that uniquely identifies the <em>STEP functions execution in progress</em> that is autoprovisioning the request, AS WELL AS uniquely identifying the task log record created in the AutoblockTaskLog DynamoDB table.</p><p>During the UI transition between submitting a block request (with the 'Submit' button) and displaying the confirmation screen (which shows the details of a successfully-provisioned request), there is a series of network transmissions in which the browser requests status updates for the autoprovisioning task, and a subsequent progression of task status updates from the server to the browser until the final update is received; indicating that the request has ultimately succeeded or failed.</p><p>Here's how it works:</p><ol><li>The browser, with a task Id in hand, attempts to connect with the Websocket server using the access token created at the onset of the guestside UI session (See the <em>Loading the Guestside Site</em> section).  The browser MUST authenticate with a valid access token (via the Cvent Auth Service) or else they will not be allowed to connect.</li><li>Successful connections are given a unique connection Id by the AWS Websocket Gateway.  Both Browser and Server are aware of the connection Id, which can be used by the server to transmit unsolicited data to the browser in absentia of a preceding HTTP Request.</li><li>Once connected, the browser requests updates to the task log identified by the Task Id that was provided to the browser by the STEP Functions orchestrator.  We call that the <em>subscribe</em> routing in the AWS Websocket Gateway configuration.  The routing is handled by an AWS lambda that uses the passkey-autoblock-data-service to update the task log identified by the provided task id with the Websocket connection Id that identifies the browser to the websocket server.</li><li>Once that Websocket connection Id field is populated in the DynamoDb task log record, it activates a custom DynamoDB Streams-based trigger that will fire every time the record is updated.</li><li>As the STEP Function execution proceeds through its execution milestones and periodically updates the task log, the trigger is activated to call back to the Websocket gateway with the Websocket Connection ID that is found in the record.  This prompts the Websocket Server to push the DynamoDB Streams payload (the task log) to the browser, completing the update cycle.</li></ol><h2>GraphQL Query The Customer gets a Blank screen when they click on their Guestside link in their email.  What do I do? </h3><p>A. This problem is most often the symptom of an <em>expired link</em>, which means the user needs to generate a new link.  The user should be able to give you feedback on the following:</p><ul style="list-style-type: square;"><li>If the user arrived at the site via Public Link, they need to re-visit the public link again to revalidate their email address and send themselves another email containing a new link.</li><li>If the user arrived at the site via an email they got from the event organizer, they probably received that email more than a month ago. They'll need to reach out to their organizer and request a new one.  NOTE: If we run into this issue frequently, we will need to tune the application to manage user email validations for longer than 30 days - 30 days is an arbitrary balance between functionality and data safety (validations that live for a long time can be exploited).</li></ul><p>However, this symptom can also sometimes be indicative of a broken or offline resource, such as the microservice hosting the application.  For now, the best way to tell which one of these scenarios best represents the customer's problem is to examine the HTTP Response code of the Guestside UI page load request.  Usually, the browser's built-in debugger/dev tools can tell you information about the HTTP response code.</p><p>If the HTTP response code is <strong>401 (Unauthorized)</strong>, the likely problem is that the guestside URL/link that was used to load the page is more than a month old, and is thus no longer valid.  In this case, the organizer must send the user a new invitation email with a new link. LINKS CANNOT and SHOULD NOT be shared between planners.</p><p>If the HTTP response code is 503 (Service Unavailable) or 504 (Gateway Timeout), it means that the guestside service is offline, either for maintenence or because it was shut down unexpectedly.  Confirm with dev that there is not an open Passkey maintenance window (usually Wednesday Mornings).  If not, escalate this loss-of-service issue to dev so that the system can be restored.</p><p>Any other HTTP response code that results in a blank screen should be escalated to dev for investigation.</p><p><br /></p><h3>Q.
