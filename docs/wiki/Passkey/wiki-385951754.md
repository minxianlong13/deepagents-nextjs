# Overview

Individual Planner Invitation feature will help organizers to add random recipients to already created but not fired up campaigns.

## User scenario

`Given an organizer`

`And an event with enabled Autoblock`

`And an autoblock wizard configuration`

`And not fired up the campaign`

`When the organizer clicks the "Add recipients" button on autoblock wizard`

`Then Resdesk displays "Add Recipients"`

`And a "Room Block Requered Notifications"`

`And a recipient section with contact fields`

`And a "Cancel" link-button`

`And an "Add recipients" submit-button`

`When the organizer selects notification campaign`

`And enters individual recipient contact info`

`And clicks the "Add recipients" submit-button`

`Then Resdesk close "Add recipients" pop up`

`And saves new recipients into the selected campaign`

`And show up success green message`

`When organizer closes success message or navigate away`

`Then the success message is no longer displayed.`

## Validation Rules

1.  The "Add recipient" menu option is displayed only if the request has at least one not fired up notification campaign.
2.  The organizer cannot select more than one campaign for adding an individual notification contact.
3.  Contact validation exists on both UI and service layers.
4.  Contact validation is inherited from the existing notification campaigns.
    1.  Contact validation should include the business checks listed in the 5th point. In addition to basic UI check on mandatory fields, UI check will handle input checks that can be inherited from creating planner on planner portal, like max/min length, special characters, etc.
    2.  Service side validation of business entity will rely on existing ExtRecipient model validation and DB constraints for text fields that exist for the current flow of adding recipient in a bulk or any other campaign creation flow.
5.  Contact fields include:
    1.  First name - not mandatory.
    2.  Last name - not mandatory.
    3.  \*Email - mandatory. One email per field.
    4.  Title - not mandatory.
6.  In case of failed check on ui show up red errors under each field.
7.  In the case of service, validation shows the error is an error UI element.

# Assumptions

-   The initial feature includes the ability to add only one recipient to only one campaign (One-to-One relationship) BUT the ability to add a collection of recipinets can be added right after MVP, based on feedback
    -   (If no then we need to include a work of scaling ui components based on new entries and handle several actions like on scroll etc.. that may extend the development of MVP)
-   No Carina usage
    -   (If yes that we need to spin up a new project and revisit complete communication with Resdesk actions that will significantly increase the scope of development in order to implement new UI project, add Catrina, inject into Resdesk, communicate to Resdesk actions)
-   No microservices implementation
    -   (Using existing infrastructure will simplify development but limit the usage of functionality outside of Resdesk)
