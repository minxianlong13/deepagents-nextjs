## The pagination question — answered

The public summaries API is paginated, but the tool does **not** page raw daily rows. It sets `groupByKeys = [month_year, product_feature_code]`, which switches `UsageSummaryDAOMapper.xml` into its grouped mode: Postgres computes `SUM(count) … GROUP BY month, account_id, product_feature_code` and returns **one row per feature per month**. Worst case for a 12-month range: 12 × 4 = 48 rows — one page (limit 2000). The tool still loops `offset += pageSize` until a short page arrives (defensive, cheap), then folds the monthly rows into per-feature totals in memory and returns them in one response. The monthly rows are kept as `monthlyBreakdown` so 6–12 month questions get a trend for free. Consolidation happens in the tool; the client receives a single, complete answer.

## Tool contract

```
name:        get_feature_wise_usage
auth:        @Authority(methods = {JWT}, roles = {"private/mcp-product-usage:read"}) GrantedAccessToken
annotations: readOnlyHint = true, idempotentHint = true

arguments (all optional, at least one path required):
  period      THIS_MONTH | LAST_MONTH | THIS_QUARTER | LAST_QUARTER | THIS_YEAR | LAST_YEAR
  startDate   YYYY-MM-DD   (used with endDate when period is absent)
  endDate     YYYY-MM-DD   (inclusive; capped at today; range ≤ 24 months)
```

Rules: calendar periods in UTC; for open periods `endDate = today`; `period` and explicit dates are mutually exclusive (400 if both / neither); `startDate > endDate` → 400; account always from the JWT, never from arguments.

## Phase 4 — The tool

`mcp/GetFeatureWiseUsageTool.java`, `@Inject` constructor `(UsageSummaryService, IdentityMappingService, UniversalProductUsageConfiguration)`.

```
@Tool(name = "get_feature_wise_usage",
      description = "Total registration usage per product feature for the caller's account over a calendar period
                     (this/last month, quarter, year) or an explicit date range. Numbers match the
                     'Monthly Billing Combined Registration Usage Summary' report. Admin users only.")
@Tool.Annotations(readOnlyHint = true, idempotentHint = true)
public FeatureWiseUsageResponse getFeatureWiseUsage(
    @Authority(methods = {AuthMethod.JWT}, roles = {MCP_PRODUCT_USAGE_READ}) GrantedAccessToken token,
    @ToolParam(name="period",    description="THIS_MONTH|LAST_MONTH|THIS_QUARTER|LAST_QUARTER|THIS_YEAR|LAST_YEAR", required=false) String period,
    @ToolParam(name="startDate", description="YYYY-MM-DD, with endDate, when period is absent", required=false) String startDate,
    @ToolParam(name="endDate",   description="YYYY-MM-DD inclusive, with startDate", required=false) String endDate)
```

Steps:

1.  `accountMappingId = token.getAuthorization().getMetadata().get("accountMappingId")` → 401 if absent (same as PR #344).
2.  `coreAccountId = identityMappingService.getAccountIdByMappingId(configuration.getEnvironmentName(), accountMappingId)` → 403 if null.
3.  `ResolvedPeriod p = UsagePeriodResolver.resolve(period, startDate, endDate, LocalDate.now(UTC))`.
4.  Build request: `ImmutableUsageDataRequest.builder().startDate(p.start.atStartOfDay(UTC)).endDate(p.endInclusive.plusDays(1).atStartOfDay(UTC)).accountId(coreAccountId).productFeatureCodes(REGISTRATION_CODES).groupByKeys(List.of("month_year", "product_feature_code")).syncedForOverage(null).billable(false).build()`. `REGISTRATION_CODES` \= the 4 `ProductFeatureCode…value()` strings. (`endDate` exclusive matches the DAO's `end_date <= #{endDate}` on day-boundary rows.)
5.  Page: `offset = 0; do { rows = usageSummaryService.getUsageSummary(req, MAX_TWO_STEP_LIMIT, offset, true); all.addAll(rows); offset += rows.size(); } while (rows.size() == MAX_TWO_STEP_LIMIT);` — **`isReport = true` is the load-bearing flag.**
6.  `return FeatureUsageAggregator.aggregate(all, p)`.

Principal type: the bundle's `Authenticators` produce `GrantedAccessToken` and `AuthenticationHandler` injects it when the parameter type is assignable — declaring `GrantedAccessToken` with `methods = {JWT}` only is correct (keep it JWT-only; #344's Sentinel "token-type mismatch" note came from mixing methods).

4.  Pagination path: temporarily lower the page size constant in a local build (or seed
    
    > 2000 grouped rows in a dev DB) and confirm two service calls with offsets 0 and 2000 and a complete, non-duplicated result. Revert.
    

### 8.4 Parity with the Usage Report (staging, the decisive gate)

**Setup** — staging silo (sg50/S606), an **admin** user (or `HasAllEventAccess`) in each of 3 accounts chosen to cover: (a) a large account with all 4 registration features active, (b) an Attendee-Hub-heavy account, (c) an account known to have cancelled/closed events in the period. Use a **closed** month (orchestrator finished, no in-flight regeneration) and, for the range case, a closed quarter.

**Step 1 — Report.** In Planner, run _Monthly Billing Combined Registration Usage Summary_ (`monthly-billing-combined-registration-usage-summary`) with the date range = the month. Export CSV. Sum `count` per `displayProductFeatureCode` (rows are per event × month × feature).

**Step 2 — Tool.** `tools/call get_feature_wise_usage` with `startDate`/`endDate` \= the same month (or `LAST_MONTH`), same account's JWT. Record `features[].totalCount` and `monthlyBreakdown`.

**Step 3 — Ground truth SQL** (read-only, same silo DB), the exact branch both paths hit:

```sql
SELECT date_trunc('month', start_date) AS month, product_feature_code, SUM(count) AS total
FROM usage_summary
WHERE account_id = :coreAccountId
  AND product_feature_code IN ('EventManagement_Registration','AttendeeHub_Registration',
                               'OnArrivalPremium_Registration','Essentials_Registration')
  AND start_date >= :monthStart AND end_date <= :nextMonthStart
  AND COALESCE(operation_type,'') <> 'Delete'
GROUP BY 1,2 ORDER BY 1,2;
```

**Step 4 — Compare** in a sheet: `report total | tool total | SQL total | delta` per feature per account. Acceptance: **delta = 0 for every feature in every account**; features absent in the report are absent in the tool; the tool's `monthlyBreakdown` equals the SQL per-month rows.

**Step 5 — If any delta:**

-   Tool ≠ SQL → bug in the tool (request flags, paging, aggregation). Fix, rerun 8.1–8.3.
-   Tool = SQL ≠ report → row-set difference. Diff the report CSV's event list against `SELECT DISTINCT report_field1_value … WHERE account_id = :id AND …`. Stubs present in our DB but not in the report are events event-api's `EventListForUsers` did not return (hard-purged event, or the user was not actually admin). Confirm the user's role; if purge is real and material, escalate to Product (Option B: pass event stubs as `reportField1Values`).
-   Report totals differ between two admins of the same account → visibility leak; stop and re-check the "admin-only" assumption with the account's user settings.

**Step 6 — Edge checks** (one account is enough):

-   Open period: `THIS_MONTH` today vs report with end = yesterday → tool ≥ report only by today's rows, if the orchestrator has already run today; label says "as of today".
-   Regeneration day: run the tool before and after a known regeneration run; totals move identically in the report.
-   Non-admin negative: a restricted user's report shows fewer events; the tool (v1) is not offered to them — confirm the AIMS capability access rule excludes non-admins, or document the known difference.
-   Zero-usage account: tool returns `features: []` with a period label, no error.
-   Silo mismatch: a JWT whose `accountMappingId` maps to another silo → 403, no data.

Record results in the PR description (table per account) and link the CSV exports.

## Research summary (why this works — verified)

-   Report chain: reporting-service → `event` datasource (`soa-reporting` `EventInformationForUsageClientExecutor`) → event-api `EventListForUsers(eventStatus=null)` → `EventDataAccess.GetEvents(acctId)` (all account events, no status filter) → `FilterEventsbyVisibility` (admins / `HasAllEventAccess` see all). Stubs are passed to our `/v1/datasource` as `reportField1Values`; every other join in the combined view is LEFT (display only).
-   Our rows are generated by `event-registration-usage` with status/test/webinar/simple-in-person/sandbox/billability exclusions already applied, so for admins `usage_summary WHERE account_id = X` ≡ the report's row set.
-   `UsageSummaryRepository.getData()` → `getUsageSummary(req, limit, offset, true)`; the tool calls the same overload with the same `productFeatureCodes` and a `groupByKeys` including `product_feature_code`.
-   Rejected: reporting MCP `query_view` (needs an open report session), reporting REST orchestration (slow, roles, async), falcon-planner/event-api joins (LEFT, no filtering).
-   Reporting side references: `content/reports/monthly-billing-combined-registration-usage-summary.json`, `content/views/monthly_registration_billing_usage_combined_summary.json`, `content/datasources/universal-product-usage.json`.
