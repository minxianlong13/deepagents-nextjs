The Create Event from Roomlist use cases will require an API that will be able to, based on various inputs, generate a new HD event that is automatically pre-provisioned with block, subblock, SBG, attendee, planner and acknowledgement campaign infrastructure so that reservation data can be processed _automatically_ (following event creation) as part of the same workflow.

This API represents the final action in the final stage of user engagement in the use case.  This API is what is called when the Hotel user hits the "Finish" button to actually perform the event create action. It is assumed that before this stage in the workflow:

-   All validation of user input has been done, automatically and/or manually.
-   An authorized Passkey user representing the Hotel in question has accepted and approved the request.
-   All measures of compatibility between the end user's room list request and the actual logical constraints of the hotel have been:
    -   Assessed and deemed good-to-go as-is
    -   Assessed and automatically transformed to compatible input(s)
    -   Assessed and manually transformed to compatible input(s)
    -   Assessed with no acceptable transformation, and removed from the request
-   All auto-detected, default and overridable settings/preferences have been confirmed and settled.

  

This design, then, is intended to cover only the final piece of the whole 'Create Event from Roomlist' use case.

# API Input Contract

As we are not building this API with external contract dependencies, we will not have an official _contract requirements_ phase for this workflow. The initial version of the API input will simply be an accumulation of contract inputs from already-existing modules that will be used by this workflow (and are already in use today).  We already have the building block contracts for creating an event, autoprovisioning, and creating reservations.  Stitched together, they will serve as the initial input contract.

It will be beneficial, however, to document the contract semantics in order to improve the integration experience when the time comes to merge this API with the User Interface(s) that will drive it.

The working assumption should be that the contract will be a JSON payload consistent with contract form factors across our suite of microservices.

Map Room Types

The most import job this step has is to create a mapping that allows the reconciliation of back-referenced room types (in the incoming reservations payload) to material room type ids once they have been created.  These mappings are used to ensure that the reservations are mapped to the precise room types as directed by the end user.

This phase aligns the requested room types in the original planner request with a usable hotel room type, and constructs a current event-level block for each RT based on input dates and room rates.  The caller of this API will have been expected to resolve RoomTypeInput beforehand, such that the fuzzy guesswork is taken out of this workflow. nput into this phase will be an array of **RoomTypeInput** combinations, where each combination resolves to a room type and corresponding contract dates, inventories and rates.

**RoomTypeInput** is:

-   RoomTypeSource: One of _FROM\_BUNDLE_, _FROM\_LIBRARY_, _AD\_HOC (Always required)_
-   RoomNights (Always required)
    -   Array of: 
        -   Contract Date
        -   Available Inventory 
        -   Room Rate
-   LibraryId (Required when RoomTypeSource is FROM\_BUNDLE or FROM\_LIBRARY)
-   Description (Required when RoomTypeSource is AD\_HOC)
-   Name (Required when RoomTypeSource is AD\_HOC)

The lambda proceeds to make MS calls as follows:

-   -   When FROM\_BUNDLE is selected 
        -   Create the original inventory via the provided libraryId (matching EVENTPROFILE.ROOMTYPE.ROOMTYPELIBRARYID).  See **PUT /room-types** in passkey-inventory-service
    -   When FROM\_LIBRARY is selected
        -   Copy RT configs from HOTELROOMTYPE table to ROOMTYPE table for the new event via the provided libraryId.
        -   Create the current event-level inventory in ROOMTYPEINVENTORY for the new ROOMTYPE table record.  See **PUT /room-types** in passkey-inventory-service
    -   When AD\_HOC is selected
        -   Create new RT config in ROOMTYPE based on provided set of inputs See **POST /events/{eventId}/hotels/{hotelId}/room-type** in passkey-room-type-data-service
        -   Create the current event-level inventory in ROOMTYPEINVENTORY for the new ROOMTYPE table record.  See **PUT /room-types** in passkey-inventory-service

This workflow phase does NOT estimate or attempt to fuzzy match Room Types based on ambiguous inputs.  Each RoomTypeInput must contain sufficient definition to exactly match one and only one target room type, or else it will specify all necessary configs to _create_ the target room type.  The system will know which of these actions to take based on **RoomTypeSource**.

Autoprovision

This phase autoprovisions the new event with:

-   **Attendee groups** matching the attendee input specification.  Attendee Group Type input consists of an array of the following Attendee Type Sources:
    -   FROM\_BUNDLE: Use existing bundle-provided attendee group specified by inbound attendeeGroupTypeId for provisioning
    -   FROM\_LIBRARY: Use library-level attendee group specified by inbound libAttendeeGroupTypeId to construct new event attendee group to use for provisioning
    -   AD\_HOC: Use the inbound AttendeeGroupType details specification to construct a new ad-hoc attendee type to use for provisioning
        -   This input will require an 'adHocRefId' so that created ad-hoc group types can be back-referenced by the Sub-block inventory and SBG creation steps.
-   **Sub-Block inventory** for the room types specified by RoomTypeInput. This input matrix will be discrete from RoomTypeInput, providing potentially different inventory request numbers, as well as an attendee group type association (Where these room sub-blocks back-reference Attendee Types that are also provided as input).
-   A Single **SBG** that correlates the created attendee groups to the provided **Planner ID**.  This API workflow will not be relied upon to create planner records, since planner records are universal across all events and accounts and should not be rolled back when there are errors in the workflow.

Reservations/Acks

This phase accepts a payload of reservation data that can be presumed extracted from the original customer roomlist.  This phase:

1.  Ensures the payload is transformed into a format acceptable for the reservation-saga.
2.  Reconciles Ad-hoc and library-level references to attendees and room types are reconciled to their actual appropriate DB ids.
3.  Invokes the reservation-saga workflow, which:
    1.  Places the reservations with the event
    2.  Sends the acknowledgements

-   Construct flexible Room Type back-reference identifier schema for workflow input contract (**1d**) Cvent JIRAd1d78885-1a8e-3259-b68d-3df198ee3d46GROUP-107237
    -   This step expects 'RoomTypeDefinitions" array-type field in parent workflow's request schema as top-level request attribute
        -   This list will contain sufficient definition metadata for all room types that are to be applied to the source room list.
    -   Bundled Room Types should be referenced via formatted string Id, eg: "BUNDLE#123456789"
        -   Prefix BUNDLE tells the mapper that the subsequent lib-level room type Id can be used to look up an existing room type identifier in the event.
    -   Library Room Types should be referenced via formatted string Id, eg: "LIBRARY#123456789"
        -   Prefix LIBRARY tells the mapper that the room type must be constructed, and that it should use the definition specified by the following hotel-level room type library id.
    -   On-the-fly Room Types should be referenced via formatted string Id, eg: "ADHOC#1"
        -   Prefix ADHOC tells the mapper that a new room type should be constructed on-the-fly and have its Id mapped to this back-reference id (in this case, the numeric identifier following the prefix can be made-up, but it must be unique in the request scope.  Multiple ADHOC-type room types cannot have the same numeric identifier.

    -   Use back-reference identifier schema to invoke MS calls to the aforementioned _three_ passkey-room-type-data service endpoints to reconcile incoming back-reference identifiers to actual room type ids.
    -   Publish mapped results to Step Functions execution state for future reference.
        -   Expect reservation → room type mappings in reservations input payload to use back-reference ids.
    -   Create 'current' event-level block for all back-referenced room types using their now-mapped room type ids and the _**PUT /room-types**_ endpoint in the passkey-inventory-service.
