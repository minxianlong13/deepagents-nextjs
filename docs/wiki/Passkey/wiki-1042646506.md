### 1\. Objective

We are migrating the **Room List upload** flow in **Passkey Smart Room Assistance (RDK2 + Java service)** to use the shared **`passkey-file-uploader` widget**.

Goals:

-   Reuse the centralized upload + sanitization pipeline.
    
-   Keep the **downstream RLM logic unchanged** (we still end up with a file in our S3 bucket + `fileId`).
    
-   Minimize risk via **feature-flagged cutover** and incremental rollout.

### 2\. Current Flow (Before Migration)

**Frontend (RDK2 / Next.js):**

1.  User uploads a file using `FileUploadWidget` (`@cvent/carina/components/FileUpload`).
    
2.  `onSelected` posts a `multipart/form-data` request to:
    
    -   `POST /api/room-list-file-upload`.
        
3.  On success:
    
    -   The API returns `{ fileId }`.
        
    -   UI sets:
        
        -   `roomlistFileId` (from response).
            
        -   `fileType` (derived from file extension: xls/xlsx/csv).
            
        -   `successfulUpload = true`.
            

**RDK2 API:** `POST /api/room-list-file-upload`

1.  Parses file via `formidable`.
    
2.  Gets `authToken` from cookie and resolves `participantId` via `authClient`.
    
3.  Streams uploaded file to Java:
    
    `POST {PASSKEY_SMART_ROOM_ASSISTANT_ENDPOINT}/{VERSION}/fileserver/participants/{participantId}/file`
    
4.  Forwards `fileId` from Java response back to UI.
    

**Java Backend (`passkey-smart-room-assistant`):**

1.  `FileMapperController.uploadMappingFile(...)`:
    
    -   * * *
        
        Sanitizes filename (`ParsingUtil.sanitizeFilenameString`).
        
    -   Validates file type (xls/xlsx/csv).
        
    -   Uses `FileMapperService.uploadFile(...)` to store file in S3.
        
2.  Returns a response containing `fileId`.
    
3.  RLM processing later consumes S3 file + `fileId` as it does today.

### 3\. Target Flow (After Migration)

The new flow introduces `passkey-file-uploader` as the place where **upload + sanitization** happens, but we still need to **pull the sanitized file** into our own S3 bucket and generate a `fileId` for RLM.

#### 3.1 High-Level Flow

1.  **RDK2 UI** renders the `passkey-file-uploader` iframe via `PenpalParent`.
    
2.  RDK2 fetches an **access token** and configures the widget:
    
    `child.configure({ accessToken, application: '<TBD: e.g. "roomlist">', uploadType: '<TBD: e.g. "file">' });`
    
3.  User uploads file in the widget; widget:
    
    -   Validates type/size.
        
    -   Sanitizes file.
        
    -   Stores sanitized file in its own storage.
        
4.  On success, widget calls parent method:
    
    `filesSelected(uploadedFiles: UploadedFile[])`
    
    where at least one `UploadedFile` object contains:
    
    -   `id` → **sanitized file identifier in `passkey-file-uploader`** (exact contract TBD).
        
    -   `name` → original/sanitized file name (used for extension).
        
5.  RDK2 calls a new Next API endpoint (JSON, not multipart), e.g.:
    
    `POST /api/room-list-widget-attach`
    
    with:
    
    `{ "widgetFileId": "<[UploadedFile.id](http://UploadedFile.id)>" }`
    
6.  New RDK2 API:
    
    -   Resolves `participantId` from auth cookie.
        
    -   Calls new Java endpoint:
        
        `POST /passkey-rlm/v1/fileserver/participants/{participantId}/widget-file/{widgetFileId}`
        
7.  Java backend:
    
    -   Uses a new `FileUploaderClient` to **download sanitized file** from `passkey-file-uploader` using `widgetFileId`.
        
    -   Determines file name/extension from metadata.
        
    -   Sanitizes the name via `ParsingUtil.sanitizeFilenameString`.
        
    -   Reuses existing `FileMapperService.uploadFile(...)` to store file in our S3 bucket.
        
    -   Returns a response with `fileId` (same shape as current `uploadMappingFile` response).
        
8.  RDK2 returns `{ fileId, fileName }` to the React component.
    
9.  React:
    
    -   Sets `roomlistFileId = fileId`.
        
    -   Derives `fileType` from `fileName` extension.
        
    -   Sets `successfulUpload = true`.
        
10.  Downstream RLM flow continues **unchanged**, using `fileId` + S3 file.

### 4\. Detailed Frontend Flow (RDK2)

#### 4.1 New Wrapper Component

We introduce a new React component (e.g. `RoomListFileUploader`) that replaces the existing `FileUploadWidget` implementation.

Responsibilities:

1.  **Fetch access token** (via a dedicated RDK2 API or existing auth flow).
    
2.  **Configure widget** once `child` + `accessToken` are available.
    
3.  Implement `FileUploaderParent` callbacks:
    
    -   `height(h: number)` → update iframe height (`setHeight(`${h}px`)`).
        
    -   `filesSelected(items: UploadedFile[])`:
        
        -   Store displayed file metadata.
            
        -   Trigger call to `POST /api/room-list-widget-attach` with `widgetFileId = items[0].id`.
            
4.  Handle local state:
    
    -   `isLoading` → when calling the backend with `widgetFileId`.
        
    -   `hasError` → when widget or backend fails.
        
    -   `successfulUpload` → mirrors current widget behavior.
        

The UI around the iframe should preserve current user expectations:

-   Show translated labels (drop area, accepted file types, file limit) either as:
    
    -   External context around the iframe, or
        
    -   Replaced by widget’s own labels if aligned with UX.
        
-   Show validation message if `showErrors` is true and no file was successfully uploaded.
    
-   Show success message identical to current copy once upload is complete.
    

#### 4.2 New RDK2 API: `POST /api/room-list-widget-attach`

Responsibilities:

1.  Parse JSON body:
    
    `{ "widgetFileId": "..." }`
    
2.  Resolve `participantId` from auth cookie using existing `getParticipantFromAuth`.
    
3.  Validate inputs; return:
    
    -   `401` if participant cannot be resolved.
        
    -   `400` if `widgetFileId` is missing/invalid.
        
4.  Call Java:
    
    `POST {PASSKEY_SMART_ROOM_ASSISTANT_ENDPOINT}/{VERSION}/fileserver/participants/{participantId}/widget-file/{widgetFileId}`
    
5.  On success:
    
    -   Return `{ fileId, fileName }` to the React layer.
        
6.  On error:
    
    -   Map Java responses to sensible HTTP codes (400/404/500).
        
    -   Log context: participantId, widgetFileId, and Java status.

#### 5.2 New `FileUploaderClient`

A dedicated client to talk to `passkey-file-uploader` backend:

-   Methods (conceptual):
    
    `SanitizedFile downloadSanitizedFile(String widgetFileId);`
    
-   `SanitizedFile` includes:
    
    -   `InputStream inputStream`
        
    -   `String originalFileName`
        
    -   `long size`
        
    -   `String contentType`
        
-   Uses configured base URL and timeouts.
    
-   Maps HTTP errors from uploader into typed exceptions (`FileNotFoundInUploaderException`, etc.).

### 6\. Open Questions / Missing Details (to be filled from Ticket 1)

At the time of writing, the following details are **TBD** and must be defined by the `passkey-file-uploader` team before we cut over:

1.  **Supported file types & size limits**
    
    -   Which extensions/mimetypes are allowed? (Currently RLM expects xls/xlsx/csv).
        
    -   Max size per upload.
        
2.  **`UploadedFile` shape**
    
    -   Final interface (at minimum: `id`, `name`, `size`, `contentType`, status).
        
    -   Which field is the canonical **sanitized file ID** used to download the file.
        
3.  **Configuration semantics**
    
    -   Accepted values and behavior of:
        
        -   `uploadType` (e.g. `'file'`, `'roomlist'`, etc.).
            
        -   `application` (used for routing/tenanting?).
            
4.  **Error handling contract**
    
    -   How are validation/processing errors surfaced to the parent React app?
        
    -   Expected error codes and messages from:
        
        -   Widget → parent callbacks.
            
        -   Backend download API → Java client.
            
5.  **Sanitized file download API**
    
    -   Exact path and HTTP method to download the sanitized file by `widgetFileId`.
        
    -   Required headers / auth model.
        
    -   Whether the file is scoped by participant / application.
        
6.  **Access token generation & validation**
    
    -   How the widget `accessToken` is generated.
        
    -   Required claims (participantId, tenant, permissions).
        
    -   Lifetime and refresh behavior.
        

All of this will be documented in this wiki section once confirmed.
