<h2>Lessons</h2><h3>Client (UI) Side:</h3><ul style="list-style-type: square;"><li>Avoiding fine, granular queries ('micro-queries')<ul style="list-style-type: square;"><li>Tried and failed:  Apollo Batch Link HTTP (coalesces client-side queries into single HTTP payload).  This utility unfortunately does NOT correlate server context (therefore, new DataSource sets are created for each query).</li><li><strong>UI-side micro-queries are not necessary for cache normalization and re-use!</strong><ul style="list-style-type: square;"><li>Apollo Client has configurable normalization and cache-redirect features that can accomplish this, but we didn't know about these until after we had already mostly completed the work.</li><li>Wasn't in a hurry to change it when we found out because our own solution appeared to be better on the surface, since normalization was built into the design (without having to worry about custom hooks for each case of cache re-direct).</li></ul></li><li>What about the 'get only what you need' principle?<ul style="list-style-type: square;"><li>The principle still holds: Get only what you need.  However, get <em>everything</em> you need for a given UX 'use case' as opposed to breaking down queries on the grounds that you have sub-components.</li><li>This will also aid in the construction of re-usable library widgets, which will be less likely to have dependencies on other library widgets with integrated GQL query dependencies.</li></ul></li></ul></li><li>In list or grid contexts, Use pagination properly to avoid over-fetching:<ul style="list-style-type: square;"><li>One query for all displayed data, except where expensive data could be out-of-banded in a way that marginalizes the UX impact - like flyovers or clickable areas)</li><li>Fetches details only for page items.</li></ul></li></ul><h3>Apollo Server Side:</h3><ul style="list-style-type: square;"><li>Avoiding HTTPDataSource, which memoizes only Objects, <em>not</em> tasks.</li><li>Avoiding fine, granular queries</li><li>Possible pagination pattern to apply on Apollo server side:<ul style="list-style-type: square;"><li>Use a list of ids as the query's &quot;source of truth&quot;</li><li>Truncate the list to only the current page</li><li>Proceed to fetch the requested details of each <em>displayed</em> item by id<ul style="list-style-type: square;"><li>This normalizes the cache in the apollo server side as well (reduces memory footprint and improves cache/memoization re-use).</li></ul></li></ul></li><li>Frequency and redundancy of Object serialization/allocation: Re-<em>using</em> objects instead of re-<em>generating</em>.</li><li>Memoizing idempotent tasks<ul style="list-style-type: square;"><li>De-serialization work to re-constitute THE SAME stringified JSON object is an idempotent task.</li><li>Re-factoring/shaping cached data into a new Object structure</li></ul></li></ul><p><br /></p><h2>Explaining the Behaviors of Apollo and NodeJS in microquery-heavy page load sequences</h2><ol><li>The whole point of memoization is to absorb the impact of duplicitous redundant activities objects in near-concurrent usage scenarios<ol><li>Prevents cache stampedes</li><li>Improves performance by<ol><li>Reusing existing memory spaces already allocated for reusable objects</li><li>Avoiding executing a task twice simply because two resolvers require the same data at the same time.</li></ol></li></ol></li><li>Micro-query context objects are, by nature, highly isolated and maximally limit object reuse (since each context has its own memoized map).</li><li>Consequently, more objects are instantiated, and more calls to expensive serialization and/or processing/utility jobs are called.</li><li>HTTPDataSource exacerbated this problem because it failed to memoize tasks<ol><li>Ergo, async field resolvers executed in the same Promise.all() frame spent time in JSON.parse() for the same object at the same time.
