## How to login impersonated users?

#### Requirements

-   We need the user to login in such a way that Odyssey can detect that the user is impersonated.
-   Odyssey needs to be able to identify the impersonator.
-   Must be impossible for impersonators to "escape" impersonation mode and actually login as the user they are impersonating using the credentials/tokens they have access to on.
-   Resdesk and RDK2 need to be able to generate the link that impersonators will use

**Assumptions**:

-   We need to update Odyssey to also look at both the impersonators plannerId and the user they are impersonating when running graphql queries.

#### Possible login flow for impersonators:

1.  User clicks the "impersonate user" button in Resdesk / RDK2
2.  Resdesk / RDK2 calls out to a passkey-auth endpoint to generate a jwt that will include all the details we need to know about the user we are going to impersonate.
    1.  We will need to pass along the eventId we want to bring the impersonator to.
    
3.  Users browser will navigate to Odyssey and pass this JWT as a query parameter.
4.  Planner portal will get passkey-auth to decode the JWT and store the impersonated users details in a context. It will navigate to the specified event.
5.  We will use the impersonators cvent-auth from resdesk / RDK2 to log in, but the graphql auth directives will be updated to also look at both users and only show information that overlaps with the two users.  
    1.  Most resdesk users do not have plannerIds, if we ever came up with a way for handling users with no ids we will need to re-use our implementation. If not we will need to figure out how to handle this.

#### Changes needed for this login flow to work:

-   We will need to update microservice endpoints like the isEventLevelPlanner endpoint to not throw errors when we are trying to impersonate users.
    -   We will need to override the checks they do to see if the bearer token is allowed

## How to indicate to the user they are in impersonator mode

-   This should be easy to accomplish by looking at the response from decoding the jwt token.
    -   We can use graphql caching and a react context to avoid making this call all the time.
-   As described in the original draft wiki for the impersonation mode, we can add a banner to the top of the site that will use the value from the context to decide on whether or not to show.

## UI Sections to hide for impersonated users

The following features/pages will need to be hidden for impersonated users:

-   Event list page
    -   No point in showing this since impersonators should not be able to see the events and there isn't anything they can really do to help users from this page.
-   Reports **(TBD)**
    -   There isn't much point to allowing reports to be run by impersonated users if the data is going to be different than the real user they are trying to help out.
-   Iframe pages
    -   Getting impersonation working in old planner portal is not be worth the effort.

## How to block impersonated users from seeing things they shouldn't

For queries that may show things the user should not see, We will do two calls, one for the impersonator and one of the user being impersonated. We will take the overlap between these two queries and use that as what the impersonator will see.

## Logging impersonator actions

**For now, the only things that can be changed from within Odyssey are the user details and the existing way of using the pkUserId and timestamp should be sufficient.  
In the future once we start to move more pages over to Odyssey this will not be enough and we may want to look into the solution described below.**

-   Until we move to the new logging approach, will need to update mutations to use a bearer token that contains the impersonators userId so that the DB will show modifications as being done by the impersonator.

Part of the requirements for this feature are that we need to have thorough logs for any changes the impersonator does on behalf of the user they are impersonating.

The current way of logging changes in the DB will not allow us to log all the details we need for impersonators. (It only stores the pkUserId and timestamp of the latest change)

It may be best to create a new table (must be postgres) dedicated to logging the actions of impersonated users.
