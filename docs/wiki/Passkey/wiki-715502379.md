# Feature Introduction

The Passkey product group already has [a detailed description of this feature](https://wiki.cvent.com/display/PASKY/Create+Event+from+Rooming+List+Workflow) and it's benefit to adopting customers. The initial iteration of Creating an Event from Roomlist will borrow as much backend workflow as it can in order to limit the time-to-market latency introduced by new backend architecture.

New technical terms and concepts will be introduced in this design. Among the most important new terms is **EMO**, or _Event Metadata Object_.  An EMO is a standardized API-grade event descriptor that is intended to be representative of Passkey Events in the passkey system for import and export purposes.  It is intended to be a normalized profile of an event which can be used to create, add to, or report on event profile information in Passkey.

In this document, we will break the effort for this feature into development **milestones**.  A _milestone_ is a checkpoint along the path to complete functionality that delivers something fluidly demonstrable (albeit incomplete) to the customer, yet alludes to and foreshadows additional remaining work that is yet to be completed.  Milestones are constructed and delivered according to Product priority and UX collaboration, typically with architecture priorities being applied in later milestones in order to expedite value to the customer earlier in the dev cycle.  A met milestone is almost always a demonstrable accomplishment (hence the name), but note that some milestones are 'special' in that they are not only demonstrable, but they are also _usable_ by selected customers within an experimental context. Obviously, not _all_ milestones can be suitable for this sort of public exposure.

Understanding what IS and what IS NOT deliverable for a particular milestone is important for constraining scope and for alleviating confusion.  Note that it is _normal_ for high-priority work to be left out of a milestone for various reasons, but this is generally planned on the promise that said work will be completed in a subsequent rollout in the near-to-mid term.

A Milestone Increment can also sometimes serve as a rallying point to regroup and discern the next most important objectives (especially when those objectives and requirements are not perfectly understood at the onset).

The milestones for this particular project are set out below.

This endpoint fetches row data in the raw file according to the 'startingAt' and 'maxFetch' pagination values provided, AND according to the subset of mapped row field values specified by the 'fetchedFields' array type query param.

The 'fetchedFields' are intended to specify PASSKEY fields, such that the endpoint implementation uses the file's previously-generated field mappings to resolve which values to fetch from which mapped columns.

Normalized fields have the advantage of an assigned data type, which is tracked by an in-code enumeration that lists all mappable Passkey fields along with their corresponding data type.

If the 'agg' query parameter is passed, then we use each mapped field's data type to automatically determine how to aggregate based on the provided aggregation operator: MAX, MIN, or UNIQUE:

-   If checkinDate, use Date.compareTo()
-   If checkoutDate, use Date.compareTo
-   If numberOfRooms, use Integer.compareTo()
-   If hotelRoomType, use String.compareTo() with toLowerCase().

When 'agg' query parameter is provided, the client can anticipate that only one object will be returned in the JSON array.

  
Further, if the field in question is a resolvable field (e.g. hotel room type), then the values returned are not the raw values, but the normalized mapped values of the actual mapped passkey data values to which they are bound.

## Infrastructure: Dynamo DB table for stored column mappings

The passkey RLM service will require the service of a DynamoDB table.  If the project is not already configured with one, we will be required to add that infrastructure to the project.

-   Currently, the passkey-rlm-service does not store column mappings - when called, it simply generates them and returns them in an (XML) response payload back to RLM legacy WF application.
-   For this project, the same set of column mappings are going to be used to:
    -   Initially auto-map the input file to a subset of fields required for event creation, including (check-in date, check-out date, room type, and number of rooms).
    -   Display the mapped fields to the user for approval
    -   Apply any _manual_ overrides the user provides to the mapping and re-display
    -   Show/Edit the mappings again in RLM once the event is created.
-   Rather then generate and re-generate the mappings for each use, we should generate them once, and store them.

### Infrastructure: Raw Data Files

The raw data of imported files needs to be stored somewhere, and it needs to be reference-able for mapping and data extraction purposes.  For the time being, we will create a simple and _temporary_ custom S3 file store in the passkey-rlm-service to house these files.  **We will not be able to deliver this feature to customers insofar that we are using this S3 bucket to keep customer data.**

There is some momentum towards building a 'safe' storage location for these files in the ECommerce VPC, where GDPR-sensitive PI can be managed securely and where PCI data - namely Credit Card data - can be substituted for tokens prior to storage.

This work is roadmapped for the last half of 2025.

### Infrastructure: New Infra For Managing Event Metadata Objects (EMOs)

-   This is the object that Pavel currently calls the 'Large Block'.
-   EMOs are formally-modelled JSON objects that contain event metadata which can be parsed from source documents (such as Room Lists or RFPs).
    -   Intended to be source-agnostic and universal for event, hotel, inventory and reservation provisioning purposes.
-   It may not be immediately important to store these objects long term, but this will be a topic that comes up in the future and we may want to look into it.
    -   We can consider an HTTP caching layer in the endpoint that generates EMOs, since we'll likely be fetching and re-fetching the same object in this workflow multiple times in succession, but we may not need that, either.
-   We will either store these in our own custom s3 bucket, or we will store them using the Cvent File Upload service, depending a pros/cons analysis.

## Mutation Workflows

This section is intended to describe the workflows that affect changes to the system and to user data, and how these flows map on one side to UI activities, and on the other to Apollo Mutation operations.

### Uploading A File

**UI Activity**: In this activity, the user has already clicked the 'Upload' button at the top of the Requests Management interface. This action brings the user to an upload file panel where they can select the file they wish to upload and submit it.

**Integrated System Actions**: The 'Upload File' widget in this panel will be integrated with a new 'upload' API endpoint in the RDK2 NextJS server (which we must build), and this will call our new room list upload API endpoint to keep the file in S3.  NOTE that this will NOT be a GraphQL mutation - just a simple upload file API in NextJS. The NextJS API will respond to the browser with a successfully-uploaded file handle, or _**file id**_.

### Binding the File to a new request and constructing initial mappings

**UI Activity**: In this activity, the user has just uploaded their file successfully using the file upload widget, and they have provided metadata values in the form inputs alongside the widget.  On the same screen, the user clicks the 'Next' button to proceed to the next page of the wizard.

**Integrated System Actions**: The 'Next' button will be integrated with a GraphQL mutation that will call multiple API methods in sequence using the file handle that was generated in the previous workflow:

-   CREATE initial header mappings and column value samples for the uploaded file.  Metadata values entered by the user on the previous screen are provided to the endpoint and persisted as part of the mappings payload.
-   CREATE the Request and bind it to the uploaded file using the newly-obtained file handle / file id.
    -   'Binding' the uploaded file the request is simply a matter of storing the file ID as a property of the Request record.
    -   Request object also potentially includes 'foreign key' for mappings, if mapping key differs from file id.
-   Mutation operation should return all keys (file id and mapping id, if they're different).

### Mapping The Headers

**UI Activity**: In this activity, the user has proceeded to the next page, where they are expected to confirm header mappings pre-mapped for them via the previous mutation operation.  The user may make an alternate selection if the original automappings are incorrect, or they may proceed without changing anything, if they determine that our automapping applied the right header bindings throughout.  In either case, they will click 'Next' to proceed to the next screen

**Integrated System Actions**: When the user clicks next, we determine if the user has applied any material change to the mappings we generated earlier.  If not, no mutation call is necessary.  If the mappings have been modified, we will capture the changes to a call to the PATCH endpoint, updating the 'piece' of mappings data that the user has modified.

### Mapping The Room Types

To produce this screen, there will be 3 primary GQL queries:

1.  Fetch UNIQUE aggregate of the room types column (to produce room type mappings)
2.  Fetch MIN aggregate of the checkin date column
3.  Fetch MAX aggregate of the checkout date column 

_**Note**: I currently do not see a place for the user to confirm the event start/end dates in the latest version of the UX design._

**UI Activity**: The user uses our new UI to assign unique room type names found in the room list to actually Passkey library-level room types fetched by another query.  The user is also going to confirm the start and end dates proposed by the system (using the MIN/MAX agg values fetched previously).  With all of this confirmed, the user clicks 'Next'.

**Integrated System Actions**: When the user clicks next, we call a mutation that will perform a couple of tasks:

1.  Invoke the mappings PATCH endpoint to provide the existing mapping record with the manual room list mappings that the user provided.
2.  Invoke the request PATCH endpoint to provide the existing request record with sanitized EMO values for event start, event end, and (perhaps) room types.

  

# Milestone 3: Create Event and Reglink Integration

The third milestone of this project is potentially special in that it delivers a customer-useable but stripped-down 'Create Event from Roomlist' function that is (initially, for this milestone) build into the existing 'Create Event' wizard in RDK2.  This wizard will be extended to launch a new, small set of modal panels when the user clicks on a new option in the wizard to create the event from room list.

This milestone is where we adapt the existing Reglink endpoint to the new Event Metadata Object (EMO) schema and call it in order to create events from room list.

## Create Room Block endpoint in passkey-reglink service

-   There is an [existing endpoint in our passkey-reglink service](https://stash.cvent.net/projects/PA/repos/passkey-reglink/browse/passkey-reglink-service/src/main/java/com/cvent/passkey/reglink/resources/RoomBlockResource.java#65) that already bundles event creation, attendee type creation, hotel setup, block creation and planner association together in one step.
-   Despite the fact that this endpoint does a couple of extra things we don't need, we nevertheless suspect that we can use it virtually as-is in order to suit our purposes here.
-   For the first milestone, the goal would be to understand and make whatever tuning necessary to make this endpoint work for our Create From Roomlist use-case (without breaking existing Reglink and IB use cases!)
-   In a subsequent milestone, we will generically extract this endpoint into its own STEP Function wrapper and refactor it to use GQL queries for data fetching.

# Milestone 4: RDK2 → RLM Integration

Finally, we need to be able to kick off an in-flight RLM session from RDK2 and load it with the mappings and data gleaned from the previously parsed raw data file.  The user will then be able to use the RLM interface to complete the process of importing their reservation list and provisioning them with inventory from the newly-created event.

We have two options here:

1.  Preferred option: Create Hook in RLM that can be called to import previously-mapped EMO to its Oracle DB. Then we can call that hook after the event is created in our create event workflow.
2.  Fallback option: Update our new 'PUT mappings' endpoint to optionally export the mapped file to RLM Oracle DB directly (with event id of -1)
