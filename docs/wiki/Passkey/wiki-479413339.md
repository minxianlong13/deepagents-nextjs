<p>This Wiki is to track how we will reset cache entries on Apollo server when source data is changed in Resdesk.</p><h2>Admin-only Mutators</h2><p>The cache-busting solution proposed here utilizes GQL Mutators to manually manipulate the Apollo backend caches.  Each data source-level entity will have a corresponding mutator, which will requre input parameters that align with cache entry unique keys.</p><p>For instance, say we have an <strong>event-api</strong> data source in Apollo.  This API has a <em>getEventInfo(id)</em> API method that fetches an Event Info response from the passkey-event-service microservice.  We've configured our cache to keep this value for 48 hours in its response cache, such that any subsequent call to <em>getEventInfo() </em>with the same Id will yield the same response.</p><p>In order to bust this cache, we would create a new Mutator that accepts an eventId parameter, re-constitutes a cache key for the aligning request using that id, and then proceeds to delete that entry from the cache.</p><ac:structured-macro ac:name="code" ac:schema-version="1" ac:macro-id="fd6dd66d-b577-40ab-ad86-5531ef049fe3"><ac:plain-text-body><![CDATA[type Mutation {
   bustEventInfoCache(eventId:ID):String @auth(methods: [BEARER])
}]]></ac:plain-text-body></ac:structured-macro><p>Armed with the new mutator, we can use a GQL client to execute the mutation in Resdesk wherever we affect event info (for instance, the 'Save' button after an organizer changes the name of their event).</p><h2>Cache Management APIs</h2><p>In order for our mutators to do what we want them to do, we need our Data Source APIs to provide admin-grade cache management functions that the mutators can use to manually manipulate the cache.
