This Wiki is to track how we will reset cache entries on Apollo server when source data is changed in Resdesk.

## Admin-only Mutators

The cache-busting solution proposed here utilizes GQL Mutators to manually manipulate the Apollo backend caches.  Each data source-level entity will have a corresponding mutator, which will requre input parameters that align with cache entry unique keys.

For instance, say we have an **event-api** data source in Apollo.  This API has a _getEventInfo(id)_ API method that fetches an Event Info response from the passkey-event-service microservice.  We've configured our cache to keep this value for 48 hours in its response cache, such that any subsequent call to _getEventInfo()_ with the same Id will yield the same response.

In order to bust this cache, we would create a new Mutator that accepts an eventId parameter, re-constitutes a cache key for the aligning request using that id, and then proceeds to delete that entry from the cache.

Armed with the new mutator, we can use a GQL client to execute the mutation in Resdesk wherever we affect event info (for instance, the 'Save' button after an organizer changes the name of their event).

## Cache Management APIs

In order for our mutators to do what we want them to do, we need our Data Source APIs to provide admin-grade cache management functions that the mutators can use to manually manipulate the cache. This is possible with both **HTTPDataSource** and **RESTDataSource** caches, per the following initialization instructions:

### Override initialize() callback

Both RESTDataSource and HTTPDataSource implementations expose an initialize() callback that API implementors can use to add their own custom initialization routines.  Further, these callbacks are provided with a DataSourceConfig object that provides initialization context to the data source, _including a reference to the cache_.  Therefore, our data sources can create a callback implementation like this to track its own handle to the config (and in turn, the Apollo cache):

Now that our data source has a handle to the cache, we just need to know a little something about how cache keys are generated for our requests.  Mercifully, the cache key behaviours of HTTPDataSource and RESTDataSource are largely (but not exactly) the same - we'll get to the differences in a moment.

### Override the cache key gen callback

In both **HTTPDataSource** and **RESTDataSource** cases, each data source implementation that wants to manipulate the cache uses an overridable method that both data source base implementations provide in order to generate cache keys for requests.  The simplest callback implementation is to just call the super.

  

**About the cache key callbacks:**

By default, the behaviour of both of these callbacks is to use the HTTP request object to generate a cache key.

-   RESTDataSource uses the _whole_ request URL (including query params) to make cache keys unique
    -   All cache keys are prefixed with 'httpcache:'.
    -   The url is provided to your custom callback as a complete string: **Request**._url_
    -   _'super.cacheKeyFor()'_ uses the prefix _plus_ the whole request url to construct a cache key.
-   HTTPDataSource likewise constructs a cache key using the request URL:
    -   No prefix for cache keys
    -   The url is provided to the custom callback via **Request**.origin and **Request**.path.
    -   '_super.onCacheKeyCalculation()_' uses the origin _plus_ the path to construct a cache key.

You do not _have_ to override the cache key gen callback, but doing so provides your impl class with explicit management responsibility of those keys, which makes it a more 'wholesome', readable/maintainable solution (code for reconstituting cache keys for flushing the cache can be centralized/unified with this body of your callback.

### Construct the API

Now that you have the means for accessing the cache and the knowledge of how keys are created, you can implement admin data source API methods that will search the cache for entries that align with a set of inbound parameters. This method will use the incoming params to re-constitute cache keys and call the cache's remove() method to delete the item and force the data source to issue a microservice request the next time the item is requested.

  

### Construct the Mutators and Resolvers

Once all data source APIs have been covered by a corresponding cache-busting API, the next step is to create API\_KEY-authorized mutators that will publish this functionality to the rest of our distributed Passkey system.  Mutators do NOT have to map 1-to-1 with cache-busting methods - a single mutator may call multiple methods to clear multiple entries.  However, the nature of the data affected by the change should impact the granularity of the mutator.  For instance, room type image changes should not force a cache reload of textual event or hotel info - it should be segregated into its own mutator so that the lifetime of legitimate 'not-stale' cache entries can be maximized.
