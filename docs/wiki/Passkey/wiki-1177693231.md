## Decision Summary

The File Uploader owns:

-   File storage and retention
-   Technical text extraction
-   PCI detection and tokenization
-   Participant and file ownership validation
-   Enforcement of approved extraction definitions

The File Uploader does **not** accept caller-provided prompts, field lists, extraction types, or JSON schemas. It also does not create or persist application entities.

The access token contains exactly one **`extracttype`** claim. This claim selects an allow-listed extraction definition, such as **`contract`**. A missing, blank, ambiguous, or unregistered claim is rejected before the file is accessed.

This boundary provides approved callers with a PCI-safe alternative to downloading the original file while preventing request data from expanding the caller’s permitted access.

> **Approval required:** Prompts, field names, and response templates are business-aware configuration. Storing or executing them through the File Uploader represents a deliberate change from the earlier text-only proposal and must be explicitly approved.

## Architecture Decision Requiring Approval

The proposed registry introduces business-aware configuration into a workflow executed by the File Uploader. Although the endpoint and orchestration code remain generic, prompts, field names, and response templates can encode application-specific behavior.

The team must explicitly choose between the following models:

Model

PCI-zone responsibility

Business intelligence

`PROMPT_PACKAGE`

Extract and PCI-process text, then return an approved prompt package

Executed outside the PCI zone

`FIELD_QUERIES`

Extract text and execute registered queries through an approved provider

Partially executed inside the PCI-zone workflow

Text-only

Extract and PCI-process text only

Entirely outside the PCI zone

  

The recommended long-term design is a governed registry outside the File Uploader codebase, accessed through a read-only adapter. Registry definitions should be versioned, reviewed, auditable, and independently deployable.

The File Uploader should cache and enforce definitions. It should not contain application-specific Java models, controller branches, or orchestration logic for individual extraction types.

The in-process definitions included in this ticket are executable examples until the following are confirmed:

-   Registry ownership
-   Persistent storage
-   Approval workflow
-   Versioning strategy
-   Deployment process
-   Audit and rollback requirements

## 4B. `FIELD_QUERIES` Response

A registry definition using `FIELD_QUERIES` contains an ordered map in which:

-   Each key becomes a response field.
-   Each value contains a predefined extraction query.
-   The configured provider executes the registered queries.
-   The generic endpoint assembles the results under `data`.

> This is used in case we need to rely on smaller queries, not full prompt   
>  

The Java client returns a generic response envelope:  
 

```
FileExtractionResponse response = client
    .extractFileText(bearerToken, 12345L, fileId)
    .execute()
    .body();

EventMetadata eventMetadata = objectMapper.convertValue(
    response.getData(),
    EventMetadata.class
);
```

  
 

A different extraction type may return a different `data` structure. The endpoint and generic response envelope remain unchanged.

Consumers use `extractionType` and `definitionVersion` to select and validate the appropriate domain model.

Every string returned by the field-query provider is PCI-scanned again before response serialization.

# Registry Contract

Each extraction definition contains the following fields:

Field

Meaning

`type`

Stable, case-insensitive key matching the token claim

`definitionVersion`

Immutable version of the approved registry definition

`mode`

`PROMPT_PACKAGE` or `FIELD_QUERIES`

`extractorVersion`

Approved provider or parser version; callers cannot override it

`supportedFormats`

Allowed PDF and/or Excel formats

`prompts`

Predefined prompts used by `PROMPT_PACKAGE` mode

`expectedResponse`

JSON template describing the expected application response

`fieldQueries`

Ordered map of response keys to predefined queries for `FIELD_QUERIES` mode

  

Definitions fail startup or registry-loading validation when any required configuration is missing or inconsistent, including:

-   Missing or duplicate type
-   Missing definition version
-   Unsupported mode
-   Missing supported formats
-   Missing prompts or response template for `PROMPT_PACKAGE`
-   Missing field queries for `FIELD_QUERIES`
-   Configuration for more than one response mode

The current `PredefinedExtractionRegistry` is an in-process implementation created for this ticket. It is exposed through an `ExtractionRegistry` interface so it can later be replaced by the approved shared-registry adapter without changing the endpoint or orchestration service.

## Conceptual Shared-Registry Definition

  

  

If the File Uploader must produce structured contract data, the definition can instead use **`FIELD_QUERIES`** with registered fields such as:

-   `name`
-   `start`
-   `end`
-   `planners`
-   `hotels`

A registry definition has exactly one response mode so that its response contract remains predictable.

Registry changes should require:

-   A named owner
-   Security review
-   An immutable version
-   Audit history
-   A rollback mechanism
-   Compatibility documentation
-   Controlled production rollout

Production tokens should ideally authorize both the stable extraction type and an approved definition version. This prevents a registry update from silently changing the response contract for an already-issued token.

This could be done in case we will not use LLM extraction and Rely on other technologies such as Textract or other tech.

# PCI Behavior

Raw extracted text is never returned before PCI processing.

If a card number is detected:

1.  The service replaces it with the existing Wallet partial-card token representation.
2.  The response sets `pciDataTokenized` to `true`.
3.  Only tokenized values may cross the PCI boundary.

If tokenization fails, the entire request fails and no extracted text or structured result is returned.

This behavior complements the available upload profiles:

-   A future PDF PCI-scanning profile may reject the upload and set its status to `ERROR`.
-   An upload in `ERROR` status cannot be processed because the extraction endpoint accepts only `READY` files.
-   For flows where tokenization is approved, the detected card value remains inside the PCI boundary and only its tokenized representation is returned.

The service must never log:

-   Raw document text
-   Extracted field values
-   Card-number values
-   Prompt-package content
-   Provider response content
-   Provider exception details that may contain document data

# Implemented in GROUP-130035

GROUP-130035 adds profile-driven extraction authorization as an additional enforcement layer. It does not replace token-claim authorization or the extraction registry.

-   Each `UploadProfile` declares supported extraction types through `supportsExtractionType(extractionType)`.
-   `FileUploadService` resolves the upload profile and checks whether the requested extraction type is permitted.
-   `FileExtractionService` rejects extraction with `403 ExtractionNotAllowed` before provider execution when the resolved profile does not permit the requested extraction type.
-   The default profile permits `EventContract`. The PCI and example profiles do not currently permit extraction.
-   Support for additional upload profiles and extraction types remains follow-up work.

The ticket requires existing `EventContract` extraction and deterministic stub behavior to remain unchanged.
