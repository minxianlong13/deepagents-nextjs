<p>Nov 3, 2023</p><p><em><strong>&amp;TLDR;</strong> A Fragmenting Oracle DOMAIN Index took down our Load Test Database and caused strange environment behaviors.  Rebuilding the Index fixed the problem.</em></p><p><br /></p><p><ac:image ac:height="250"><ri:attachment ri:filename="1200px-Morning,_just_after_sunrise,_Namibia.jpg" /></ac:image></p><p>Dzmitry had to halt his RDK2 Load Test this morning because his TXN DB started to spin out of control, pegging the CPU at a hard 100% until connections and associated processes had to be manually killed.  After investigating with the DBA team, the problem was identified to be a mal-performing rogue event search query being made by passkey-event-service on behalf of RDK2.</p><p>The issue has some truly bizarre qualities that are mystifying and fascinating - and maybe even relevant - and they'll be mentioned here.  But first, the preamble:</p><ol><li>Dzmitry's load test emulates 20-30 RDK2 users, stepping up gradually from lower number of requests to higher number of requests</li><li>User activity is emulated by having load users interact with the RDK2 home page in various ways, including clicking on advanced search options and getting advanced search results in the event grid.</li><li>After several minutes of load testing, Dzmitry noticed query times going up unusually and exponentially.  When he checked his DB stats, he saw that the TXN db was pegged at 100%.  When he killed the load, the CPU remained pegged at 100%.</li></ol><p>Our DBA team identified the problem at the Oracle level: One SQL query shape in particular was working it's way up to 20 mins of latency, and was being called over and over again by Dzmitry's load tests.  So, the same 20-minute mal-performant query was getting called over and over in a frequency sufficient enough to take down the DB.</p><p>Datadog revealed the problematic query to be an event search query emanating from the passkey-event-service.  DD was good enough to give us the precise invocation URL used by the UI request to spawn the query, so we were able to drop that URL into Postman and run the query ourselves manually.</p><ac:structured-macro ac:name="code" ac:schema-version="1" ac:macro-id="2ad33874-83a4-4adb-926d-a3e0a386f47a"><ac:plain-text-body><![CDATA[GET https://passkey-event-service-core-passkey-dev.us-east-1.lb.core.cvent.org/sg50/passkey-event/v1/events?
