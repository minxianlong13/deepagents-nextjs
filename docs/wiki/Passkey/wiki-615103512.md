Nov 3, 2023

_**&TLDR;** A Fragmenting Oracle DOMAIN Index took down our Load Test Database and caused strange environment behaviors.  Rebuilding the Index fixed the problem._

  

Dzmitry had to halt his RDK2 Load Test this morning because his TXN DB started to spin out of control, pegging the CPU at a hard 100% until connections and associated processes had to be manually killed.  After investigating with the DBA team, the problem was identified to be a mal-performing rogue event search query being made by passkey-event-service on behalf of RDK2.

The issue has some truly bizarre qualities that are mystifying and fascinating - and maybe even relevant - and they'll be mentioned here.  But first, the preamble:

1.  Dzmitry's load test emulates 20-30 RDK2 users, stepping up gradually from lower number of requests to higher number of requests
2.  User activity is emulated by having load users interact with the RDK2 home page in various ways, including clicking on advanced search options and getting advanced search results in the event grid.
3.  After several minutes of load testing, Dzmitry noticed query times going up unusually and exponentially.  When he checked his DB stats, he saw that the TXN db was pegged at 100%.  When he killed the load, the CPU remained pegged at 100%.

Our DBA team identified the problem at the Oracle level: One SQL query shape in particular was working it's way up to 20 mins of latency, and was being called over and over again by Dzmitry's load tests.  So, the same 20-minute mal-performant query was getting called over and over in a frequency sufficient enough to take down the DB.

Datadog revealed the problematic query to be an event search query emanating from the passkey-event-service.  DD was good enough to give us the precise invocation URL used by the UI request to spawn the query, so we were able to drop that URL into Postman and run the query ourselves manually.

  

Even without server load, running the service endpoint once in isolation was enough to reveal the problem: The microservice went away to process the request and never came back.  The service's load balancer gave up waiting for it and returned an HTTP 504 to Postman.

8 minutes later, the service gleefully reported to Datadog that the query was finished and ready for use.

Executing the raw query in a local dev tool like SQL Developer yielded query response times of 1.5 to 3 seconds.  This was completely unexpected, since all the evidence when executing the same query from the event microservice implicated the database as the malperformer (including the long query times reported by Oracle server, and the high CPU use.

  

To date, I am still not able to explain this discrepancy, but both Dzmitry and Deepender were on the call and saw it reproducably: Execute the query in the microservice, expect 20 mins execution time.  Execute the same query in SQL Developer from my local laptop, 1.5 to 3 seconds.  My best guess is either env-specific JDBC driver settings or the use of Prepared Statements is somehow driving or directing the query plan on the server side.

The performance problem with the query has to do with this clause, near the bottom of the query:

Problematic Query Fragment 0) \]\]>

This clause is searching for events that have a participating hotel whose name matches a user-provided string ('test'). This test is performed by an Oracle DOMAIN-type index that is synced with table changes every four hours.  DOMAIN indexes typically provide much faster text searching than traditional wildcard or regex pattern searches, but in this case, the presence of this clause in the above search increased the response time by orders of magnitude.

The problem, it turns out, is that the index was old and fragmented. Although having been synch'd and updated regularly, the index had not been rebuilt since it was initially deployed 2+ years ago.  Deepend took a few minutes to invoke an Index Rebuild in Oracle EM (Enterprise Manager), and the problem was solved.

Conversations in StackOverflow [here](https://stackoverflow.com/questions/4078712/performance-issues-with-jdbc) and [here](https://stackoverflow.com/questions/1339549/slow-query-in-java-by-jdbc-but-not-in-other-systems-toad?noredirect=1&lq=1) seem to indicate that poorly-typed PreparedStatement parameter substitutions may cause the query plan optimizer to skip using an index because it thinks it can't perform the type conversion efficiently enough to make the index use worthwhile.  This could be particularly true when the Index performance is already degraded (Oracle keeps track of these things and considers them in query plan creation), and it might explain why we were seeing two very different performances of this query between SQL Developer and the deployed microservice.

From above links"_Check to make sure someone hasn't set the property **oracle.jdbc.defaultNChar=true**.  This is sometimes done to resolve unicode problems but it means all columns are treated as nvarchars. If you have an index on a varchar column, it won't be used because oracle has to use a function to convert the character encoding._"

  

Once the index finished rebuilding, the same query that took 20 minutes to run in the passkey-event-service now took a half second.

In writing this, my purpose is to document the experience and the side effects of this issue in the sg50 environment so that we'll know what to do next time it happens without having to spend 4-5 hours of research on it.  Also, it serves as a warning that we should consider maintaining our Indexes with scheduled weekend rebuild jobs in order to prevent a similar experience from happening in our customer-facing environments.
