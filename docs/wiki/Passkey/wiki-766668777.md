# Instructions

This page is a place to build and track mappings of GQL Schema entity types that are to be ported from our various CDF applications into new subgraph schemas.  These fields need to be enumerated here in the mapping wiki so that we can identify and adjust for duplicates, or otherwise refactor as we see fit.

Each team is to fill out the document below with new 'Subgraph Entity' sections (and corresponding tables) for each Schema entity in their application.

**NOTE: Target Field Name is a column to reduce the Source SchemaObject.FieldName into one common naming. ie; passkey-rdk2 and passkey-planner-portal-app both have Event.Name. If one had slightly different SchemaObject name, we would still want to map both to Event.name.** **If you are adding to an existing subgraph entity on this list for your app, and find that the current Target Field Name is not satisfactory, please start a discussion in #passkey-graphql.**

## Schema Section

-   Find the Business domain that will house the schema entity, and look for that domain's corresponding section in the document below
-   If the entity is not already considered in the section, create a new sub-heading for the entity, along with a new table in which to apply entity field details.
-   Be alert for duplicates and overlap!  Make notes where potential overlaps are detected.
-   If the field value maps to another entity, make note of that in the notes field as well.

## Queries/Mutations Section

-   List all queries and mutations that your application uses, along with the intended response value entity type.

# Schema

Each table below is representative of a Schema object that we intend to create in the appropriate business subdomain's subgraph. Before adding a new header and table for your Schema entity below, PLEASE determine that there is not already an existing entity that would be appropriate to host your app's required fields.  It is _good_  to unify the graph insofar that we are mindful of permissions and recursive relationships (relationship edges should always be manifested in the parent object, NOT in the child object).

# Queries/Mutations

Queries are MANAGED entry points into the graph.  Applications are allowed to share the same query, and they SHOULD, _even if_  they're requesting different data from the same object.  Once they are all accounted for, this chart will give us an opportunity to look for consolidation opportunities and unify the entry points.

Remember, we are looking for the QUERY name, here - NOT the operation name.  The difference is that queries are enumerated in your app schema files, while operations only appear in your app's operation files.

Note: Consolidation eventually needs to consider permissions differences between apps as well, but we still need a starting point for those discussions, so please track queries here.
