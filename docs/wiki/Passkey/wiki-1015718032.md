## Overview

The Passkey Event Request Workflow is a serverless AWS Step Functions-based system designed to reconcile relevant details from arbitrary external input documents (such as room lists, RFP-type contracts, flight manifests as well as other data sources) to Passkey Events. 

The workflow processes these input documents through an **Event Request** entity, which follows the EMO (Event Metadata Object) document specification and is intended to represent source document information in a normalized and consumable way.  Documents are processed in source-type specific ways in order to produce EMOs in various degrees of partial completion.  Once the system has extracted, solicited and/or collected enough qualifying data to create or update a Passkey event, such steps can be automatically taken via the workflow.

The system is designed to be idempotent, and AI-agent-friendly, extensibly supporting multiple request types and iterative data accumulation.

## Architecture Components

### API Gateway Integration

The system exposes a REST API v1 endpoint (`POST /v1/event-requests`) that serves as the entry point for workflow execution:

**Endpoint**: `POST /v1/event-requests`

**Authentication**: Token-based Lambda authorizer validates bearer tokens via Cvent Auth Service

**Input Contract**:

  
`{   contextInputs: {     httpRequestId: string;       // Generated by API Gateway     accessType: string;          // From authorizer     accessToken: string;         // From authorizer     userId: string | number;     // From authorizer     participantId: string | number; // From authorizer   },   clientInputs: {     assemblyOnly: boolean;       eventRequest: EventRequest;  // Follows existing Java Model for interface of same name   } }`

**Security Model**: The API Gateway VTL request template separates client-provided data (`clientInputs`) from context-derived authentication data (`contextInputs`), preventing credential spoofing. Clients cannot override authentication fields as they are injected from the authorizer context.

**Extensibility**: Meanwhile, new request types (and their corresponding fields) can be added by:

1.  Extending `EventRequestType` enum
2.  Creating new `*EventRequestClientInputs` interface
3.  Adding corresponding workflow logic (see below)

### Step Functions Workflow

The workflow implements a 6-step pipeline with compensatory rollback capabilities:

#### Step 1: Load-In (`step1LoadIn`)

**Purpose**: Fetch existing EventRequest from passkey-event-data service

**Input**: `EventRequestWorkflowInputs`

**Output**: Updates `EventRequestWorkflowEvent.dbRequest` with existing request (if found) or null

**Logic**: Queries passkey-event-data service using `requestType` and type-specific identifiers (e.g., `fileId` for ROOM\_LIST)

#### Step 2: Upsert Request (`step2UpsertRequestFromInput`)

**Purpose**: Create or update EventRequest in database

**Input**: Current workflow state with `dbRequest` from Step 1

**Output**: Updated `EventRequestWorkflowEvent.dbRequest` with persisted request

**Logic**:

-   If `dbRequest` exists: Performs PATCH update with new data from `clientInputs`
-   If `dbRequest` is null: Creates new EventRequest
-   Persists changes via passkey-event-data service
-   Supports partial updates for iterative data accumulation

**AI-Agent Friendly**: Allows multiple invocations to progressively build up EventRequest data

#### Step 3: Verify Request (`step3VerifyRequest`)

**Purpose**: Validate EventRequest completeness and determine next action

**Input**: Current workflow state with updated `dbRequest`

**Output**: Decision to proceed or terminate

**Logic**:

-   If `assemblyOnly === true`: Terminate (data collection mode)
-   If insufficient data for event creation: Terminate with validation errors
-   If validation passes: Proceed to Step 4

**Idempotency**: Enables "assembly mode" where requests can be built incrementally without triggering event creation

#### Step 4: Create Event (`step4CreateEvent`)

**Purpose**: Construct Passkey event from EventRequest

**Input**: Validated `EventRequestWorkflowEvent.dbRequest`

**Output**: Event ID from passkey-reglink service

**Logic**:

-   Checks EventRequest.eventId to ensure event hasn't already been created.
-   Transforms `EventRequest.eventMetadataObject` into passkey-reglink API format passkey-reglink API is already EMO-friendly.
-   Invokes passkey-reglink HTTP API to create event
-   Stores returned `eventId` in workflow state

#### Step 5: Patch Request Status (`step5PatchRequestStatus`)

**Purpose**: Update EventRequest with creation results

**Input**: Workflow state with `eventId` from Step 4

**Output**: Updated `dbRequest` with status='PROCESSED' and `eventId`

**Logic**: Persists final status to passkey-event-data service

#### Step 6: Post-Creation Callback (Choice Step)

**Purpose**: Execute request-type-specific post-processing

**Input**: Completed EventRequest with `eventId`

**Logic**: Routes to type-specific callback:

-   `ROOM_LIST` → `step6aRoomlistCallback`
-   `GML` → `step6bGMLCallback`

**Extensibility**: New request types add new choice branches

## Compensatory Flow

The workflow implements a cascading rollback pattern with 2 retry attempts per step before triggering compensation:

### Main Flow Compensation (Steps 1-5)

**Default Retry Policy**: Each step retries up to 2 times with exponential backoff (rate: 2)

**Compensation Chains**:

-   **Step 1 fails**: → `MainFlowFailed` (no compensation needed)
-   **Step 2 fails**: → `compensateStep1LoadIn` → `MainFlowFailed`
-   **Step 3 fails**: → `compensateStep2UpsertRequestFromInput` → `compensateStep1LoadIn` → `MainFlowFailed`
-   **Step 4 fails**: → `compensateStep3VerifyRequest` → `compensateStep2...` → `compensateStep1...` → `MainFlowFailed`
-   **Step 5 fails**: → `compensateStep4CreateEvent` → `compensateStep3...` → `compensateStep2...` → `compensateStep1...` → `MainFlowFailed`

**Compensation Responsibilities**:

Note: State may require separate dbRequestNew and dbRequestOrig attributes in order to support rollback.

-   `compensateStep1LoadIn`: Clear any cached request data from workflow state
-   `compensateStep2UpsertRequestFromInput`: Delete or revert EventRequest in database
-   `compensateStep3VerifyRequest`: Clear validation state/flags
-   `compensateStep4CreateEvent`: Possibility: Delete created event via passkey-reglink API
-   `compensateStep5PatchRequestStatus`: Revert EventRequest status to previous state

### Post-Success Compensation (Steps 6a/6b)

**Isolation**: Steps 6a and 6b failures do NOT trigger main flow rollback

**Compensation**:

-   **Step 6a fails**: → `compensateStep6aRoomlistCallback` → `PostSuccessCallbackFailed`
-   **Step 6b fails**: → `compensateStep6bGMLCallback` → `PostSuccessCallbackFailed`

**Rationale**: Event creation succeeded; callback failures should not undo the event. Compensatory steps handle cleanup of callback-specific side effects only.

## Data Flow

  
`API Gateway (POST /v1/event-requests)   ↓ [VTL Template: Inject contextInputs, preserve clientInputs] Step Functions StartExecution   ↓ Step 1: Load existing EventRequest → state.dbRequest   ↓ Step 2: Upsert EventRequest → persist to DB → update state.dbRequest   ↓ Step 3: Verify completeness   ↓ [if valid && !assemblyOnly && !eventId] Step 4: Create Event → eventId   ↓ Step 5: Update EventRequest status=PROCESSED, eventId   ↓ Step 6: Choice by requestType   ├→ ROOM_LIST: step6aRoomlistCallback  └→ GML: step6bGMLCallback`

## Key Design Principles

### 1\. Extensibility

-   Request types are enum-based and easily extended
-   Client input contracts use TypeScript interfaces with inheritance
-   Workflow choice step dynamically routes based on `requestType`
-   VTL template passes through all `clientInputs` fields without modification

### 2\. Idempotency

-   Multiple workflow invocations with same `fileId` update existing EventRequest
-   `assemblyOnly` flag enables data accumulation without side effects
-   Step 3 verification prevents duplicate event creation

### 3\. AI-Agent Friendly

-   Supports iterative data collection across multiple API calls
-   Partial updates allow progressive refinement of EventRequest
-   Validation step provides clear feedback on missing data
-   Stateful EventRequest entity maintains context between invocations

### 4\. Security

-   All input is JSON (data-only: no markup, no injections, no arbitrary scripts)
-   Authentication data isolated in `contextInputs` (non-spoofable)
-   Client data isolated in `clientInputs` (untrusted)
-   API Gateway authorizer validates all requests via cvent-auth
-   VTL template enforces separation of concerns

### 5\. Reliability

-   Automatic retries (2 attempts per step)
-   Compensatory rollback for transactional consistency
-   Post-success callbacks isolated from main transaction
-   CloudWatch (and Datadog) logging at each step

## Future Enhancements

1.  **Update Existing Events**: Extend workflow to support updating events (not just creation)
2.  **Additional Request Types**: Add support for new document types beyond ROOM\_LIST and GML
3.  **Async Callbacks**: Convert Step 6 callbacks to asynchronous processing for long-running operations
4.  **Validation Rules Engine**: Externalize Step 3 validation logic for dynamic rule configuration
5.  **Event Versioning**: Track EventRequest versions for audit and rollback capabilities
