## **Overview**

During the last few weeks, a series of merging and branching issues has significantly disrupted our normal workflow. These issues were severe enough to trigger the need to explicitly write down and reiterate our branching strategy to avoid similar problems from occurring again. After reviewing our branching strategy document and attending Brad's presentation, a few discussions transpired amongst team members and leaders. The intent of this document is to highlight some of the topics covered in those discussions and propose a series of changes to our branching strategy in order to circumvent and minimize some of our current risks and pain\-points.  
  

## **Identified issues**

### Release branch Creation

After listening to Brad and Anton's description of the process required to cut a new release branch, a few concerns were raised about how time-consuming and potentially error-prone this process was. The process goes as follows: Each release, a team lead is assigned to the "release branch cutting" duties. This responsibility is rotated between all team leads in order to balance the workload. It involves hand picking each certified ticket and merging the changes into the RELEASEITEMS branch one by one. Depending on the complexity of a release, this process can get very tedious and time consuming. The leads need to gather a complete list of every ticket that were certified and manually apply/merge each feature branch into the new release items branch.  Additionally, this introduces risk and duplication of work since merge conflicts that have already been resolved in QAI/CI by devs will have to be resolved again by the leads to the best of their knowledge.

### Risk and QE confidence

As a follow-up to the previous point, adding each certified feature/bug to the RELEASEITEMS branch creates a new code base that has never been tested before. Since each certified feature has never been tested against other in a clean environment (i.e. without uncertified code), QE would have to re-execute all the testing against the new release branch to achieve the same level of confidence.  Additionally, if any merge conflicts occurred during the release branch cutting process, the affected area would also need to be retested as there's no guarantee that the conflicts were resolved to be functionally equivalent. Since QE only has one week to validate the new branch, retesting each feature/bug/affected areas would be very difficult and a tremendous waste of duplicate effort.  We therefore assume these unnecessary risks and focus on doing higher-level testing.  Ideally, QE should be focussing on environment testing (e.g. DB, configs, etc) and performance testing at this point to grow the confidence that was already achieved in QAI/CI.

### Epic branch maintenance

Another concept that appears to be causing grief is the use of epic branches. From my understanding, we use epic branches to contain major features until they're ready for prime time. The idea of the process is to facilitate the release of the epic feature when it gets certified. Instead of merging each single feature that were created from the epic, our team leads would only need to merge the epic branch into the release branch and avoid having to merge dozens of smaller features. As a dev working on a feature, you create a feature branch off the epic branch and work on that branch. When done, the changes are first pushed to QAI for QE certification. Once certified, the dev needs to create a pull request into the epic branch. This is to ensure that the epic branch only contains certified code and be used for the release branch. The major concern with this is that developers need to remember to create a pull request (PR) and merge their changes into the epic branch after the fact. It sometimes can take a few days for a feature to get certified depending on its complexity. By that time, developers have moved on to other tickets and are prone to forget to do that final step of creating a PR for the epic branch.  Maintaining an epic branch across multiple releases also introduces merge conflicts, both downstream and upstream.  Downstream conflicts increase as a given release gets older since there's more chance that another feature/bugfix was made to the same files used by the epic.  Although this situation should improve drastically with 2-week releases.  For epic branches that spans multiple release, the epic branch needs to be synchronized with the master branch after each release, which also generates conflicts for any files modified in each branch.

### Accidental branch pollution

Using our current branching strategy,  we constantly run the risk of polluting a branch if a developer accidentally merges QAI upstream into their current branch or simply by creating a fresh branch from QAI.  We've recently had to spend a few days worth of work to revert all the features that were committed to an epic branch using un-certified QAI code.

## **Proposed Solution**

In order to circumvent some of the issues identified, I'd a like to suggest incorporating some of the qualities of GitFlow  branching strategy ([{+}](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)[GitFlow](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)) into our current branching strategy.  Our current way of manually merging all certified changes into a release branch is due to the fact that our development branch (QAI) is constantly in a polluted state where we have both certified and uncertified changes in it. With a few simple behavioural changes, we could adapt QAI into a clean development branch where only certified changes are persisted. This would have the advantage of allowing tech leads to cut release-candidate branches straight from QAI and greatly minimize the amount of work and risk involved in creating new release branches. No need to handpick each certified change and resolve numerous merge conflicts.  

  
Additionally, cutting a release branch from QAI would significantly increase our QE confidence since all the testing performed against QAI and would not be invalidated by creating a new code base. Each release branch would be continuation of QAI and QE could focus their release-branch testing efforts on environment and performance testing.  As a side-effect of using trunk-based development, the use of epic branches would become unnecessary since all the changes in the "trunk" are certified or about to become certified.  This would solve a multitude of conflict resolution and maintenance issues.

  
Finally, as we've seen a few months ago, merging QAI upstream is extremely dangerous and should be avoided. Although this "NEVER DO THAT" was heavily communicated lately, there is always the risk that someone might accidentally do it again. Using the suggested approach of keeping a clean development branch (QAI) would allow for this. Developer would be free to merge QAI into their working branch to sync up their code base. 

## **Implementation**

In order to keep our development branch clean at the time of cutting a release branch, we need to introduce the concept of a stabilization period. This stabilization period (usually 2-3 days) is intended to clean up QAI (when required) and wrapping up any remaining QE efforts to certify the final work in progress.  Communication (email/slack/etc) will be sent to inform all stakeholders (dev, qe, etc) when a given release enters the stabilization period.  At this point, all stakeholders should focus their efforts on branch stabilization (i.e. certification).  This means that all committed code needs to be certified or otherwise disabled (through feature flag or feature reversal) before the release branch cutoff.  Under special circumstances, a critical change may remain uncertified in the development branch for the release cutoff.  This means that the item's developer and QE have a high level of confidence that this item will get certified in a timely fashion in the release branch.  Any such "extension" requires approval from the product owner and release management.

  
Although adding efforts to disable features may seem to introduce more work, the benefits of keeping a clean development branch should far outweigh the effort required. Also, feature reversal should only occur in exceptional cases and not be the norm. If we end up having to revert features each release, we should re-evaluate our sprint/release planning strategy instead of blaming our branching strategy. In the case where a reversal is in fact required, the responsibility falls on the ticket developer and should do so as soon as possible to allow QE enough time to validate the reversal effort and test for potential side-effects.  Feature reversal should be done in a matter that minimizes impact.  For example, coding features in isolation and only commenting out the entry point instead of rolling back the whole feature.

  
Constant communication between devs, QEs, and product owners during the stabilization period is critical for this approach to be successful.  Even at the sprint planning level, concerns about tickets that are at risk of not getting certified should be raised.  All three parties must always be in agreement in order to have successful releases and minimize code reversal. For example, if a developer feels they have plenty of time to finish a major story before feature freeze while QE clearly doesn't think they have enough time to fully certify before release cutoff, a discussion needs to happen. The product owner will either approve the release item to be finished in the release branch to satisfy QE's time requirement or the feature will have to be reverted and pushed to the next release.

  

What happens on release cutoff?  Each team should have a dev and QE lead signoff on the release stabilization effort. This sign off means that all features/bugs of that team have been certified and that there's no outstanding uncertified code in our development branch. Once all the teams have signed off, a designated lead can cut the new release branch and communicate to the dev teams that our development branch is open for future development.

  

Finally, once the release branch reaches production, we can merge it back into both the development and master branches.  This will ensure that any work performed in the release branch post-cutoff gets applied to other branches.  There's no need to merge master back into development using this approach.  The master branch represents a certified production-quality branch and the development branch represents a working branch that is constantly kept relatively clean for future releases.

## **Risks**

One of the main risks identified while discussing this proposal was our database repo. Currently, we don't have a reliable way to test local database changes. Therefore, we use QAI as a sandbox for testing DB changes where we can push changes for exploratory reasons. Until we come up with a better way to test database changes, the database repo would have to remain under the current branching strategy where only certified changes would get promoted to the release branch.

  
Additionally, introducing the concept of a stabilization period introduces the risk that a developer may accidentally commit a merge during the freeze which would risk making it to production without getting tested. Clear communication through email and during scrum will be required to ensure everyone is aware of the this stabilization period.

  
What if I'm done with all my release work during this stabilization period and I want to work on future work? If developers are done with current release work and want to start working on future release work, they are free to do so but cannot merge any changes to the development branch until communication has been sent that the release branch was cut. This strategy shouldn't impede development but may block QE from testing next release features prior to release cutoff.

## **Summary**

In conclusion, I think it would fairly reasonable to incorporate these concepts and it would significantly simplify our current process and mitigate some of the risks associated with branching.  By keeping QAI clean and stop using epic branches, we would increase quality confidence, speed up code sharing, reduce merge conflicts, and reduce the amount of work involved in cutting release branch.
