# Overview

Disclaimer

This exploration focuses exclusively on the global Top Navigation. It does not include a specific evaluation of local Side Navigation functionality or Notifications.

Passkey is transitioning to a Microfrontend (MFE) application architecture. Each MFE requires access to shared Passkey UI elements and functionality, including a global navigation menu. The global Top Navigation component must be reusable across all Passkey MFEs. This document outlines the current approach to Top Navigation, identifies its limitations, and proposes an alternative solution with significant improvements.

# Current Architecture

The top navigation in Passkey is implemented in _passkey-rdk2_ (and its sub-packages) through several components:

1.  **Data Access**: The _rdk2_ GraphQL API provides numerous queries essential for determining navigation display. The schema, client operations, data sources, and resolvers are all located in the _passkey-rdk2/app_ package.
2.  **Business Logic**: The _TopNavigationData.ts_ file in _passkey-rdk2-lib_ serves as the core data model and business logic provider for the Top Navigation system.
3.  **Presentation**: The _TopNavigation.tsx_ component in _passkey-rdk2-lib_ acts as a presentational wrapper, leveraging Carina components to construct a custom Passkey Top Navigation layout.
4.  **Integration**: Each MFE application includes a specific _TopNavigation.tsx_ component to organize GraphQL calls to the _rdk2_ API and build the prop object supplied to the library’s Top Navigation component. 

## How It Works

1.  Each MFE consumes _passkey-rdk2-lib_ and relies on its data aggregation process.
2.  MFEs must replicate the exact GraphQL schema and operation definitions from _rdk2_ to execute the necessary queries.
3.  The MFE’s TopNavigation component aggregates data via direct calls to the _rdk2_ API, utilizing 25 different GraphQL operations, evaluates feature flags, performs light data processing, and passes a large prop object (mostly raw data) to the RDK2 library component.
4.  The _TopNavigationData.ts_ class in _passkey-rdk2-lib_ filters menu items based on user permissions, manages URL generation, and constructs the navigation structure.
5.  The UI component renders top-level navigation tabs, dropdown menus, user profile, app switcher, and notifications.

## Problems

1.  **Duplicate Schema:**
    
    1.  Redundant copying of the _rdk2_ schema and operations into every application.
    2.  Inconsistencies may arise across MFEs.
    3.  Lack of schema versioning; changes at the source require updates everywhere, risking non-backward compatible changes and potential breakages.
2.  **Excessive Data Fetching:**
    
    1.  Multiple separate GraphQL queries for related data.
    2.  Redundant fetching of user data and permissions.
    3.  Managing 25 different operations increases the risk of errors when copying code.
3.  **Poor Separation of Concerns:**
    
    1.  Business logic is mixed with UI rendering.
    2.  Feature flags are intertwined with navigation structure.
    3.  The p_asskey-rdk2-lib_ Top Navigation component has a poor prop contract, receiving data not ready for rendering.
    4.  The UI component library is responsible for additional data processing, which should be handled elsewhere.
4.  **Performance Concerns:**
    
    1.  Multiple loading states must be managed.
    2.  Frequent re-rendering due to complex state management.
    3.  No optimized data fetching strategy.
5.  **Prop Drilling:**
    
    1.  Excessive props are passed through component layers.
    2.  Complex, nested data structures with unclear boundaries.

**Example**: Query for fetching GML Hotels in _passkey-admin_ was outdated and throwing a GraphQL schema validation error leading to a bug in production.

# Proposal

The primary objectives of the new approach are to consolidate the data aggregation process and separate business logic from the UI components in _passkey-rdk2-lib._ 

## Encapsulated Model Package

_See [POC branch](https://github.com/cvent-internal/passkey-rdk2/compare/development...poc/GROUP-109573) for example code in passkey-rdk2_

To streamline data collection, a new package is proposed to house the entire GraphQL layer related to Passkey navigation. The proof of concept (POC) envisions a _passkey-navigation-model_ package within the _rdk2_ repository, alongside _passkey-rdk2-lib_. The exact placement and naming of this package remain open for discussion.

This package is intended to serve as a GraphQL model package, similar to those found in other CDF applications. The concept draws inspiration from the now-deprecated CDF @cvent/planner-navigation library. The navigation model defines a schema that closely mirrors the types used in Carina (see NavigationProviderProps). Here is an important snippet from the proposed schema that highlights how the model defines a data structure that looks like a generic menu as opposed to lower-level, internal Passkey data.

A single query, _passkeyNavigation_, is defined, requiring only a userId to generate the menu. All other necessary data can be derived from the userId. Correspondingly, only one client operation is needed.

**Ultimately, the _passkey-navigation-model_ package and its dependent data sources are responsible for constructing a ready-for-display Passkey menu object, abstracting data collection and processing away from the UI component library. This also relieves each MFE from this burden. This module answers the question, "What menu options and data needs to be displayed in the global navigation?"**

## Summary of Benefits

1.  **Separation of Concerns:**
    
    1.  Isolates navigation data gather and logic from the main application code.
    2.  Enhances maintainability and testability of navigation functionality.
2.  **Consistent API Interface:**
    
    1.  Provides a unified GraphQL API for navigation across applications.
    2.  Ensures consistent data structure and access patterns.
3.  **Reusability without Duplication:**
    
    1.  Enables sharing between multiple applications (e.g., RDK2, call center, room-categories).
    2.  Prevents duplicate implementations of navigation-related schema, operations, and invocations.
4.  **Centralized Navigation Management:**
    
    1.  Establishes a single source of truth for navigation structure.
    2.  Simplifies updates and maintenance.
5.  **Performance Optimization:**
    
    1.  Facilitates navigation-specific query optimizations.
    2.  Supports fine-tuned caching strategies for navigation data.
6.  **Versioning:**
    
    1.  Allows independent versioning of the navigation model.
    2.  Enables teams to adopt navigation changes at their own pace.
7.  **Better Testing:**
    
    1.  Increased modularity supports focused testing.
    2.  Simplifies mocking of navigation data for other components.
