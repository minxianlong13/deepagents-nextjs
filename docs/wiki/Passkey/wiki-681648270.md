This document is intended to outline our approach for including Autoblock-oriented _notifications_ to the notifications panel in the RDK2 Home Page (Lighthouse). There are two notification variants that are of interest that share the same raw data set:

-   **Free-sell Requests Pending Approval**: These notifications provide the user with a total count of 'pending' block requests that have not yet been approved across all of their events.  If they click on the notification header to open the details view, the count will be broken down so that there is a count of pending requests _per event_.
-   **New Free-sell Block Requests**: These notifications provide the user with a total count of block requests that have been received within the last 72 hours.  If they click on the notification header to open the details view, the count will be broken down so that there is a count of total New block requests _per event_.

# Event Bus Modelling

New _Block Request Events_ will be produced by our STEP Function workflows that are currently responsible for creating and modifying Autoblock requests.  The events will be consumed by a registered consumer in the passkey-alerts project and used to manage aggregate rows in DynamoDB for tracking alert/notification data on a _per event_ and _per participant_ basis.

## Upgrading passkey-alerts to CDF

This effort will require an in-place migration of the passkey-alerts service to CDF in order to support the new CDK stacks required to host the consumer lambda and the associated DynamoDB infrastructure it will use.

## Event Bus Event Definition: BlockRequest

-   We anticipate that events of this type will be emitted by successful executions of the Autoblock Autoprovision Workflow <_Type=AUTOBLOCK, Action=CREATE, approveMethod=AUTO|MANUAL_\>

## Entity Definition: PendingBlockRequestsAggregate

### Highlights

-   We anticipate that records of this entity type will be created and updated via a BlockRequest event Consumer Lambda.
-   We anticipate that the consumer will manage two aggregate records per raw block request event received - one record intended for use on the RDK2 home page view and one for the classic event home view.
    -   When _BlockRequest.Action=INSERT_ and _BlockRequest.Detail.approveMethod=MANUAL_, the consumer will CREATE new records for each of the two key constructions defined below, OR increment the aggVal record attribute of each record if they already exist.
    -   When _BlockRequest.Action=MODIFY_ and _BlockRequest.Detail.approveMethod=MANUAL_ and _BlockRequest.Detail.modifyType=REJECT|APPROVE_, the consumer will decrement the count associated with each record.  If the record does not already exist, then the event is ignored and a warning should be logged to indicate that the aggregate notification data is out of sync with the raw block request data.
    -   On the home page, the query can return all records matching PARTICIPANT partition key.  These records can be SUMed to show a total count, or sort key detail can be used to construct an event specific drill-in notification.
-   Each of these records will store an accurate view count in the **aggVal** record attribute.
-   When this alert data is to be viewed by participant, the first key construction variant will be used to fetch the set of records with the same Participant-oriented partition key (but different **event** sort keys)
-   When this alert data is to be viewed by event, the second key construction variant will be used to fetch the set of records with the same event-oriented partition key (but different **participant** sort keys)
-   The TTL of each record - regardless of partition/sort key order - should be based on the event's close date, or some similar milestone. Perhaps has some feedback, here.

### Access Patterns

1.  Get total count of pending-status block requests for a single participant of a single event (For event participant, event home)
    1.  In this use case, we have the participant id AND the event id to create a complete partition and sort key and fetch the one row we need (NOTE: It doesn't matter which key construction we use - they'll both return the same value).
2.  Get SUM total count of pending-status block requests for all participants of a single event (For event owner, event home)
    1.  Here, we have only an event id.  We provide it as the partition key of the second key construct above, returning us counts from each participant (which can be SUMed to produce a total count).
3.  Get SUM total count of pending-status block requests for one participant of ALL participating events (For any participant, main home)
    1.  Here, we have only a participant id.  We provide it as the partition key of the first key construct above, returning us counts for each event. The counts can be SUMed for a total, and we can also return the records raw so that when user's drill in, we will already have an event-based breakdown.

## Entity Definition: DailyBlockRequestsAggregate

### Highlights

1.  We anticipate that records of this entity type will be created and managed by the same BlockRequest event consumer lambda that is servicing **PendingBlockRequestAggregate** records.
2.  Only one record of each key construction type will exist per participant, per event, per day.  
    1.  One record to index lookups by participant (See Key Construct #1 below)
    2.  One record to index lookups by event (See Key Construct #2 below)
3.  The TTL of these records should be based on the created date + 4 days (we don't care about records more than 3 days old).

### Key Construction

In all use cases, the aggVal field is used to store the aggregate.  As seen below, a single Raw Block Request row will trigger the INSERT or UPDATE of two aggregate rows:

1.  One row to facilitate the generation of a total aggregate value per _event_, SUMmable across all participants specific to that event  (PK == EVENT#1234)
2.  One row to facilitate the generation of a total aggregate value per _participant_, SUMmable across all events specific to that participant (PK == PARTICIPANT#1234)

# Java-based Block Request Event Consumer DynamoDB Updates

The above schema describes two entities co-existing in the same table.  Our goal here is to construct a system that allows us to provide raw update events for every created/modified block request that will be consumed by an event consumer, and then used to aggregate views of that raw data (using the participant and event ids provided in the event payload).  These aggregated views can be used differently for phase one and phase 2 of this work:

**Phase 1**: The browser reaches out to the Apollo backend for AB alerts data using a modified alerts query, which will use the existing alerts data source and existing pull architecture to fetch the latest alerts data from the alerts microservice.  For phase 1, we will have to supply a new MS endpoint for fetching autoblock alerts data from the new DynamoDB table.

**Phase 2**: In Phase 2, we migrate to a push architecture that makes use of a few new-to-us technologies:

-   Apollo Subscriptions: This allows the browser to submit a query with a '@subscribe' annotation that (once configured correctly) will provide the UI with near-live updates from the DB on an ongoing basis.
-   Redis Subscriptions: This allows the Apollo cluster to work as one when a user is subscribed to entity changes through a single Apollo node (otherwise, the frontend subscription and the backend updates/events would have to converge on precisely the same Apollo node, and we can't do that).
-   An Apollo community library called **graphql-redis-subscriptions** which is used to wire up the two above concepts to create an ecosystem for cache-aware, distributed subscriptions from backend-to-browser.  It is used elsewhere in Cvent for similar purposes.
