# 1\. Data Protection and Retention Lifecycle

### PRA Finding

**Issue**

The original PDF is stored before PCI detection and may remain for 30 days. Draft EMOs are retained indefinitely, with no documented deletion, backup, legal-hold, or customer-deletion process.

**Requirement to close**

Implement or formally risk-accept upload-time PCI handling and define EMO retention, deletion, backup, legal-hold, and customer-deletion controls.

* * *

## Current Implementation

### Original uploaded file

Files uploaded into the PCI-zone File Uploader are retained for **1 day**, rather than 30 days.

Implementation:

[https://github.com/cvent-internal/passkey-file-uploader](https://github.com/cvent-internal/passkey-file-uploader)

`passkey-file-uploader/packages/passkey-file-uploader-sb/infra/lib/commonProps.ts   `[GitHub reference](https://github.com/cvent-internal/passkey-file-uploader/blob/master/packages/passkey-file-uploader-sb/infra/lib/commonProps.ts#L18)

The File Uploader owns file storage, retention, PCI detection/tokenization, participant/file ownership validation, and enforcement of approved extraction definitions.

### Event Request / EMO retention

Event Request objects are also not retained indefinitely.

A TTL is assigned when the request is created if one is not already present:

`EventRequestsService.java:39,61-63`

The TTL is:

**creation time + 30 days**

When the workflow later updates the Event Request to `PROCESSED`, the update does not replace the TTL:

`step5PatchRequestStatus.ts:32-36`

The patch implementation preserves the existing TTL if a new value is not supplied:

`EventRequestsService.java:217-219`

Therefore, both draft and processed Event Requests expire automatically based on the original 30-day TTL.

I created a follow up ticket for enhancement is required to support deletion of Event Requests by **participant ID**, allowing all applicable requests associated with a participant to be removed as part of the customer-deletion workflow.

## Authorization and IDOR Protection

The Create Event from File workflow has multiple authorization layers.

### 2.1 Workflow ingress authentication

`   [https://github.com/cvent-internal/passkey-event-data](https://github.com/cvent-internal/passkey-event-data)   POST /v1/event-requests`

is protected by an API Gateway Lambda Request Authorizer.

Relevant implementation:

`passkey-event-request-workflow/infra/lib/components/api-gateway.ts:217-219`

The authorizer requires an Authorization Bearer token and verifies it through Auth Service:

`lambda-token-authorizer.ts:71-83,145-168`

Auth Service verification endpoint:

`/v1/access_token/{token}/verify`

Requests that fail token validation are rejected before the Event Request workflow is started.

* * *

### 2.2 Trusted identity mapping

Caller identity is not taken directly from arbitrary request-body values.

API Gateway injects trusted authorization context into the Step Functions request, including:

-   `participantId`
    
-   `userId`
    
-   `hasSisterHotels`
    
-   `userTypeId`
    
-   access token
    

Implementation:

`api-gateway.ts:144-160`

These values originate from the validated authorizer context and are injected server-side before execution of the workflow.

This prevents a caller from changing request-body identity information in order to impersonate another participant.

* * *

### 2.3 Event Request authorization / IDOR protection

Before processing the Event Request, Step 1 validates whether the authenticated caller is permitted to operate against the target participant.

Implementation:

`step1LoadIn.ts:160-197`

The authorization logic includes:

-   Passkey-user authorization
    
-   Sister-hotel organization handling
    
-   Participant / owner-participant validation
    

Requests that do not satisfy the authorization rules are rejected before Event Request processing continues.

### Authorization chain

`Bearer Token`

→ `Lambda Authorizer`

→ `Auth Service Token Verification`

→ `Trusted Identity Context Injected by API Gateway`

→ `Participant Authorization / Ownership Validation`

→ `Event Request Processing`

This provides the primary IDOR protection for the EMO/Event Request workflow.

# 3\. Production Extraction Security & Quality Assurance

### PRA Finding

**Issue**

The current implementation includes a provider stub and follow-up work for production parsing and file-signature validation. Prompt-injection testing, adversarial document testing, accuracy thresholds, and comprehensive business validation are also not evidenced.

**Requirement to close**

Deploy validated production parsing, add file-signature checks, complete adversarial testing, define accuracy thresholds, and provide business-validation results.

* * *

## Current Design Controls

The generic File Uploader extraction design already establishes several important boundaries.

The File Uploader:

-   Resolves the extraction type from a trusted token claim
    
-   Does not accept caller-provided prompts
    
-   Does not accept caller-defined extraction fields
    
-   Does not accept caller-defined schemas
    
-   Resolves physical file format from persisted upload metadata
    
-   Validates participant/file ownership
    
-   Performs PCI detection/tokenization before extracted content can leave the PCI boundary
    

The extraction endpoint accepts only an approved `extracttype` from the access token and resolves it against the registered extraction definition.

This prevents an API caller from modifying the request body to expand the extraction operation beyond the capability authorized by the token.

* * *

## Work Still Required

The current ticket intentionally uses a replaceable deterministic extraction provider.

Before production rollout, the following work remains:

### Production parser

Replace the deterministic provider with the approved production PDF extraction implementation.

### File-signature validation

Persisted MIME metadata alone is not sufficient protection against content-type spoofing.

The production implementation must verify the actual PDF signature/container structure before parsing.

### Adversarial testing

Testing should include documents containing:

-   Prompt-injection text
    
-   Instructions attempting to override extraction behaviour
    
-   Unexpected/malformed document structures
    
-   Large or unusually formatted contracts
    
-   Missing required business information
    
-   Conflicting values
    
-   Invalid dates/rates
    
-   Unexpected text or embedded content
    

### Extraction accuracy

Define an agreed validation dataset and measurable acceptance criteria for the fields required by the Contract workflow.

The validation should cover the business fields consumed by Event Request / Event Metadata, including applicable event, planner, hotel, date, rate, and room information.

### Business validation

The Contract workflow remains responsible for validating extracted structured data before using it for Event Request/Event creation.

The production extraction result must not be treated as trusted business data solely because the parser or LLM returned syntactically valid JSON.

* * *
