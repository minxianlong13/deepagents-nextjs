## PROPOSED DESIGN

## Decision

Use React Server Components (RSCs) for the initial, mostly static page. Keep dynamic regions (such as Event search, filtering, and pagination) in client components that call focused HTTP route handlers.

Do not call domain services from page components or client components. Put authorization, service orchestration, mapping, caching, and observability in shared server-side use cases.

## Architecture

PL\[Page loader\] PL --> UC\[Event page use case\] CL\[Client Event list\] --> RH\[Event search route handler\] RH --> UC2\[Event search use case\] UC --> AU\[Authorization service\] UC2 --> AU UC --> CA\[Server cache\] UC2 --> CA UC --> DS\[Domain service clients\] UC2 --> DS DS --> MS\[Domain microservices\]\]\]>

Glossary:

-   **React Server Component page:** Server-rendered page content sent as an initial snapshot.
-   **Page loader:** Thin server module called by the RSC page.
-   **Event page use case:** Shared server operation that authorizes, combines data, and returns a page-shaped model.
-   **Client Event list:** Interactive browser component for search, filtering, and pagination.
-   **Event search route handler:** Small HTTP endpoint used only by the live list.
-   **Event search use case:** Shared server operation that returns one page of search results.
-   **Authorization service:** Verifies identity and checks access to the requested resource.
-   **Server cache:** Request, application, or distributed cache used according to data sensitivity.
-   **Domain service clients:** Typed adapters for downstream APIs.
-   **Domain microservices:** Services that own Event, availability, or related domain data.

## Initial page sequence

\>P: Request page P->>L: Load static page model L->>A: Authenticate and authorize resource A-->>L: Authorized actor and scope L->>C: Read safe cached data alt Cache miss L->>D: Fetch required domain data in parallel D->>M: Call domain APIs M-->>D: Domain responses D-->>L: Typed results L->>C: Store cacheable data end L-->>P: Page view model P-->>B: Rendered page and initial list data\]\]>

Glossary:

-   **Browser:** The web browser of the user.
-   **RSC page:** React Server Component page responsible for initial rendering.
-   **Page loader:** Thin entry point that calls the page use case.
-   **Authorization service:** Validates the user and confirms page/resource access.
-   **Server cache:** Stores only data that is safe to reuse under its cache key.
-   **Domain service clients:** Server-only typed clients for domain APIs.
-   **Domain microservices:** Downstream services that own the data.

## Live Event search sequence

\>H: Type search text H->>H: Debounce input H->>Q: Read matching browser cache entry alt Browser cache miss or stale result H->>R: GET search results R->>S: Validate input and execute search S->>A: Authenticate and authorize search scope A-->>S: Authorized actor and scope S->>C: Read scope-safe cached data alt Cache miss S->>D: Fetch matching Events D-->>S: Typed domain results S->>C: Store permitted cacheable data end S-->>R: List view model and next cursor R-->>Q: JSON response end Q-->>H: Current list results H-->>U: Update only the Event list\]\]>

Glossary:

-   **User:** Person who interacts with the Event list.
-   **Client Event list:** Browser component that owns local search and pagination state.
-   **Browser query cache:** Client-side cache for recent search requests and list pages.
-   **Event search route handler:** HTTP endpoint that serves only interactive Event-list results.
-   **Event search use case:** Server operation that enforces rules and assembles the list payload.
-   **Authorization service:** Validates identity and resource scope on every request.
-   **Server cache:** Server-side cache keyed to prevent unauthorized reuse.
-   **Domain service clients:** Typed adapters used to call downstream APIs.

## Caching rules

Layer

Purpose

Key requirements

Request memoization

Deduplicate calls during one RSC render

Include all function inputs. Do not treat as cross-request caching.

Server data cache

Reuse safe data across requests

Cache raw or shared data when possible. Use a short time-to-live for search.

Authorization cache

Avoid repeated permission lookups

Use a short lifetime only if permission revocation does not need to be immediate.

Browser query cache

Make live lists responsive

Key by event, normalized query, filters, sort, and cursor.

Do not share a user-filtered result only by EventId or search text. A final list cache key must include the tenant or event and the authorization scope or entitlement version. It must also include the normalized query, filters, sort, cursor, and locale. If that is not practical, cache unfiltered upstream data and apply visibility rules after the cache read.

## Implementation rules

-   Authorize before each downstream call path. The RSC page check does not authorize the route handler.
-   Keep page-specific loader code thin. Put meaningful logic in shared use cases.
-   Use parallel calls inside the use case only after authorization succeeds.
-   Return page/list view models, not raw domain responses.
-   Keep an RSC-owned query separate from a client-owned live query to avoid stale or inconsistent views.
-   Use explicit invalidation on Event changes. Otherwise, use short cache lifetimes for list search.

## What replaces GraphQL

GraphQL capability

Replacement

Resolver

Shared server use case

Authentication directive and context

App Router authentication plus authorization service

Resolver orchestration

Use case plus typed domain clients

Schema response type

TypeScript input and view-model types

Apollo browser cache

Browser query cache such as TanStack Query or SWR

Data loader / per-request deduplication

Request memoization or request-scoped loader

This approach suits a small set of page-specific operations. Reconsider GraphQL if many pages or separate consumers need flexible, independently composable reads.
