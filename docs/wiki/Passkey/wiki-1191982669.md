<h2><span style="color:var(--ds-background-accent-red-subtle,#f87168);">PROPOSED DESIGN</span></h2><h2>Decision</h2><p>Use React Server Components (RSCs) for the initial, mostly static page. Keep dynamic regions (such as Event search, filtering, and pagination) in client components that call focused HTTP route handlers.</p><p>Do not call domain services from page components or client components. Put authorization, service orchestration, mapping, caching, and observability in shared server-side use cases.</p><h2>Architecture</h2><ac:structured-macro ac:name="mermaid-macro" ac:schema-version="1" ac:macro-id="b1a2c3d4-e5f6-7890-abcd-ef1234567801"><ac:plain-text-body><![CDATA[flowchart LR

Do not treat as cross-request caching.</td></tr><tr><td>Server data cache</td><td>Reuse safe data across requests</td><td>Cache raw or shared data when possible. Use a short time-to-live for search.</td></tr><tr><td>Authorization cache</td><td>Avoid repeated permission lookups</td><td>Use a short lifetime only if permission revocation does not need to be immediate.</td></tr><tr><td>Browser query cache</td><td>Make live lists responsive</td><td>Key by event, normalized query, filters, sort, and cursor.</td></tr></tbody></table><p>Do not share a user-filtered result only by EventId or search text. A final list cache key must include the tenant or event and the authorization scope or entitlement version. It must also include the normalized query, filters, sort, cursor, and locale. If that is not practical, cache unfiltered upstream data and apply visibility rules after the cache read.</p><h2>Implementation rules</h2><ul><li>Authorize before each downstream call path. The RSC page check does not authorize the route handler.</li><li>Keep page-specific loader code thin. Put meaningful logic in shared use cases.</li><li>Use parallel calls inside the use case only after authorization succeeds.</li><li>Return page/list view models, not raw domain responses.</li><li>Keep an RSC-owned query separate from a client-owned live query to avoid stale or inconsistent views.</li><li>Use explicit invalidation on Event changes. Otherwise, use short cache lifetimes for list search.</li></ul><h2>What replaces GraphQL</h2><table class="wrapped"><thead><tr><th>GraphQL capability</th><th>Replacement</th></tr></thead><tbody><tr><td>Resolver</td><td>Shared server use case</td></tr><tr><td>Authentication directive and context</td><td>App Router authentication plus authorization service</td></tr><tr><td>Resolver orchestration</td><td>Use case plus typed domain clients</td></tr><tr><td>Schema response type</td><td>TypeScript input and view-model types</td></tr><tr><td>Apollo browser cache</td><td>Browser query cache such as TanStack Query or SWR</td></tr><tr><td>Data loader / per-request deduplication</td><td>Request memoization or request-scoped loader</td></tr></tbody></table><p>This approach suits a small set of page-specific operations. Reconsider GraphQL if many pages or separate consumers need flexible, independently composable reads.</p><h2>Sources</h2><ul><li><a class="external-link" href="https://github.com/cvent-internal/passkey-room-categories-ui/blob/master/.claude/skills/nextjs-app-router-auth/SKILL.md">Cvent App Router authentication guidance</a></li><li><a class="external-link" href="https://github.com/cvent-internal/bi-hub/blob/master/.claude/skills/apollo-client/references/rsc.md">Cvent RSC versus browser data-fetching guidance</a></li><li><a class="external-link" href="https://github.com/cvent-internal/bt-Event-profile-ui/blob/main/docs/technical-documentation.md">Example Cvent App Router RSC with a co-located BFF</a></li></ul>
