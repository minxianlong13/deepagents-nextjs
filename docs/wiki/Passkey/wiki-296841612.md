<h2>The API Gateway</h2><p>The entry point into Passkey's AWS components is the API Gateway. The API Gateway supports error handling by using regex to categorize output from lambda functions. For example, a developer can define any output containing the string 'error' to result in a 500 response. Alongside these regex mappings, a developer can optionally create a 'mapping template', which allows them to transform the lambda output, effectively creating a response with the structure of their choosing. Together, the mapping template and the regex mapping are known as an Integration Response. Importantly, there must always be a &quot;default&quot; integration response which catches any lambda output without a regex match. This default response is the proverbial sticky wicket we need to keep in mind when designing error handling for AWS services.</p><p><sub>Integration responses for an API Gateway endpoint. Here the default integration is a successful 202 response.</sub></p><p><ac:image ac:height="400"><ri:attachment ri:filename="Screen Shot 2020-11-05 at 8.22.37 PM.png" /></ac:image></p><p>Currently, the default integration response returns a success code on all of our API Gateway endpoints. This often masks errors, as there are no regex matches for unanticipated errors, leaving the successful default response as the only mapping available to them. The obvious solution is to map the default response to an error response such as 500, and create a regex to explicitly map success codes. We can use lambda functions to our advantage here, and make sure successful lambda outputs contain a unique string to match against, as well as passing along the microservice response. For example, our lambda function might contain the following code:</p><ac:structured-macro ac:name="code" ac:schema-version="1" ac:macro-id="5898ebef-a6ec-465a-be3c-1bc6a55ce16a"><ac:parameter ac:name="language">js</ac:parameter><ac:plain-text-body><![CDATA[const resultObj = await this.callEndpoint(requestObj);
const resOut = {
	lambdaResult: "GREAT_SUCCESS",
	serviceResponse: resultObj
};]]></ac:plain-text-body></ac:structured-macro><p>From here we can match using the regex &quot;.*GREAT_SUCCESS.*&quot; and use a simple mapping template to pass the service response through to the client as the API Gateway response. Meanwhile, we can set the default integration response up as an error response.</p><h2>AppSync</h2><p>Cvent has done some work to create support for <ac:link><ri:page ri:space-key="RD" ri:content-title="AppSync Error Handling" /><ac:plain-text-link-body><![CDATA[AppSync Error Handling.]]></ac:plain-text-link-body></ac:link> Mostly they have created a mechanism to provide additional error details in a GraphQL response format. It's something that will probably be useful if we expose GraphQL as a resource for clients, or even internally so we can get useful error messages. As of now, it's not entirely relevant because our GraphQL usage is limited to the Get Reservation lambda which wraps calls to AppSync. We might be able to use it to avoid the way AppSync is wrapping microservice error responses, but we can also do that manually.</p><h2>Error Response Format</h2><p>Passkey has developed guidelines around the structure of error responses (<ac:link><ri:page ri:content-title="Passkey Microservice Error Codes Best Practices" ri:space-key="PASKYArchive" /></ac:link>). It's already our goal to bubble up microservice responses to the client through lambdas and the API Gateway, so this format already exists and is supported to some extent.</p><ac:structured-macro ac:name="code" ac:schema-version="1" ac:macro-id="1cedc4fb-f674-4024-ae74-4ab01bf4a9d8"><ac:parameter ac:name="title">Microservice Error Response Format</ac:parameter><ac:plain-text-body><![CDATA[{

We won't have to play with integration response mappings and can simply pass the lambda output through. The value of the code field can determine which kind of HTTP response code we want to map the error to.</p><h2>Lambda Functions</h2><p>Currently, our lambda functions handle errors from our microservices very well, but they handle all other errors very poorly. We have all of the lambda functionality in the same try block, but when any error is caught from those operations, the lambda expects it to be a microservice error and expects certain fields to be present. If the error is caused by bad lambda code, or an issue with DynamoDB, a new error will be thrown because the error handling will attempt to reference undefined fields.</p><p>To resolve this issue, we'll add a new class to run our lambda functions through and handle any resulting errors. This will have to be accompanied by a refactor of our lambda code,  both to encapsulate lambda functionality into functions that can be passed around, and to create new custom error types to allow different errors to be handled appropriately.
