<h1>Introduction</h1><blockquote><p><em>&quot;Gitflow Workflow is a Git workflow design that was first published and made popular by <a style="text-decoration: none;" href="http://nvie.com/posts/a-successful-git-branching-model/">Vincent Driessen at nvie</a>. The Gitflow Workflow defines a strict branching model designed around the project release. This provides a robust framework for managing larger projects.  </em></p><p><em>Gitflow is ideally suited for projects that have a scheduled release cycle. This workflow doesn’t add any new concepts or commands beyond what’s required for the <a style="text-decoration: none;" href="http://www.atlassian.com/git/tutorials/comparing-workflows/feature-branch-workflow">Feature Branch Workflow</a>. Instead, it assigns very specific roles to different branches and defines how and when they should interact. In addition to <code>feature</code> branches, it uses individual branches for preparing, maintaining, and recording releases. Of course, you also get to leverage all the benefits of the Feature Branch Workflow: pull requests, isolated experiments, and more efficient collaboration.&quot;</em></p><p><em>source: <a href="https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow">https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow</a></em></p></blockquote><h1>Branch Types</h1><h2>Main branches</h2><p>Our two main branches (master and development) will have an infinite lifetime and will be at the core of our development.</p><h4>Master</h4><p>Consistent with all git repos, origin/master will be our main branch where its source code represents a production-ready state.  Master represents our release history of production code and only production-ready code should get pushed to master at any given moment, no exceptions.</p><h4>Development</h4><p>The development branch, on the other hand, will act as our CI branch where all completed feature work goes into. Contrary to our previous branching strategy, this branch can be trusted and all feature branches should be created from development (not master).  All features merged into development are intended for production, no exceptions.  Once the source code reaches a stable state and is ready for prime time, it will get merged back into master and tagged with a release version for production deployment.</p><p>As our continuous integration branch, development will be the branch against which QE validation and automation occurs, similar to our previous QAI branch.  As mentioned earlier, the source code from the development branch can be trusted.   This is achieved by only allowing certified features to remain in development.  This does not mean that the development branch only contains certified features, it means that all features in development will either get certified before getting released or else will be removed/turned off.  Removal of features can be done through various mechanism but using the experiment framework is highly recommended to avoid manual intervention, which can be costly.</p><h2>Support branches</h2><p>The support branches is where all the feature work, bugfixes, and hotfixes goes.</p><h4>Feature and Bugfix</h4><p>The feature and bugfix branches behave very similarly to our previous branching strategy.  The only difference is that each should get forked/created from development instead of master and merged back into development once ready.</p><h4>Release</h4><p>This is where the development branch goes when we want to release a set of features (in our case, this is on a 2-week release cycle).  Every two weeks (per release schedule), leads will create a new release branch from development.  This release branch will be deployed to a staging environment for final validation/certification.  Once certification is achieved, the release branch will get merged into both master and development.  After merging into master, a release tag will get created by a lead and <ac:inline-comment-marker ac:ref="18c6b3e0-2bf1-4d06-bc54-3a6cc050ed43">master will be ready for production deployment</ac:inline-comment-marker>.  Merging the release branch back into development will ensure that any bug found and fixed during certification will find their way back into development.  Additionally, such bug fixes can also be co-merged directly into development if required.</p><h4>Hotfix</h4><p>The hotfix branch is intended for urgent issues found in production.  Hotfix branches are forked from master and applied to both master and development once validated.  Merging into development will ensure that the bug does not get re-introduced next release.  A new release tag should also get created after the hotfix is merged into master.</p><p><br
