# Introduction

> _"Gitflow Workflow is a Git workflow design that was first published and made popular by [Vincent Driessen at nvie](http://nvie.com/posts/a-successful-git-branching-model/). The Gitflow Workflow defines a strict branching model designed around the project release. This provides a robust framework for managing larger projects._  
> 
> _Gitflow is ideally suited for projects that have a scheduled release cycle. This workflow doesn’t add any new concepts or commands beyond what’s required for the [Feature Branch Workflow](http://www.atlassian.com/git/tutorials/comparing-workflows/feature-branch-workflow). Instead, it assigns very specific roles to different branches and defines how and when they should interact. In addition to `feature` branches, it uses individual branches for preparing, maintaining, and recording releases. Of course, you also get to leverage all the benefits of the Feature Branch Workflow: pull requests, isolated experiments, and more efficient collaboration."_

# Branch Types

## Main branches

Our two main branches (master and development) will have an infinite lifetime and will be at the core of our development.

#### Master

Consistent with all git repos, origin/master will be our main branch where its source code represents a production-ready state.  Master represents our release history of production code and only production-ready code should get pushed to master at any given moment, no exceptions.

#### Development

The development branch, on the other hand, will act as our CI branch where all completed feature work goes into. Contrary to our previous branching strategy, this branch can be trusted and all feature branches should be created from development (not master).  All features merged into development are intended for production, no exceptions.  Once the source code reaches a stable state and is ready for prime time, it will get merged back into master and tagged with a release version for production deployment.

As our continuous integration branch, development will be the branch against which QE validation and automation occurs, similar to our previous QAI branch.  As mentioned earlier, the source code from the development branch can be trusted.   This is achieved by only allowing certified features to remain in development.  This does not mean that the development branch only contains certified features, it means that all features in development will either get certified before getting released or else will be removed/turned off.  Removal of features can be done through various mechanism but using the experiment framework is highly recommended to avoid manual intervention, which can be costly.

## Support branches

The support branches is where all the feature work, bugfixes, and hotfixes goes.

#### Feature and Bugfix

The feature and bugfix branches behave very similarly to our previous branching strategy.  The only difference is that each should get forked/created from development instead of master and merged back into development once ready.

#### Release

This is where the development branch goes when we want to release a set of features (in our case, this is on a 2-week release cycle).  Every two weeks (per release schedule), leads will create a new release branch from development.  This release branch will be deployed to a staging environment for final validation/certification.  Once certification is achieved, the release branch will get merged into both master and development.  After merging into master, a release tag will get created by a lead and master will be ready for production deployment.  Merging the release branch back into development will ensure that any bug found and fixed during certification will find their way back into development.  Additionally, such bug fixes can also be co-merged directly into development if required.

#### Hotfix

The hotfix branch is intended for urgent issues found in production.  Hotfix branches are forked from master and applied to both master and development once validated.  Merging into development will ensure that the bug does not get re-introduced next release.  A new release tag should also get created after the hotfix is merged into master.

# Scenario Guidelines

This section will cover the typical steps required to perform various worklfow scenarios.

### Start working on a new feature

When starting to work on a new feature, a new branch should be forked from development.

First, I recommend refreshing your local development with origin to make sure you have the latest version of the code.

bashRDarkCreate new feature

During development, all commits should be pushed to the feature branch.  Once all the work is done and tested locally, it can be merged into development for QE certification.  I recommend re-syncing your branch with development to ensure your PR contains no merge conflicts.  If merge conflicts arise from the local merge, fix them before submitting your PR.  This will save a lot a of churn.

bashRDarkPush new feature

**Important note**: Developers need to be careful when merging into development.  Developers are responsible for being aware of when a release branch will be cut from development.  Features going into development should allow QE enough time to validate prior to deployment.  If a feature is too big to be fully validated before the current release deployment, it should be kept in your local feature branch until a release branch is cut from development.  Constant communication between Devs, QEs and Product Owners is required to ensure that all parties involved are in agreement for a feature to be merged late in the release cycle.

### Cutting a new release branch

At the end of every each development cycle, a new release branch will be cut (forked) from development. 

bashRDarkCutting a release branch

Once the release is cut, it can be deployed to our staging environments for QE to resume/finalize validation.

**Important note**: Although it should be the developers' responsibility to ensure that all merged features had plenty of time to be validated, it would be safe to confirm with Devs, QEs, and Product Owners that a particular repository does not contain any uncertified features/bugfix prior to cutting the release branch.  Doing this upfront will save time and headaches down the line.

### Merging a release into master

At this point, the release branch has been fully validated and is ready for prime time. 

bashRDarkMerging a release branch

### What happens if we discover a bug in a release branch?

In this scenario, we follow the same steps as creating a bugfix branch but instead of forking from development, we fork from the release branch and merge back into the release branch for validation. 

bashRDarkCreating a bugfix from release

When you're ready to merge it back:

bashRDarkMerging a hotfix branch into master

As an additional step, you'll also need to merge the bugfix into development to ensure we don't re-introduce at the next release.

bashRDarkMerging a hotfix branch into development

### Creating a hotfix branch

In the event that a critical bug is discovered in production, a slightly different workflow will be required to hotfix it compared to a regular bugfix.  A new hotfix branch will need to be created from master instead of development.

bashRDarkCreating a hotfix branch

Once the fix completed, the branch should be deployed to a staging environment for validation.

### Merging a hotfix branch

Once the fix is fully validated, the hotfix branch can be merged back into master for deployment to production.

bashRDarkMerging a hotfix branch into master

Additionally, the hotfix branch should also get merged into development to ensure the bug does not get re-introduced next release.

bashRDarkMerging a hotfix branch into development

### How to find balance between making small PRs and not merging code that is not intended for production?

Some feature are inherently large, no matter how you slice them (e.g. generating a new microservice).  There's been a push lately to encourage frequent check-ins and merges in order to have smaller PRs.  This seems to contradict the concept of only merging complete features intended for QE validation.  Creating "progress" PRs would put partial code into development that is not intended for production (yet).

We need to evaluate if the experiment framework would be adequate to cover all potential scenarios, especially with the new autoblock UI.  

Bottom line, we need to have discussions on how to strike a balance between keeping PRs at a reasonable size and isolating feature until they're ready.
