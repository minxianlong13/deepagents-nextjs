## How is auth Initialized in the Browser so that apps can authenticate?

1.  Once successfully logged in, a user's browser is immediately provided with a JSESSIONID auth cookie, an RD4\_ID\_\* cookie, and a cvent-auth auth cookie.
2.  The domain associated to the JSESSIONID cookie is **always exactly equal** to the domain of the Resdesk Classic server.  That way, Only communications with the Resdesk Server will contain a JSESSIONID cookie for auth, AS LONG AS the request came from a web page loaded from the Resdesk server in the first place, OR a browser navigates directly to Resdesk from another site.  Cross-site cookie sharing of a JSESSIONID cookie is disallowed by JBoss.
3.  The domain associated to the RD4\_ID\_\* cookie is always the parent domain of Resdesk (and therefore, the parent domain of everything else).  That's **core.cvent.org** in alpha, ts50 and it50, and **passkey.com** in pr50, sg50 and ct50.  This cookie is a 'shareable' version of the JSESSIONID:
    1.  It is bound to a parent (rather than app-specific) domain; and
    2.  It is an encrypted string, for additional security.
4.  The domain associated with the cvent-auth cookie is always the **_parent_ domain** of the RDK2 web access URL.  That way, _RDK2 along with any other app_ on the passkey.com domain will receive the cookie in browser communications with that browser.
5.  _NOTE for cvent-auth: Because the cookie domain (passkey.com) and the RDK2 document origin (manage2.passkey.com) are not exactly  the same, it means that the browser will not allow the our RDK2 browser-side javascript code to have read-access to the cookie.  This is the tradeoff we've made to achieve cross-app authentication sharing - if your application requires auth metadata on the browser side, you'll have to make a query/request to the server to fetch it._

  

## What does my app need to implement this auth?

1.  First and foremost, you're going to use the cvent-auth cookie and the bearer token id it contains for all of your primary authentication.  This mostly goes without saying.  The good news is that this auth is built-in to CDF out-of-box and is largely management-free - just provide the cvent-auth cookie to any remote call you wish to make out to any remote service.  As long as it lives in the same parent domain, you're good.
2.  BUT, your app will need to 'babysit' the Resdesk Classic session while the user is in your app playing around.  To do this, you will require a **SessionManager** to run in the user's browser, which will use an Apollo query to integrate with the passkey-authentication-service's **/sessionHandle** endpoint.  The /sessionHandle endpoint is supplied with a JBoss Session Id (from the RD4\_ID\_\* cookie) and the cvent auth BEARER token (from the cvent-auth cookie) to creating a _binding_ _record_ in our Oracle DB that maps JBoss Sessions → Cvent Auth Tokens.  As part of management, this endpoint will also refresh the keepalive value associated with the server side JBoss session - this prevents it from invalidating.  Here's the moving parts that you need:
    1.  You'll need a new **GraphQL datasource** to allow Apollo to communicate with the passkey auth service.
        1.  RDK2's datasource implementation is here: [https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/data-sources/passkeyAuthentication-api.ts](https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/data-sources/passkeyAuthentication-api.ts)
    2.  You'll need a new **GraphQL Mutation** that the Browser can call in order to cause your app to call the passkey-auth-service
        1.  RDK2's Mutation implementation is here: [https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/resolvers/auth/index.ts](https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/resolvers/auth/index.ts)
        2.  RDK2's Mutation definition is here: [https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/graphql/operations/manageSessionMutation.ts](https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/graphql/operations/manageSessionMutation.ts)
    3.  You'll need a new SessionManager React Component to track user activity in the browser and invoke the 'manage session' mutation once every few minutes in order to sustain the JBoss Session.  
        1.  RDK2's SessionManager component is here: [https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/components/userSession/UniversalSessionHandler.tsx](https://stash.cvent.net/projects/PC/repos/passkey-rdk2/browse/packages/passkey-rdk2/src/components/userSession/UniversalSessionHandler.tsx)

# Temporary Sticky Session Management between Resdesk and Microfrontend Apps

Currently, the Passkey dev team finds itself in a position of transition: Its legacy flagship product, Resdesk, is being broken down into smaller front-end modules (called 'Microfrontends' or _MFs_ herein) that are slowly replacing the older Struts-based UI screens that the monolithic Resdesk currently offers its customers.

So the team is dragging the application into the modern age 'in-place' - not with a single wholesale upgrade, but with incremental, strategic cutovers, piece-by-piece, of old Resdesk UI pages with new React-driven MFs.

## The challenge of session management continuity

One of the general challenges we face in this migration is the fact that Resdesk is a stateful, session-managed service, with session-managed user sessions accumulating 'user-journey' information as the user browses the application from one space to another, and then re-using that information (on the server side, from session memory) elsewhere in the application in often unpredictable ways.

In contrast, the new Microfrontends and their NextJS/Apollo-based backend-for-frontend (BFF) counterparts are _stateless_, and attempt to traverse the user through the application smoothly with any necessary user-journey context being _continually_ _provided_ , rather than being _remembered_ or _recalled_ from session persistence.

This presents a challenge at points of re-entry back into Resdesk classic - if our microfrontends are not persisting a user journey historical context, and Resdesk is sensitive to this, how do we re-enter from RDK2 to Resdesk 'Classic' gracefully without causing errors or introducing navigation problems?

These integration points between Microfrontends and Resdesk Classic (and vice versa) require careful consideration on several important points in order to ensure we do not break the user experience:

1.  **Cross-site browsing**: Clicking back and forth between apps shouldn't fire unwanted security policy or CORS triggers in the browser
2.  **_Same-origin_ policy management**: Secure communication between UI payloads served up from different origin domains in the same window should be allowed
3.  **Sticky session management**: Insofar that we continue to integrate with Resdesk Classic, all new apps need to ensure that the same Resdesk node is used and re-used in the same user session following login.
4.  **Session context loading**: To ensure that we provide the correct context data in order to load the requested screen in the requested app.

This document is intended to focus primarily on the sticky session problem, although points 2 will also be touched upon since it is related.

## Sticky sessions

So, we know that Resdesk uses stateful session management to track user journey data on the server side.  How does it do that?

1.  Resdesk uses the overrideable Wildfly session management framework to integrate with Oracle backend, where session metadata is stored.
2.  Created sessions are supplied with a unique identifer, which is encrypted and sent back to the user's browser in a cookie.
3.  Resdesk persists session object payloads (those are often large, and filled with user, event, hotel, room type and inventory information) in a local in-memory session cache.
4.  Cached session data is eventually _evicted_ due to logouts, or session inactivity.
5.  Cache is not distributed - local only.

#### Okay, so if Resdesk manages session data locally, and Resdesk load is distributed across N servers behind a load balancer...

...then how does this all still work when a user makes follow up requests to Resdesk after building their session history on one Resdesk node, only to be redirected by the load balancer to an entirely different node?

Sticky Sessions:

1.  An old Load Balancer trick as old as the hills. Sticky sessions allow user sessions to remember which node they were previously redirected to, so that they can be re-directed there again for subsequent requests.
2.  Available as an LB feature in AWS LBs.
3.  Cookie-based.  Browser requests passing through the Resdesk LB to a Resdesk Node will receive 2 new cookies (both of them separate from the auth cookie supplied by Wildfly):
    1.  A new same-site cookie that specifies and tracks the Resdesk Node behind the LB that processed the request (called AWSALB)
    2.  A second cookie with a relaxed same-site policy that other origins can use to do the same thing (named similarly - AWSALBCORS)
4.  Created by Resdesk when the user browses to the login screen.

The general idea is that AWS sticky session cookies have a lifetime of about 10 mins after initial creation.  If a user subsequently makes another request to Resdesk in that timeframe, they will send that cookie back to the Load Balancer, which will decrypt it and forward the user's request to the appropriate node.  As part of the response, the server will re-write that cookie back into the header with a new 10-minute TTL and send it back to the browser, which updates the cookie in its cookie repo.

So, a long as an active Resdesk user is making requests to the server within 10 min timeframes, they will always use the same Resdesk Node for the duration of their session.  Further, there are setTimeout() callbacks in the application running in the browser to ensure that requests are being made as long as a user's session is valid.  Keep in mind that for PCI-compliance reasons, after 15-or-so minutes of inactivity, users are automatically logged out of Resdesk. Any sticky session data kept for that user would begin to grow stale at that time.

#### Alright.  So then, we're good, right?  Nothing to see, here?

No, we still a have a problem.  The entirety of the above sticky session workflow works just fine in Resdesk classic.  In RDK2 (or in some other Microfrontend), we do NOT use or care about the session management in Resdesk Classic, and neither does the RDK2 load balancer require sticky sessions to function properly.

Here's what happens if we do nothing in Microfrontends:

1.  User browses to Resdesk and logs in:
    1.  Resdesk authorizes the user and creates a new server-side session object for storing session data, as prescribed in the details above.  This login activity also creates a valid BEARER token for RDK2 authorization.
    2.  Resdesk provides the browser with a JSESSIONID cookie (containing WF session id) for per-request Resdesk authentication, and also produces a cvent-auth cookie (containing BEARER token) for per-request RDK2 auth. 
    3.  Sticky session cookies are additionally created by the LB and sent back to the browser as part of the response
2.  User is redirected to RDK2 Home Page
3.  User engages in session activity in RDK2 for > 10 minutes.
    1.  RDK2 User Timeout Monitor (runs in browser) tracks user browser activity and prevents the browser application from instigating a PCI-enforced logout insofar that activity is detected (which would invalidate the BEARER token).
4.  AFTER +10 mins of RDK2 activity, user clicks a link back to Resdesk Classic.
5.  Browser displays a CSA error and user is blocked from browsing back to Resdesk, _despite_  the user activity monitor functioning correctly in step 3a.

#### So, what happened?

-   The user's session was broken because of an expired sticky session cookie.
-   The AWS LB for Resdesk Classic provided us with a sticky session cookie so that _other_  apps can return to Resdesk and use the same 'sticky' node that was used in the last request.
-   This cookie has a TTL of 10 minutes, and that is only managed/refreshed through issuing new subsequent requests inside of that 10 minute period.
-   In our 10 minute period described above, the user was engaged with RDK2 - NOT Resdesk Classic - and RDK2 requests do not pass through the Resdesk Classic LB.  Therefore, while users were active in that time, and requests were being made, the TTL of the sticky session cookie was counting down and _never being refreshed_.
-   When trying to browse back to Resdesk Classic, the LB redirected the request to a different load-balanced node rather than the sticky one.  This node has NO RECORD of the session data supplied by the user's Wildfly Auth Session Id.
-   Since the Resdesk Wildfly Node is not able to identify the user's cookie-provided auth session ID, the request fails with HTTP 401 (Unauthorized)
-   The CSA error reflecting the 401 is displayed.

## Fixing the RDK2 sticky session problem

For reference: Cvent JIRAd1d78885-1a8e-3259-b68d-3df198ee3d46GROUP-96863

So, what did we do to fix this problem? And, can we re-use this solution across other microfrontends?

The short answer is yes, but there are some things we have to do beforehand in order to accommodate the addition of other frontend apps:

1.  First thing we had to do was update the RDK2 User activity monitor callback (See step 3c in the _'Alright. So then, we're good...'_ section ).  This callback 'wakes up in short time intervals - 1 minute, I think - to see if the user had any capturable browser activity in the last time interval (captures mouse moves, button clicks, etc).  It can then decide what it wants to do if it has detected activity, and what it wants to do if it hasn't detected activity.
    1.  We updated the callback to make a cross-site call to Resdesk classic's /ok JSON endpoint when activity is detected.
    2.  This means that once a minute, if activity in RDK2 is detected, a remote call out to /ok is executed, which passes through the Resdesk Classic LB and subsequently refreshes the TTL on our sticky session cookie.
2.  There was a second part to this fix: Resdesk Classic did not implement CORS, and so did not allow browser documents with a different document origin to call back to the server.  Our calls to /ok were being fulfilled by the LB, but the response was disallowed by CORS because the origin of the RDK2 application (where the call originated) was different from the destination origin.  As part of its security policy, browsers will not store Cookie header responses from requests that have failed CORS requirements.
    1.  To address this, we updated Resdesk Classic CORS configuration to conditionally allow requests from other document origin domains to be made to resdesk:
        1.  In our lower environments (alpha, ts50, sg50), we allow cross-origin requests to Resdesk from ANY domain (this allows us to cross-navigate from RDK2 → alpha Classic on our laptops).
        2.  In CT50 and PR50 (Production), we allow cross-origin requests to Resdesk IF the current document origin is RDK2.

  

## What is left to be done?

### One Time Efforts

Unfortunately, the relevant CORS `Access-Control-Allow-Origin` header that had to be updated in Wildfly to allow RDK2 only allows us to supply a single origin value - you cannot supply a list of origin domain values to the browser using this header.  However, each application will require a tuned `Access-Control-Allow-Origin` header value specific to the application domain nonetheless.

How do we do this?  We need to do a few things in Resdesk to help us moving forward:

1.  We need to remove the `Access-Control-Allow-Origin` header configuration that is currently statically configured in Resdesk's standalone.xml file.  This was our stop-gap solution to get RDK2 to work, but with new incoming apps, this is no longer suitable.
2.  We need to create a **configurable origin whitelist** for Resdesk, possibly managed in Hogan.  This whitelist would be a list of domains allowed to make cross-origin requests to Resdesk.
3.  We need to replace the previously statically-configured `Access-Control-Allow-Origin` header value with a new dynamic, Filter-based java class that:
    1.  Inspects the request's URL target to see if it is trying to hit the 'ok' endpoint (The only CORS use case we have)
    2.  Inspects the request's host/domain header to make sure the request is originating from a whitelisted domain.
    3.  Dynamically inject the correct `Access-Control-Allow-Origin` header value into the request response to reflect the domain from whence the request came.

### Ongoing Efforts

New apps coming onboard as microfrontends integrated with Resdesk Classic will all have the same implications as mentioned above and will require the same mitigations:

1.  A user activity tracker in the browser to:
    1.  Invalidate the BEARER token after 15 mins (or whatever) of inactivity
    2.  To ensure that the Resdesk Classic sticky session cookie is refreshed as long as there is minute-by-minute browser activity.
2.  An update to Resdesk Configuration
