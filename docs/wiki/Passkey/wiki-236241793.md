# Roadmap

Due to the nature of our current branching strategy and project structure, spreading the migration across two sprints should help reduce the load and help facilitate developer adoption.  The first sprint (Nogal aka bug bash sprint) will be used to perform the bulk of the prep work to setup the migration.  At this point, developers are free to keep using our current branching strategy.  The second sprint (Olive) will mark the beginning of the new branching strategy.  Starting with Olive, every team members must adhere to the GitFlow principles in order to have a successful branching. Refer to these guidelines for additional details: 

### Nogal (bug bash) sprint

The goal of this release is to get started on upgrading our pipeline and eliminate as many roadblocks as possible. Our goal is to have all repositories (~54 microservices and ~33 legacy repos) updated to prevent any further pollution to reach their development branch once the Olive sprint starts. In order to minimize risk and workload, we're going to use a lazy loaded approach and only lock-up each repository to prevent accidental pollution and leave the refreshing of new "development" branches to individual developers as they encounter changes in such repo.

### Olive sprint

At this point, GitFlow principles should be full adopted across all teams.  Assuming our migration prep work was successful, this is where team members will start creating new "development" branches when they touch each repo.  Details can be found [here](https://wiki.cvent.com/display/PASKY/GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branchforlegacy).

### Beyond Olive

Clean up any processes, jobs, and branches rendered irrelevant.

# Microservice Impact

### Current branching structure

After reviewing our microservice structure, it appears that they are closely in-line with GitFlow principles and should require little effort to migrate.  Additionally, most microservices are not currently used in production so migrating those first is lower risk.  Most microservices are already using a "development" branch for feature work and master for production code. 

Only a handful of microservice still use "CI" as their development branch and these will be required to be updated.  Finally, it is important to note that all existing "development" branches are not guaranteed to be clean since the principle of only merging code intended for production into "development" was not mandatory in our previous branching practice.  Therefore, each existing "development" branch will need to be refreshed from master as part of the migration.

# Legacy Applications Impact

### Current branching structure

Passkey currently has 14 legacy applications and 33 repositories.  Each repository uses "QAI" as its development branch and master as its production branch.  To synchronize Passkey repos with our naming standards used in microservices, new "development" branches will have to be created from master for each repository.  At that point, QAI will no longer be needed and should be locked-down from the repository, this will mitigate the risk of accidentally merging a feature to QAI after the migration.  With the introduction of a new "development" branch and the adoption of GitFlow principles, migrating legacy repositories should not be a problem. The hardest transition will most likely be for developers to adopt the GitFlow principals. In order to ease this transition, our roll out strategy for legacy applications will be slightly less aggressive than microservices.  The details of this rollout are described below.

### CI tools

The continuous integration tool of our legacy apps are Jenkins for building artifacts and Octo to deploy them.  Only Jenkins would require a minor update to its default target branch configuration.  A test run was performed on May 11th, 2020 to test our current pipeline for any gotchas.  The test consisted of creating a fresh branch off master and attempting to build and deploy it to QAI using our current CI tools.  The test was successful, which adds to our migration confidence.

# Rollout Gameplan

### Microservices

#### Nogal sprint

As mentioned earlier, there's a list of 9 microservices that still don't have "development" as their development branch.  Each of these will need to be updated to use "development" and retire "CI".  This will require a Jenkins file upgrade, new branch creation, and adding proper permissions to the new branch ([Bitbucket Branch Permissions](https://confluence.atlassian.com/bitbucketserver/using-branch-permissions-776639807.html)).

The responsibility of upgrading each microservice will fall on their respective team owner and needs to occur during the Nogal sprint.  At the end of Nogal (June 23rd), a team of volunteers will update each microservice in order to rename their current "development" branch to "QAI" and set the renamed branch to read-only to avoid any future interaction.  This effort is strictly a precaution to ensure that we don't lose any code from partially merged feature. 

#### Olive sprint

At this point, every developers should have had their intro to GitFlow and know how to develop using its principles.  Communication will be submitted as soon as Olive starts to inform everyone that GitFlow is a GO and all microservice development must follow its principles.  If a developer encounters a microservice with a missing "development" branch, follow [these steps](https://wiki.cvent.com/display/PASKY/GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branchformicroservices).

That's it, microservices will be fully migrated once all the repositories are refreshed.

#### Olive release

In an ideal world, Team Leads should be free to cut a release branch straight from development upon release cutoff but it would be precautionary to double-check that each repository does not have any un-certified work in development. This does not apply to code isolated behind the experiment framework.  If such items exists, communications between all parties involved needs to occur and a course of action needs to be determined. 

Once the release branch is cut from development, communications should be submitted to inform developers that they can resume pushing features into development.

Finally, as per the current pipeline, once QE is all done certifying the release, each release branch can be merged into master and deployed to production.

### Legacy applications

#### Nogal sprint

Similar to microservices, each legacy repo will require to have it development branch locked-down.  Since the name of the branch used for development is QAI, there's no need to rename it.  Simply update the permissions to read-only.  This will be performed by a team of volunteer on June 23rd after hours.

#### Olive sprint

As with microservices, everyone should be using GitFlow at this point and all our repos should be ready for it.   Developers should follow [these steps](https://wiki.cvent.com/display/PASKY/GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branchforlegacy) when they encounter a repo with no "development" branch.

#### Olive release

Now that our new "development" branches are in place and all un-certified features have been merged, the release process should be as follows.

1.  Ensure that a given repo does not have any code not intended for production.
2.  Cut a release branch from development.
3.  Inform the team that the release branches have been cut and merging can resume.
4.  Build release artifacts
5.  Deploy applications for QE validation
6.  Merge release into master
7.  Go to Production

Mini-FAQ:

1.  What if there’s no “development” branch in the repository that I’m working on?  Follow these guidelines to create a fresh “development” branch and make sure to update the “Migration progress” section of the document: [https://wiki.cvent.com/pages/viewpage.action?spaceKey=PASKY&title=GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branch](https://wiki.cvent.com/pages/viewpage.action?spaceKey=PASKY&title=GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branch)
2.  What if I had a feature partially checked into QAI?  - This will be part of the migration effort for individual team members.  Those changes will not be reflected in the new “development” branch and you’ll need to re-create new PRs from your feature branch.
3.  What if I had certified changes in QAI but not yet released (i.e. not in master)? - Again, this will be part of the migration effort for individual team members.  Those changes will not be reflected in the new “development” branch and you’ll need to re-create new PRs from your feature branch.  As additional safety measure, the individual running point on the Nogal release for each team should double check that all features intended for the release were in fact merged into “development”.  If some features are missing, we’ll have to cherry-pick them into “development” like we used to do for “RELEASEITEMS”.  This issue should be one-time thing for the first release after the migration.
