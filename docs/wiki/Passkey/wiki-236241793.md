branching strategy and project structure, spreading the migration across two sprints should help reduce the load and help facilitate developer adoption.  The first sprint (Nogal aka bug bash sprint) will be used to perform the bulk of the prep work to setup the migration.  At this point, developers are free to keep using our current branching strategy.  The second sprint (Olive) will mark the beginning of the new branching strategy<span style="letter-spacing: 0.0px;">.  Starting with Olive, every team members must adhere to the GitFlow principles in order to have a successful branching. Refer to these guidelines for additional details:</span><span style="letter-spacing: 0.0px;"> </span><ac:link><ri:page ri:content-title="GitFlow Guidelines" /></ac:link></p><h3>Nogal (bug bash) sprint</h3><p>The goal of this release is to get started on upgrading our pipeline and eliminate as many roadblocks as possible. Our goal is to have all repositories (~54 microservices and ~33 legacy repos) updated to prevent any further pollution to reach their development branch once the Olive sprint starts. In order to minimize risk and workload, we're going to use a lazy loaded approach and only lock-up each repository to prevent accidental pollution and leave the refreshing of new &quot;development&quot; branches to individual developers as they encounter changes in such repo.</p><h3>Olive sprint</h3><p>At this point, GitFlow principles should be full adopted across all teams.  Assuming our migration prep work was successful, this is where team members will start creating new &quot;development&quot; branches when they touch each repo.  Details can be found <a href="https://wiki.cvent.com/display/PASKY/GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branchforlegacy">here</a>.</p><h3>Beyond Olive</h3><p>Clean up any processes, jobs, and branches rendered irrelevant.</p><h1>Microservice Impact</h1><h3>Current branching structure</h3><p>After reviewing our microservice structure, it appears that they are closely in-line with GitFlow using a &quot;development&quot; branch for feature work and master for production code. </p><p>Only a handful of microservice still use &quot;CI&quot; as their development branch and these will be production into &quot;development&quot; was not mandatory in our previous branching practice.  Therefore, each existing &quot;development&quot; branch will need to be refreshed from master as part of deploy pipeline is already setup correctly to handle our migration effort.</p><h1>Legacy Applications Impact</h1><h3>Current branching structure</h3><p>Passkey currently has 14 legacy applications and 33 repositories.  Each repository uses &quot;QAI&quot; as its development branch and master as its production branch.  To synchronize Passkey repos with our naming standards used in microservices, new &quot;development&quot; branches will have to be created from master for each repository.  At that point, QAI will no longer be needed and should be locked-down from the repository, this will mitigate the risk of accidentally merging a feature to QAI after the migration.  With the introduction of a new &quot;development&quot; branch and the adoption of GitFlow principles, migrating legacy repositories should not be a problem. The hardest transition will most likely be for developers to adopt the GitFlow principals. In order to ease this transition, our roll out strategy for legacy applications will be slightly less aggressive than microservices.  The details of this rollout are described below.</p><h3>CI tools</h3><p>The continuous integration tool of our legacy apps are Jenkins for building artifacts and Octo to deploy them.  Only Jenkins would require a minor update to its default target branch configuration.  A test run was performed on May 11th, 2020 to test our current pipeline for any gotchas.  The test consisted of creating a fresh branch off master and attempting to build and deploy it to QAI using our current CI tools.  The test was successful, which adds to our migration confidence.</p><h1><span style="color: rgb(0,0,0);font-size: 24.0px;letter-spacing: -0.01em;">Rollout Gameplan</span></h1><h3>Microservices</h3><h4>Nogal sprint</h4><p>As mentioned earlier, there's a list of 9 microservices that still don't have &quot;development&quot; as their development branch.  Each of these will need to be updated to use &quot;development&quot; and retire &quot;CI&quot;.  This will require a Jenkins file upgrade, new branch creation, and adding proper permissions to the new branch (<a href="https://confluence.atlassian.com/bitbucketserver/using-branch-permissions-776639807.html">Bitbucket Branch Permissions</a>).</p><p>The responsibility of upgrading each microservice will fall on their respective team owner and needs to occur during the Nogal sprint.  At the end of Nogal (June 23rd), a team of volunteers will update each microservice in order to rename their current &quot;development&quot; branch to &quot;QAI&quot; and set the renamed branch to read-only to avoid any future interaction.  This effort is strictly a precaution to ensure that we don't lose any code from partially merged feature. </p><h4>Olive sprint</h4><p class="p1">At this point, every developers should have had their intro to GitFlow and know how to develop using its principles.  Communication will be submitted as soon as Olive starts to inform everyone that GitFlow is a GO and all microservice development must follow its principles.  If a developer encounters a microservice with a missing &quot;development&quot; branch, follow<a href="https://wiki.cvent.com/display/PASKY/GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branchformicroservices"> these steps</a>.</p><p class="p1">That's it, microservices will be fully migrated once all the repositories are refreshed.</p><h4>Olive release</h4><p class="p1">In an ideal world, Team Leads should be free to cut a release branch straight from development upon release cutoff but it would be precautionary to double-check that each repository does not have any un-certified work in development. This does not apply to code isolated behind the experiment framework.  If such items exists, communications between all parties involved needs to occur and a course of action needs to be determined. </p><p class="p1">Once the release branch is cut from development, communications should be submitted to inform developers that they can resume pushing features into development.</p><p class="p1">Finally, as per the current pipeline, once QE is all done certifying the release, each release branch can be merged into master and deployed to production.</p><h3>Legacy applications</h3><h4>Nogal sprint</h4><p>Similar to microservices, each legacy repo will require to have it development branch locked-down.  Since the name of the branch used for development is QAI, there's no need to rename it.  Simply update the permissions to read-only.  This will be performed by a team of volunteer on June 23rd after hours.</p><h4>Olive sprint</h4><p>As with microservices, everyone should be using GitFlow at this point and all our repos should be ready for it.   Developers should follow <a href="https://wiki.cvent.com/display/PASKY/GitFlow+Roadmap#GitFlowRoadmap-Stepstocreateafresh%22development%22branchforlegacy">these steps</a> when they encounter a repo with no &quot;development&quot; branch.</p><h4>Olive release</h4><p>Now that our new &quot;development&quot; branches are in place and all un-certified features have been merged, the release process should be as follows.</p><ol><li>Ensure that a given repo does not have any code not intended for production.</li><li>Cut a release branch from development.</li><li>Inform the team that the release branches have been cut and merging can resume.</li><li>Build release artifacts</li><li>Deploy applications for QE validation</li><li>Merge release into master</li><li>Go to Production</li></ol><p><br /></p><h2>Steps to create a fresh &quot;development&quot;
