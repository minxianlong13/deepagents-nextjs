## **Initial Discovery Kickoff - Vision for** **High Level Workflow:**

* * *

From a Core Event Page, the initial assumption was the bridge page starts with no room block details yet, and is solving for the Cvent Event Management Customer working with their own Passkey license in either:

1.  Single hotel event
2.  Single multi-hotel event
    

Assuming there is a Passkey username mapped and linked to a user's Core account in this scenario: 

1.  After creating core Event, the Room Blocks navigation would lead to a “blank” bridge page with no Passkey linkage.  CTA for “Create room block”  - Click to open new window into Passkey account.    
2.  Once created in Passkey and core is refreshed, decided stats become visible for anyone who has access to that event object in core to see and has proper access into Manage. Ensure other users with visibility into that same core account but no Passkey account is solved for.

**Two things came out of initial discovery:** 

1.  For Passkey - Is prioritizing a workflow where the core user is first CREATING their Passkey event from Core really the right path for adoption success?  It was decided to focus more first on the LINKING of an already existing Passkey event to Core first rather than the creation. 
2.  Instead of just relying on MyCvent users to be able to link to a Passkey event, can we rely on a customer or account mapping, so all users of the core account can link to a Passkey event?  We don't have to rely on MyCvent users functionality only to surface what events can be linked and shown within Core.

In a sample set pulled, the majority of Passkey events get created days or weeks **after** the Cvent event.  2/3 ratio
