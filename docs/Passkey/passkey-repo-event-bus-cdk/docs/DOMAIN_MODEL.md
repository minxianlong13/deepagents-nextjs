# Domain Model

## Glossary

### Event Bus
A centralized messaging system that enables decoupled communication between microservices by routing events based on patterns and rules.

### Event Bridge
AWS managed service that provides serverless event bus functionality with built-in event routing, filtering, and transformation capabilities.

### Producer
A service or component that generates and publishes events to the event bus. In this context, the Passkey Manage API acts as the primary producer.

### Consumer
A service or component that subscribes to and processes events from the event bus. Lambda functions serve as consumers in this architecture.

### Event Schema
A structured definition of event data format, including required fields, data types, and validation rules.

### Dead Letter Queue (DLQ)
A queue that stores events that failed to be processed successfully, allowing for manual inspection and reprocessing.

### AsyncAPI
A specification for describing event-driven APIs, similar to OpenAPI for REST APIs. Used to generate event schemas and documentation.

### Elasticsearch Cluster
A distributed search and analytics engine used for storing, searching, and analyzing event data in real-time.

### Hogan
Cvent's configuration management system that provides environment-specific settings and secrets management.

### LocalStack
A local AWS cloud stack that emulates AWS services for development and testing purposes.

### CDK (Cloud Development Kit)
AWS framework for defining cloud infrastructure using familiar programming languages like TypeScript.

## Core Entities

### Event
**Description**: A discrete occurrence or state change in the system that other services need to know about.

**Attributes**:
- `id`: string - Unique identifier for the event
- `source`: string - The service that generated the event
- `detailType`: string - The type/category of the event
- `detail`: object - The event payload containing specific data
- `time`: datetime - When the event occurred
- `version`: string - Event schema version

**Relationships**:
- Generated by Producers
- Consumed by Consumers
- Routed through Event Bus

### Reservation
**Description**: A hotel booking record that represents a guest's stay at a property.

**Attributes**:
- `reservationId`: string - Unique identifier for the reservation
- `guestId`: string - Identifier for the guest making the reservation
- `hotelId`: string - Identifier for the hotel property
- `checkInDate`: date - Guest arrival date
- `checkOutDate`: date - Guest departure date
- `roomType`: string - Type of room reserved
- `status`: enum - Current reservation status (confirmed, cancelled, completed)
- `createdAt`: datetime - When the reservation was created
- `updatedAt`: datetime - When the reservation was last modified

**Relationships**:
- Associated with Guest
- Associated with Hotel
- Generates Reservation Events

### Guest
**Description**: A person who makes hotel reservations and stays at properties.

**Attributes**:
- `guestId`: string - Unique identifier for the guest
- `firstName`: string - Guest's first name
- `lastName`: string - Guest's last name
- `email`: string - Guest's email address
- `phone`: string - Guest's phone number
- `loyaltyNumber`: string - Loyalty program identifier

**Relationships**:
- Makes Reservations
- Receives Notifications
- Has Authentication Sessions

### Hotel
**Description**: A property where guests can make reservations and stay.

**Attributes**:
- `hotelId`: string - Unique identifier for the hotel
- `name`: string - Hotel name
- `address`: object - Hotel location details
- `amenities`: array - Available hotel amenities
- `roomTypes`: array - Available room categories

**Relationships**:
- Hosts Reservations
- Has Room Inventory
- Generates Property Events

### Notification
**Description**: A message sent to users through various channels (email, SMS, push).

**Attributes**:
- `notificationId`: string - Unique identifier for the notification
- `type`: enum - Delivery channel (email, sms, push)
- `recipient`: string - Target recipient identifier
- `template`: string - Message template identifier
- `data`: object - Template variables and content
- `priority`: enum - Delivery priority (high, normal, low)
- `status`: enum - Delivery status (pending, sent, failed)
- `scheduledFor`: datetime - When to send the notification

**Relationships**:
- Triggered by Events
- Sent to Guests
- Processed by Notification Services

### Authentication Session
**Description**: A user's authenticated session with the system.

**Attributes**:
- `sessionId`: string - Unique session identifier
- `userId`: string - Authenticated user identifier
- `authMethod`: enum - Authentication method used
- `authenticatedAt`: datetime - When authentication occurred
- `expiresAt`: datetime - When the session expires
- `ipAddress`: string - Client IP address
- `userAgent`: string - Client browser/app information

**Relationships**:
- Belongs to User/Guest
- Generates Authentication Events
- Has Security Context

## Business Rules

### Event Processing Rules

1. **Event Ordering**: Events must be processed in the order they were generated to maintain data consistency
2. **Idempotency**: Event consumers must handle duplicate events gracefully without side effects
3. **Schema Validation**: All events must conform to their defined AsyncAPI schema before processing
4. **Retry Logic**: Failed events are retried up to 3 times with exponential backoff before being sent to DLQ

### Reservation Rules

1. **Date Validation**: Check-out date must be after check-in date
2. **Status Transitions**: Reservations can only transition between valid states (confirmed → cancelled, confirmed → completed)
3. **Modification Windows**: Reservations can only be modified within allowed time windows before check-in
4. **Cancellation Policy**: Cancellations must follow hotel-specific cancellation policies

### Notification Rules

1. **Delivery Preferences**: Notifications must respect guest communication preferences
2. **Rate Limiting**: Notification sending is rate-limited to prevent spam
3. **Template Validation**: All notifications must use approved templates with valid data
4. **Retry Policy**: Failed notifications are retried based on priority and channel type

### Authentication Rules

1. **Session Management**: Only one active session per user unless multi-session is enabled
2. **Security Events**: Failed authentication attempts are logged and monitored for security threats
3. **Token Expiration**: Authentication tokens have configurable expiration times
4. **Multi-Factor Authentication**: High-privilege operations may require additional authentication factors

## Event Lifecycle

### Event Generation
1. Business operation occurs in source service
2. Event is created with appropriate schema
3. Event is published to EventBridge
4. Event routing rules determine target consumers

### Event Processing
1. Consumer receives event from EventBridge
2. Event schema is validated
3. Business logic is executed
4. Side effects are performed (database updates, notifications)
5. Processing result is logged

### Event Storage
1. Processed events are indexed in Elasticsearch
2. Event metadata is preserved for audit trails
3. Search indexes are updated for real-time queries
4. Historical data is retained per retention policies

## Data Consistency Patterns

### Eventually Consistent
The system follows an eventually consistent model where:
- Events are processed asynchronously
- Different services may have temporary data inconsistencies
- Consistency is achieved through event replay and reconciliation
- Compensating actions handle failed operations

### Event Sourcing
Key entities maintain their state through event streams:
- All state changes are captured as events
- Current state can be reconstructed from event history
- Audit trails are automatically maintained
- Time-travel queries are possible

### CQRS (Command Query Responsibility Segregation)
The system separates read and write operations:
- Commands generate events that modify state
- Queries read from optimized read models (Elasticsearch)
- Read models are updated asynchronously from events
- Different consistency guarantees for reads vs writes

## Integration Patterns

### Publisher-Subscriber
- Services publish events without knowing consumers
- Multiple consumers can subscribe to the same events
- Loose coupling between producers and consumers
- Dynamic subscription management

### Event-Driven Saga
- Complex business processes span multiple services
- Each step publishes events for the next step
- Compensating actions handle failures
- Process state is maintained through events

### Event Streaming
- Continuous flow of events for real-time processing
- Stream processing for analytics and monitoring
- Event replay capabilities for system recovery
- Temporal event queries and aggregations
